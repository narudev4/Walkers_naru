# モックアップ作成

トリガー: 「モックアップ作って」「モック」「デモ作って」「画面作って」

## 入力
$ARGUMENTS

## 全体フロー

```
① ヒアリング → ② 画面構成 + デザイン方向性策定（承認必須） → ③ Next.jsプロジェクト作成 → ④ 画面実装（frontend-designスキル適用） → ⑤ Vercelデプロイ → URL共有
```

> **絶対ルール**: ② の画面構成・デザイン方向性がユーザーに承認されるまで ③ に進んではならない。推測でコードを書き始めない。

## Step 1: ヒアリング

ユーザーに以下を確認する:

1. **クライアント名**: どの企業向けか
2. **サービス名 / プロジェクト名**: 何のモックアップか
3. **対象ユーザー**: 誰が使う画面か（エンドユーザー / 管理者 / 両方）
4. **必要な画面**: どの画面が必要か（LP、ダッシュボード、一覧、詳細 等）
5. **参考デザイン**: 参考にしたいサービス・サイトがあるか
6. **提案書との連携**: 既に提案書がある場合、機能一覧から画面を導出する
7. **デザインの好み**（任意）: 好きなテイスト・色・雰囲気があれば

### 自動収集

- **memories/facts.md** からクライアント情報を参照
- **03_projects/{クライアント名}/**: 既存の提案書・議事録があれば機能一覧を参照
- 既存モックアップがあればベースとして活用

## Step 3: Next.jsプロジェクト作成

### プロジェクト配置

```
output/deploy/{project-name}/
├── src/
│   ├── app/
│   │   ├── layout.tsx        # 共通レイアウト（Navbar/Footer）
│   │   ├── page.tsx          # ★ テストハブ（全画面へのリンク集）
│   │   ├── globals.css       # グローバルスタイル（CSS変数・フォント・アニメーション定義）
│   │   ├── {page1}/page.tsx  # 各画面
│   │   ├── {page2}/page.tsx
│   │   └── ...
│   └── components/
│       ├── Navbar.tsx         # 共通ナビゲーション
│       ├── Footer.tsx         # 共通フッター
│       └── ...                # 画面固有のコンポーネント
├── public/                    # 静的ファイル・フォント
├── package.json
├── next.config.ts
├── tsconfig.json
├── postcss.config.mjs
├── tailwind.config.ts（v4では不要）
└── .gitignore
```

### インデックスページ = テストハブ（必須）

`src/app/page.tsx`（`/`）は **テストハブ** として実装する。サービスのLPではない。

テストハブの構成:
- **ヘッダー**: サービス名（仮称）、「{クライアント名} 様向け モックアップ テストハブ」、Walkers
- **凡例**: 画面の分類タグ（例: 要件定義ベース / 提案書ベース / 追加機能）
- **セクション別リンク**: 機能カテゴリごとにグリッド表示
  - 各リンクに分類タグ（色分けドット + ラベル）を付ける
  - リンク先は各画面のパス（`/dashboard`, `/customers`, 等）
- **フッター**: 「株式会社Walkers」

参考実装: `output/deploy/tire-wms/index.html`

> **テストハブもデザイン方向性に合わせた美しいUIで作る。テストハブがないモックアップは不完全とみなす。**

### 技術スタック（固定）

| 項目 | 技術 |
|------|------|
| フレームワーク | Next.js (latest) + App Router |
| 言語 | TypeScript |
| スタイリング | Tailwind CSS (latest) |
| デプロイ | Vercel |

### プロジェクト初期化手順

```bash
cd output/deploy/
npx create-next-app@latest {project-name} --typescript --tailwind --app --eslint --src-dir --no-import-alias

```

> **注意**: `node_modules/` は `.gitignore` に含まれていること。`npm install` は初回のみ。

## Step 4: 画面実装（frontend-designスキル適用）

### 成果物タイプの判定（最初に・CRITICAL）

**実装に入る前に、作るものが「業務システム」か「魅せるページ」かを必ず判定する。** これを誤ると、業務システムなのに"宣伝LPっぽい"見た目になり、クライアントから繰り返し同じ指摘を受ける（実例: 福岡県・株式会社ナンバー案件で「LPっぽい」と複数回FB）。原因は、下記「フロントエンドデザインガイドライン」が本質的に *魅せるサイト（LP・ブランド・ポートフォリオ）* 向けに最適化されているため。業務システムでは多くの既定値を**反転**させる。

**A. 業務システム / 内部ツール（管理画面・SaaSダッシュボード・現場オペレーション・予約/在庫/CRM等）の場合 → 既定値を反転:**

- **アプリのクローム必須**: 永続する左サイドバー or 上部ナビ + パンくず + （必要なら）ツールバー。「今どこにいて、どこへ行けるか」が常に見える＝システムの記号。
- **情報密度を上げる**: テーブル・密なリスト・コンパクトな余白。1画面に業務で必要な情報を詰める。大きな余白や1要素だけの画面にしない。
- **定型・予測可能なレイアウトを採用する**（＝ユーザーが学習済みのパターン＝使いやすい）。「予想外・非対称・グリッド破り・要素の重なり」は**避ける**。下記ガイドラインの「定型を避けよ」はここでは適用しない。
- **業務文言で書く**: 機能名・操作ラベル中心。**ヒーロー見出し・宣伝コピー・大きなCTA・「〜をご体感ください」「〜を実現」等の価値訴求文を置かない**。
- **画像はニュートラルなプレースホルダー**（グレーのタイル＋画像アイコン）。絵文字を商品/カタログ画像の代わりにしない。
- **フォント/モーション**: 視認性優先・装飾は最小限。UDフォント（BIZ UDPGothic 等）が好適。マキシマリストな演出・派手なアニメは抑制し、操作フィードバック（hover/ローディング/トースト）に留める。
- **テストハブ(`/`)も「システムのランチャー/ナビ」として作る**（ヒーロー型LPにしない）。ロール別の画面ディレクトリ＋状況タイル等、"ログインして使うコンソールのホーム"に見せる。
- **受け入れテスト（実装後・必須）**: スクショを撮り「これは *仕事で開くツールのホーム* に見えるか、それとも *そのツールを宣伝するページ* に見えるか？」を自問する。宣伝の兆候（価値主張の見出し／〜ご体感ください等の一文／目立つCTA／スクロールする機能紹介セクション）が出たら**作り直す**。
- **モバイルアプリUIが含まれる場合**は、それ自体は実アプリ画面として作ってよい（端末フレーム内表示）。コンソール（デスクトップ）とモバイル画面を1つのシステムとして束ねる。

**B. LP・ブランドサイト・プロダクト紹介・マーケ・ポートフォリオの場合 → 下記ガイドラインをそのまま適用**（魅せる・記憶に残る・個性的フォント・マキシマリスト等）。

> 迷ったら A 寄りで判断する（業務システムを LP 風にする失敗の方がクライアント評価を大きく下げるため）。Step 2 のデザイン方向性提示の段階で、この判定結果（A/B）も併せてユーザーに確認するとよい。

### デザイン思考（コーディング前に必ず実行）

コードを書く前に、Step 2で承認されたデザイン方向性を基に以下を内部で明確化する:

1. **Purpose**: このUIはどんな問題を解決する？誰のためのもの？
2. **Tone**: 承認された美的方向性を徹底する（ブルータリズム、ラグジュアリー、レトロフューチャー、ミニマル等）
3. **Differentiation**: このUIの「忘れられないポイント」は何か？

### フロントエンドデザインガイドライン（CRITICAL）

以下のガイドラインは**全画面に適用する**。Step 2で承認された方向性に沿って実装する。

#### タイポグラフィ
- **個性的で美しいフォントを選ぶ**。Google Fontsから目的に合った特徴的なフォントを選定する
- ディスプレイ用フォント（見出し）+ ボディ用フォント（本文）のペアリング
- `next/font/google` でフォントを読み込み、CSS変数で管理する
- **禁止フォント**: Inter、Arial、Roboto、system-ui等のジェネリックフォント。Space Grotesk等の「AI頻出フォント」も避ける

#### カラー & テーマ
- CSS変数（`globals.css`）でカラーパレットを一元管理する
- **支配色 + 鋭いアクセントカラー**の構成。均等配分の淡いパレットは避ける
- ライト/ダークはStep 2の承認に従う。毎回同じにせず案件ごとに変える
- **禁止**: 紫グラデーション on 白背景、その他AIが頻出させる定番配色

#### モーション & アニメーション
- **ページロード時**: `animation-delay` を使ったスタガード（段階的）フェードイン
- **スクロールトリガー**: Intersection Observer APIで要素の出現時にアニメーション
- **ホバーエフェクト**: 予想外の変化で驚きを与える
- CSSアニメーションを優先。Reactの場合は Motion ライブラリも可
- マキシマリストな方向性なら派手に、ミニマルなら抑制的に。方向性に合わせる

#### 空間構成 & レイアウト
- **予想外のレイアウト**: 非対称、要素の重なり、対角線的な流れ、グリッドを破る配置
- 潤沢なネガティブスペース OR 意図的な密度感（方向性次第）
- クッキーカッターな定型レイアウトを避ける

#### 背景 & ビジュアルディテール
- 単色背景をデフォルトにしない。雰囲気と深みを作る
- 方向性に合わせて以下を活用: グラデーションメッシュ、ノイズテクスチャ、幾何学パターン、レイヤードされた透過、ドラマチックなシャドウ、装飾ボーダー、グレインオーバーレイ

#### 絶対に避けるべきこと（AIスロップ）
- ジェネリックフォント（Inter、Roboto、Arial、system fonts）
- 紫グラデーション on 白背景
- 予測可能な定型レイアウト・コンポーネントパターン
- 文脈無視の没個性デザイン
- **毎回同じデザインに収束すること** — 案件ごとにフォント・カラー・テーマ・美的方向性を変える

> **重要**: 実装の複雑さは美的方向性に合わせる。マキシマリストなデザインには手の込んだアニメーションとエフェクトが必要。ミニマルなデザインには抑制、精密さ、スペーシングとタイポグラフィへの繊細な配慮が必要。

### 基本実装ルール

1. **モックアップなのでバックエンドは不要** — データはハードコード or ダミーデータ
2. **レスポンシブ対応必須** — PC / タブレット / スマホで見れること
3. **日本語UI** — テキストは全て日本語
4. **ナビゲーション** — 全画面間を遷移できるNavbarを設置
5. **インタラクション** — ボタンのhover、モーダル、タブ切り替えなど基本的なUIインタラクションは実装する
6. **ダミーデータ** — リアルに見えるダミーデータを入れる（空の画面にしない）
7. **外部CDN不使用** — Tailwind CSSのみでスタイリング。外部CSSやアイコンライブラリはnpmでインストールする
8. **画像** — AI画像生成は **Codex の image gen2** を第一選択とする（Codex MCP `codex` ツール経由 or `codex:codex-rescue` エージェントに image gen2 での生成を指示）。物件写真・ヒーロー画像等を生成し `public/images/` に配置する。CSSグラデーションのみのプレースホルダーはクオリティが低く見えるため、画像生成を第一選択とする。生成できない場合のみグラデーション代替を許容する

### コンポーネント設計

- 共通コンポーネント（Navbar, Footer, Button, Card等）は `src/components/` に配置
- 画面固有のコンポーネントも `src/components/` に配置
- 1ファイルが200行を超えたらコンポーネント分割を検討

## Step 5: Vercelデプロイ

### Basic認証（必須・2026-07-20〜）

<!-- 発火条件: 2026-07-20 naru指示「今後モックには必ずBasic認証つける」。以降すべてのモックアップのVercelデプロイに適用する。廃止条件: naruが本ルールの廃止を明示した場合、またはVercel純正のDeployment Protection機能（Pro以上のプラン）に統一する方針へ変更された場合に廃止。 -->

**デプロイするすべてのモックアップに Basic 認証を必ずかける**（URLが第三者に漏れても中身を見られないようにするため。クライアントがURLを開くだけで見れる、という従来の運用は廃止）。Vercel純正のPassword Protectionはプラン依存で使えない場合があるため使わず、Next.js の `proxy.ts`（v16以降。旧`middleware.ts`）でアプリケーション層に実装する。

`src/proxy.ts` を作成（プロジェクトルート直下、`src/app/`と同階層）:

```ts
import { NextResponse } from "next/server";
import type { NextRequest } from "next/server";

export function proxy(request: NextRequest) {
  const user = process.env.BASIC_AUTH_USER;
  const pass = process.env.BASIC_AUTH_PASSWORD;
  const auth = request.headers.get("authorization");

  if (auth?.startsWith("Basic ")) {
    const [u, p] = Buffer.from(auth.slice(6), "base64").toString().split(":");
    if (u === user && p === pass) return NextResponse.next();
  }

  return new NextResponse("Authentication required", {
    status: 401,
    headers: { "WWW-Authenticate": 'Basic realm="Protected"' },
  });
}

// v16でファイル名はmiddleware.ts→proxy.ts、関数名はmiddleware→proxyに変わったが、
// configのexport名は変わらず`config`のまま（`proxyConfig`ではない。誤って`proxyConfig`にすると
// Next.jsに読まれず一切フィルタが効かない＝全ページ含め集客用LPまで認証がかかってしまう）
export const config = {
  matcher: "/((?!_next/static|_next/image|favicon.ico).*)",
};
```

- 認証情報は `BASIC_AUTH_USER` / `BASIC_AUTH_PASSWORD` の環境変数で管理し、**コードにハードコードしない**
- ユーザー名は `walkers` 固定でよい。パスワードは案件ごとに推測されにくい文字列（8文字以上の英数字）を都度生成する
- ローカル開発用に `.env.local` にも同じ値を設定する（`.gitignore` 済みであることを確認）
- Vercel側は `vercel link --yes` でプロジェクトをリンクした後、`vercel env add BASIC_AUTH_USER production --value "walkers" --yes` と `vercel env add BASIC_AUTH_PASSWORD production --value "{生成したパスワード}" --yes` で設定する
- **注意**: このスキルで作るプロジェクトはGitリポジトリ非連携のままCLIから直接デプロイする運用のため、`env add NAME preview` はGitブランチ指定を要求されて失敗する（"Project does not have a connected Git repository" エラー）。Preview環境変数は設定不可のため無視し、production環境変数のみ設定すれば足りる（下記の通り初回から本番デプロイするため）
- **内部業務ツールと一般公開LP（集客用シミュレーター・診断ツール等）が1つのモックアップに混在する案件では、対象読者が違う画面を同じ認証・同じナビゲーションに混ぜない**（実例: 鯉幟株式会社案件で相続税シミュレーターLPを内部の物件管理サイドバーに含め、Basic認証で公開LPまでロックしてしまっていた）。公開LPのルートは`matcher`の否定先読みに追加して認証対象から除外し、内部ツールの永続サイドバーのナビ項目にも入れない（別途footer等で参照リンクを置く程度に留める）

### デプロイ手順

環境変数がproductionにしか設定できないため、無印（preview）デプロイでは401になり確認できない。**初回から本番相当でデプロイする**:

```bash
cd output/deploy/{project-name}
npx vercel --yes --prod
```

- 初回は Vercel アカウントとの紐付けが必要（`vercel login` 済みの前提）
- プロジェクト名は `{project-name}` をそのまま使用
- **Basic認証を必ずかけてからデプロイする**（上記参照。認証なしでの公開は禁止）
- デプロイ完了後、URLと認証情報（ユーザー名・パスワード）をユーザーに共有する

### デプロイ後の更新


## ルール（厳守）

1. **画面構成・デザイン方向性を必ずユーザーに承認させてからコードを書く**（推測で実装しない）
2. **技術スタックは固定**（Next.js + TypeScript + Tailwind CSS + Vercel）。他の技術を勝手に使わない
3. **`output/deploy/{project-name}/` に配置する**。`output/gui/` には置かない
4. **Vercelにデプロイしてからユーザーにデプロイ済みURLを共有する**
5. **全モックアップに Basic 認証を必ずかける**（2026-07-20〜。認証なしでの公開は禁止。実装詳細はStep 5参照）
6. 提案書がある案件は、提案書の機能一覧と矛盾しないモックアップを作る
7. 既存のモックアップがある場合はベースとして活用する（ゼロから作り直さない）
8. レスポンシブ対応は必須（クライアントがスマホで見る可能性がある）
9. ブラウザを `open` コマンドで勝手に開かない（URLをテキストで伝える）
10. **AIスロップを絶対に出さない** — Inter/紫グラデーション/白背景の定型デザインは禁止。案件ごとに独自のデザインを追求する
11. **デザインの複雑さは方向性に合わせる** — マキシマリストなら派手に、ミニマルなら繊細に
