# 提案書作成

トリガー: 「提案書作って」「提案書」「プロポーザル」

## 入力
$ARGUMENTS

## 利用ツール

| ステップ | ツール | 用途 |
|---------|--------|------|
| Step 1 | Read (built-in) | `memories/facts.md`、ローカル提案書・議事録の参照 |
| Step 1 | Glob (built-in) | `03_projects/` 内の既存ドキュメント検索 |
| Step 1 | `get_events` (google-workspace MCP) | MTG情報（参加者・日時）取得 |
| Step 1 | `search_docs` (google-workspace MCP) | Geminiメモ・既存提案書の検索 |
| Step 1 | `get_doc_as_markdown` (google-workspace MCP) | Geminiメモ・ドキュメント本文取得 |
| Step 3 | `copy_drive_file` (google-workspace MCP) | テンプレートのコピー（`parent_folder_id` にマイドライブ「提案書」フォルダIDを指定） |
| Step 3 | `batch_update_doc` (google-workspace MCP) | プレースホルダー置換（operation: `find_replace` 一括 / `replace_text` index個別） |
| Step 3 | `inspect_doc_structure` (google-workspace MCP) | 重複プレースホルダーの index 取得（`detailed=true, tab_id`） |
| Step 3 | `search_docs` (google-workspace MCP) | 既存提案書の検索（更新時） |
| Step 3 | Write (built-in) | ローカルバックアップ保存 |

## 全体フロー

```
MTG実施 → ① 情報収集 → ② 骨子策定（承認必須） → ③ Google Docs作成 → ④ レビュー・改訂 → 提出
```

> **絶対ルール**: ② の骨子がユーザーに承認されるまで ③ に進んではならない。推測で本文を書き始めない。

> **提案書の基本思想**: 提案書とは、前回のMTGで口頭で話した内容を改めて書類に起こし、クライアントと合意を取るためのもの。AIが一般論やテンプレ的な文章を書く場ではない。MTGで実際に話された課題・方向性・合意事項をベースに、それを正確に文書化することが目的。したがって、Geminiメモや議事録などMTGの一次情報が最も重要なインプットであり、それがない状態でAIが推測で本文を書くことは禁止。

## Step 1: 情報収集（インプット整理）

### 1-A: 自動コンテキスト読み込み（最初に必ず実行 — 推測の前に読む）

**ヒアリングより先に、ローカル＋クラウドの一次情報を自動で読み込む。** 議事録があるのに項目を聞き直すのは禁止。

1. **案件の特定**: `$ARGUMENTS`・トリガー文から案件名（`03_projects/` 直下のディレクトリ名）を判定する。判別できないときだけ「どの案件の提案書ですか？」と1問だけ確認する。
2. **一次情報を Glob → Read で自動収集**（MTGの実際の発言＝最重要インプット）:
   - `03_projects/{案件}/minutes/**/minutes.md` と同階層の `transcript.txt`（議事録・逐語。`meeting-transcribe` 出力。**最優先**）
   - `03_projects/{案件}/proposal/`・`03_projects/{案件}/` 直下の既存提案書・要件メモ（あれば版番号付与の判断材料）
   - `00_context/memories/facts.md`・`decisions.md`（クライアント情報・商談状況・決定事項）
   - `04_sales/` 配下に該当案件のパイプライン情報があれば参照
3. **MCP が使える場合のみ追加収集**:
   - `get_events(q="案件名")` で MTG 日時・参加者
   - Gemini メモ: `search_docs` → `get_doc_as_markdown` で本文取得
4. 読み込んだ一次情報から **課題・要件・合意事項・ネクストアクション・予算/スケジュール感・参加者** を抽出し、出典（どのファイルの何行か）を自分の中で押さえる。

### 1-B: 不足分だけヒアリング（gap-filling）

- **自動読み込みで埋まった項目は聞き直さない。** 埋まらなかった・確証が持てない項目だけをピンポイントで質問する（1メッセージ1質問）。
- 憶測禁止: 一次情報に無い重要事項（金額・固有名詞・意思決定）は断定せず確認する。
- **一次情報が一つも見つからない場合に限り**、従来型の対話ヒアリングにフォールバックする。確認項目: クライアント名・担当者 / 案件名・サービス名（仮称）/ 背景・課題 / ターゲット / 主要機能 / 予算・スケジュール感 / 競合・参考サービス。これらは埋めるべき項目のチェックリストであり、一度に全部は聞かない。実際の質問は1メッセージ1問に絞り、回答を起点に順次埋める。

### 1-B2: 「先方企画済み案件」の判定（1-Cの前に必ず実行）

一次情報を読んだ時点で、**この案件が「先方が既に企画・要件定義済みで、Walkersには開発だけを依頼している」タイプかどうか**を判定する。判定を後回しにして骨子を先方目線で書いてしまうと、Step 2以降が丸ごとやり直しになる（2026-07 センス・インターナショナル案件で発生）。

**判定基準（いずれか2つ以上に当たれば「企画済み案件」と判定）**:
1. 先方から企画書・要件定義書・仕様書・ワイヤーフレーム等、サービスの中身（名称・概要・ターゲット・機能・マネタイズ・業務フロー）を先方が作成した資料が提供されている
2. 資料のタイトルや依頼文言が「見積もり依頼」「開発をお願いしたい」等、企画フェーズを終えて発注フェーズにあることを示している
3. 初回MTGで、サービスの目的・ターゲット・特徴・展開計画を説明していたのが先方側であり、Walkers側はヒアリング（聞く側）に終始していた
4. 議事録・Geminiメモに「御社が考えたサービスを開発する」「ご依頼内容の通り開発する」に近いニュアンスの発言がある

**判定結果の扱い**:
- 「企画済み案件」と判定した場合 → Step 1-Cの構造化と、Step 2骨子の「提案概要」「現状整理」の扱いを下記の通り変更する（詳細はStep 2参照）
- 判定に迷う場合は骨子提示時にユーザーへ確認する（「本案件は先方企画済み型として、提案概要・現状整理を簡略化する想定でよいか」を1問で確認）
- 通常型（Walkers側が課題を診断してソリューションを設計する案件）は従来のフルセクション構成のままでよい

### 1-C: 情報の構造化

収集した情報を以下の形式で整理し、ユーザーに確認する:

```
■ クライアント: {企業名} {担当者名} 様
■ 支援内容: {内容}
■ 概要: {一行で}
■ ターゲット: {誰が使うか}
■ 主要課題:
  - {課題1}
  - {課題2}
  - {課題3}
■ 求められている機能:
  - {機能1}
  - {機能2}
  - ...
■ 予算感: {あれば}
■ スケジュール感: {あれば}
■ 参考サービス: {あれば}
```

→ **この整理内容が正しいか確認してから Step 2 に進む**

## Step 2: 骨子策定（構成案の作成）【承認必須】

収集した情報をもとに提案書の骨子を作成し、**ユーザーに提示して承認を得る**。

### 骨子に含める項目（表紙＋テンプレート9セクションに対応）

1. **表紙**: Walkersロゴ、サービス名、概要一行、クライアント名、提案日
2. **提案概要**: 目的、ターゲット、特徴、ローンチ目標、期待効果
3. **現状整理**: 業界・市場の現状、課題テーブル
4. **提案ソリューション**: 支援コンセプト、主要機能一覧テーブル
5. **取引/利用フロー**: ステップ形式でのフロー説明
6. **システム構成**: 開発形態、技術スタック、セキュリティ対策
7. **開発スケジュール**: フェーズ分け・マイルストーンテーブル
8. **補助金・資金調達活用戦略**: 該当する場合のみ
9. **概算見積もり**: ※提案段階では概算のみ。要件定義完了後に本見積りを提示する前提
10. **会社概要**: **テンプレートの値をそのまま使用（AIによる書き換え厳禁）**

> **CRITICAL — 会社概要セクションのルール**:
> 会社概要セクション（テンプレートの最終セクション）はテンプレートに正しい値が入力済み。提案書作成時にAIがこのセクションの値を書き換えること・推測で別の値を入れることは**絶対に禁止**。テンプレートからそのままコピーすること。会社名・代表者・設立・事業内容・所在地・Webサイトの全項目が対象。

> **重要**: 骨子段階で方向性のズレを修正する。ここが承認されてから本文執筆に進む。
> セクション5, 8は案件の性質に応じて取捨選択する。**プロジェクト体制セクションは標準では使用しない（テンプレートから削除済み・会社概要が最終セクション）。** 骨子段階でユーザーに「どのセクションを含めるか」を確認する。

### 「先方企画済み案件」の場合の「提案概要」「現状整理」の書き方（CRITICAL — 1-B2で判定した案件に適用）

**前提**: 提案書は常にWalkersが先方に向けて話す文書であり、Walkersが実際に提案しているのは**開発スコープの切り方・技術選定・開発スケジュール・費用の4つだけ**。先方が既に企画・診断・決定した内容（サービスの目的・ターゲット・特徴・事業背景・課題・展開計画）を、Walkersの言葉で説明し直す・診断し直す・主語を付けて語り直すことは提案ではない。

**やってはいけないこと（主語を変えるだけの偽装に注意）**:
主語を「御社は」に変えても、内容そのものが「先方から聞いた話をそのまま反復している」なら中身は先方目線のままで、Walkersとしての付加価値はゼロ。「御社は、従来型のプレスリリースでは反応が薄く〜という課題を抱えています」のように先方の説明をなぞっただけの文は、話者を変えても実質NG-24と同じ欠陥を含んでいる。

**具体的な書き方**:
1. **「提案概要」セクション**: サービスの目的・ターゲット・特徴・ローンチ計画の説明はしない。代わりに「本提案の目的＝Walkersが今回開発するPhase・スコープ・制約（稼働上限〇時間、単価〇円等）」だけを書く。先方企画の内容（サービス名・コンセプト等）は見出し直下に1〜2行「ご依頼内容の確認」として事実のみ転記するに留め、Walkers側の診断・評価・言い換えは加えない
2. **「現状整理」セクション**: 業界・市場の課題診断は書かない（先方は既に自分で診断済みであり、Walkersが後から「御社は〜という課題を抱えています」と診断し直すのは滑稽）。このセクション自体を省略するか、残す場合は「ご依頼内容の確認」（先方の企画書の要点を正確に転記するだけの事実確認）に置き換える
3. **削るか薄くした分量は、提案スコープ・技術選定・スケジュール・費用の説明の中に、必要な文脈だけ簡潔に織り込む**（例: 見積もり根拠の説明で「稼働上限40時間の制約下で、ご依頼いただいた機能のうち優先度の高いものから実装します」のように触れる程度）
4. **骨子提示時にユーザーへ明示する**: 「本案件は先方企画済み型のため、提案概要・現状整理を『ご依頼内容の確認』に圧縮/省略し、開発スコープ・技術・スケジュール・費用を中心に構成します」と一言添えて承認を取る

## Step 3: Google Docs作成（本文執筆）

承認された骨子をもとにGoogle Docsで提案書を作成する。

### 出力形式
- **Google Docs** で作成する（ローカルMDではない）
- `copy_drive_file` でテンプレートをコピー（**コピー先はマイドライブ「提案書」フォルダ。`parent_folder_id` に下記の提案書フォルダIDを必ず指定する**）→ `find_replace` でプレースホルダーを置換
- 既存の提案書を更新する場合は `search_docs` で検索 → `get_doc_as_markdown` で取得 → `batch_update_doc` で更新

### Google Drive 格納先（必須）

### テンプレート使用（必須）
- **テンプレートID**: `1SS_Xw7gGHPOpLj8x8lgUJr4gmJRE8OZUqSA7_4Fr5DA`
- **URL**: https://docs.google.com/document/d/1SS_Xw7gGHPOpLj8x8lgUJr4gmJRE8OZUqSA7_4Fr5DA/edit
- **手順**:
  1. `copy_drive_file` でテンプレートをコピーし、命名規則に従ったタイトルを付ける（`parent_folder_id="14NMX2LoSluaJkiNdz-iQy_HU_joJKXRK"`＝マイドライブ「提案書」フォルダを指定）
  2. `find_replace`（`batch_update_doc` の operations）で **一意な** `[プレースホルダー]` を骨子の内容に一括置換する
  3. **重複プレースホルダーの罠**: スケジュール表の `[期間]`×4、見積表の `[金額]`/`[備考]`、システム構成の `[推奨技術と理由を記載]`、体制の `[役割説明]`/`[人数]` など同一文字列が複数あるものは `find_replace` で一括置換すると全行同じ値になる（→ NG-3）。これらは `inspect_doc_structure(detailed=true, tab_id="t.0")` で各セルの index を取得し、`batch_update_doc` の `replace_text` を **index 降順** に並べて個別置換する（テンプレはタブ構造のため `tab_id` 指定が必須）。
  4. 不要なセクション・行（セクション5/8、未使用のステップ・役割枠等）があれば該当部分を削除する
  - **ツール名の注記**: `find_replace`・`replace_text` はいずれも `batch_update_doc` の operation `type` 名であり、独立した呼び出しツールではない（`find_replace`＝一意プレースホルダーの一括置換 / `replace_text`＝index指定の個別置換）。1 箇所だけの単純置換なら独立ツール `find_and_replace_doc` を使ってもよい。
- **禁止**: `create_doc` で空ドキュメントを作ってテンプレ構造を手動再現すること（書式が失われる）
- **禁止**: テンプレートを取得せずに執筆を開始すること

### ファイル命名規則
- 新規: `【{クライアント名}様】{案件名}のご提案`
- 改訂: `【{クライアント名}様】{案件名}のご提案 v{N}`

### ローカルバックアップ
- 保存先: `03_projects/{クライアント名}/proposal/YYYY-MM-DD_{案件名}.md`
- プロジェクトフォルダがない場合は作成する

### 執筆ルール
- 文体: ですます調、ビジネス文書として適切なトーン
- **文末は句点「。」**: 本文・箇条書きの各項目・表のセル内すべて。文になっていれば必ず付ける（体言止め・単語のみの項目は不要）。詳細は `.claude/refs/external-docs.md`「文末は句点」を参照
- **モックアップURLは提案書に記載しない**: 「画面イメージ」節やURL追記用の HTML コメントを差し込まない（`propose-and-demo` SKILL.md Step 4-A）
- 図表: テキストベースで構成案を示す（Docs段階ではテキスト中心）
- 見積もり: 金額部分は `【要入力】` プレースホルダーを置き、ユーザーが記入

### 文章品質の原則（CRITICAL — 2026-06 古谷レビューで確立）

1. **主述近接ルール**: 一文は40字以内を目安にする。主語と述語の間に長い修飾句を挟まない。声に出して読んで引っかかったら分割する
2. **先方目線の説明**: 業界用語・社内常識（準委任/請負、MVP、API従量課金など）を使ったら「なぜそうするのか」を一文で添える。Walkersの常識は先方の常識ではない
3. **1項目1行**: ターゲット・特徴・課題など複数の対象を一文に詰め込まない。「、および」「〜と〜」が出たら箇条書きに分割する
4. **先方が上に説明できるか**: 決裁者は「いくら？なぜその金額？何が含まれる？」を上司に聞かれる。提案書だけで稟議が通るか？を最終チェックの視点にする

### 見積もり・商流の基本方針（CRITICAL）

Walkersの標準的な受注フローは以下の通り。提案書はこのフローに沿って記載する:

1. **要件定義フェーズ（準委任契約）**: 要件定義・設計を準委任契約で先行実施する。提案書には要件定義の期間・想定工数・概算金額を記載する
2. **本見積り**: 要件定義完了後、確定したスコープに基づいて本見積りを提示する
3. **開発フェーズ（請負 or 準委任）**: 本見積り合意後に開発着手

したがって、提案書の概算見積もりセクションには:
- **要件定義フェーズ**: 準委任契約としての期間・金額（これは比較的確度が高い）
- **開発フェーズ**: あくまで概算レンジ（「要件定義後に本見積りを提示」と明記）
- **「要件定義完了後に正式な本見積りをご提示いたします」** の一文を必ず入れる
- **要件定義の標準時間単価**: 12,000〜15,000円/h（税別）。案件難度で調整（難案件は上限寄り・平易な案件は下限寄り）。総額＝単価×想定工数で算出し、単価・工数を変えたら総額も必ず連動更新する（旧標準10,000円/hは人材単価の上昇に伴い改定済み）

### 補助金活用セクションの記載ルール（CRITICAL）

対象: デジタル化・AI導入補助金等を提案に含める場合。

**前提理解**: この補助金は「開発費を補助する制度」ではなく、「事務局に登録された“既製ITツール”の導入費を補助する制度」。補助対象になるのは原則この3費目のみ:
1. ソフトウェア購入費（事務局に登録済みのITツール）
2. クラウド利用料・サブスク（一定年数分。例: Shopifyベーシックプラン）
3. 導入関連費＝役務（導入設定・マニュアル作成・操作研修・保守サポート等。**上限あり**）

→ カタログ外のフルオーダー制作（追加開発）は原則この枠の外。**補助金セクションを書く前に、提案する費目が上記のどれに該当するか（ツール本体／サブスク／導入役務／追加開発）を必ず確認する。「構築費＝当然に補助対象」と決め打ちしない**（どの枠でどう積むかは案件ごとに補助金担当に確認）。

**補助率は固定値で書かない**: 枠・申請区分・賃上げ要件で **1/2〜2/3**（原則1/2、条件を満たすと2/3）。常に「1/2〜2/3（申請区分で変動）」とレンジで書く。2/3固定で断定しない。

**派生数値の連動（最重要）**: 補助率がレンジなら、そこから計算される還付額・実質負担・コスト比較もすべてレンジで書く。下限ケース（1/2）で破綻する金額断定（「補助200万を狙える」「還付約100万」等）は書かない。

**交付決定後着手が原則**: 交付決定前に発注・契約・支払いした経費は対象外。スケジュールは「要件定義（自費）→ 申請 → 交付決定後に構築一式」の順で書く。

**成功報酬（補助金サポート費）**: 採択額の **8〜15%** で提示（市場水準。案件で調整）。単一値（8%固定等）で書かない。

**補助上限**: 枠・導入プロセス数で変動。具体額は年度の公募要領で確認し、提案書では「約」「補助上限の範囲内」と書く。

## NGリスト（過去提案書のFB分析に基づく禁止事項）

> 以下は11件の過去提案書とそのバージョン改訂履歴（v1→v2→v3→v4）を分析し、ユーザーが繰り返し修正・削除したパターンを抽出したもの。**これらを絶対に繰り返さないこと。**

### NG-1: テンプレート指示文の消し忘れ（CRITICAL）
- **実例**: 板垣・伊藤の提案書で「※補助金や資金調達が不要な場合は、このセクションを削除してください」がそのまま残っていた
- **実例**: セクション7のタイトルが「※本案件では該当なし（補助金・資金調達）活用戦略」になっていた
- **ルール**: 不要セクションは**セクション見出しごと完全に削除する**。テンプレート内の「※〜してください」指示文は最終ドキュメントに絶対に残さない
- **チェック**: 完成後に `※` で始まるテンプレート指示文が残っていないか全文検索する

### NG-2: 【要入力】プレースホルダーの大量放置
- **実例**: 板垣・伊藤の提案書で見積もり全行が「【要入力】」のまま、運用保守費用も「月額【要入力】」のまま提出
- **ルール**: ユーザーが記入する金額部分のみ `【要入力】` を使うのはOK。だが**1つの提案書内で3箇所以上の【要入力】が残る場合、ユーザーに「以下の項目が未入力です」と明示的にリストアップして確認を促す**
- **特に注意**: 見積もりテーブルの全行が【要入力】のまま完成報告するのは NG

### NG-3: コピペミスによるデータ重複
- **実例**: 1LCの提案書で見積もりテーブルの全4行が同じ金額「112,000〜224,000」になっていた（ライト/スタンダード/プレミアムが全て同額）
- **実例**: テレックの提案書でスケジュールのPhase 2/3/4が全て「約2週間」「要件定義フェーズにて詳細計画を策定」になっていた
- **ルール**: `find_replace`（`batch_update_doc`）実行後に、**テーブル内の全行が同じ値になっていないかを確認する**。特に見積もりテーブルとスケジュールテーブルは各行が異なる値を持つべき

### NG-4: 空のチームメンバー枠
- **実例**: 板垣・伊藤の提案書でプロジェクト体制の最後に「：」だけの空行が残っていた
- **ルール**: テンプレートの体制セクションには予備枠があるが、**使わない枠は削除する**。「：」や空のバレットは残さない

### NG-5: 「はじめに」スタイルの書き出し（❌ → エグゼクティブサマリー ✅）
- **実例**: BLUE SHIFT v2で「佐藤様、平素より大変お世話になっております」から始まる手紙調の書き出し → v3で全面削除し「エグゼクティブサマリー」に変更
- **ルール**: 提案書の冒頭は**ビジネスフォーマルな「提案概要」として構成する**。手紙調の挨拶文で始めない。MTGで既に関係構築済みのクライアントに対して、書面で改めてお世辞を述べる必要はない

### NG-6: 代表者情報の誤記（CRITICAL）
- **実例**: BLUE SHIFT v2・家BnB v1で代表者が「古谷大輝」（提案書作成者）になっていた → 正しくは「渡邊 敦司」
- **ルール**: 会社概要の代表者は**絶対に渡邊 敦司**。提案書の作成者（PM: 古谷大輝）と代表者を混同しない。会社概要セクションはテンプレートからコピーするルールを厳守

### NG-7: ジェネリックな市場分析（AI感のある文章）
- **実例**: 板垣「国内クラウドファンディング市場は年々拡大しており」、伊藤「コロナ禍以降の非接触ニーズとセキュリティ強化の両面から需要が拡大」
- **ルール**: 現状整理セクションは**クライアント固有の課題にフォーカスする**。業界全体の一般論や「〇〇市場は年々拡大」のような定型フレーズは使わない。MTGで聞いた実際の困りごと・具体的な数値（「毎月4〜5件の誤発注」「20社の仕入先」等）をベースに書く

### NG-8: 選択肢の過多（プラン3つ以上）
- **実例**: 家BnB v1で梅/竹/松の3プラン → v2でA/B 2プラン、BLUE SHIFT v3で2パターン → v4でコスト重視の1パターンのみ
- **ルール**: 見積もりの選択肢は**最大2パターン（推奨プラン + オプション拡張）**に留める。3つ以上の選択肢は意思決定を複雑にし、結局ユーザーが削る。推奨プランを明示すること

### NG-9: 冗長なユーザーフロー図・ビジネスフロー図
- **実例**: BLUE SHIFT v3で3アクター（医師/医療機関/運営チーム）の詳細ビジネスフロー → v4で全削除
- **実例**: 家BnB v1のASCIIアーキテクチャ図 → v2で削除
- **ルール**: フローやダイアグラムは**5ステップ以内の簡潔なもの**に留める。3アクター以上の複雑なフローは提案書ではなくミーティングで説明する。提案書はシンプルさが命

### NG-10: 「期待される効果」セクション
- **実例**: BLUE SHIFT v2の「定量的効果」「定性的効果」セクション → v3で全削除
- **ルール**: 「〇〇が改善されます」「△△の効率化が期待されます」のような漠然とした効果予測は**書かない**。代わりに、提案ソリューションの説明の中で具体的なメリットを自然に織り込む

### NG-11: 見積もり金額が過大（スコープ肥大化）
- **実例**: SincerelyYours v1で1,416万円 → v2で220万円（84%削減）、家BnB v1で350万円 → v3で180万円（48%削減）
- **ルール**: MVP提案の見積もりは**「小さく始める」が基本方針**。初回提案で大きな金額を出すと修正が必要になる。要件定義フェーズ（50-100万円）+ MVP開発（100-300万円レンジ）を基本とし、拡張はオプションとして提示する

### NG-12: スケジュールテーブルの空白・プレースホルダー放置
- **実例**: オーケーウェブ(latest)のスケジュールテーブルが全Phase「[期間]」「[作業内容]」のまま空白
- **ルール**: スケジュールは概算でも必ず**具体的な期間（「約2週間」「約1ヶ月」等）と作業概要**を記入する。空のスケジュールテーブルは提案書の信頼性を大きく損なう

### NG-13: セクション番号の不統一
- **実例**: 各提案書でセクション番号がバラバラ（補助金セクションの有無で後続番号がずれる）
- **ルール**: 不要セクションを削除した場合は**残りのセクション番号を振り直す**。番号が飛ぶ（6→8等）のは体裁が悪い

### NG-14: 造語・誤変換の放置
- **実例**: オーケーウェブの「順人期間」（4箇所）— 正しくは「順応期間」「習熟期間」または「オンボーディング期間」
- **ルール**: 完成前に**日本語として不自然な造語がないか確認する**。特にAI生成時に発生しやすい誤変換に注意

### NG-15: 責任分界の曖昧さ
- **実例**: SincerelyYours v1ではデザイン責任がWalkers側だったが → v2でクライアントがFigmaで提供する形に明確化
- **ルール**: 「誰が何をやるか」を**提案ソリューションまたはプロジェクト体制で明確に記載する**。特にデザイン・コンテンツ・テスト・運用の責任分界は曖昧にしない

### NG-16: 補助率を固定値で断定する（CRITICAL）
- **実例**: anything提案書 §7「補助率2/3を見込みます」→ 古谷FBで「1/2〜2/3（申請区分によって変動）」に修正
- **ルール**: デジタル化・AI導入補助金の補助率は枠・申請区分・賃上げ要件で変動（原則1/2、条件付き2/3）。常に「1/2〜2/3」とレンジで書き、根拠枠が確定するまで2/3固定で断定しない

### NG-17: ベース数値の変動で派生数値の整合が崩れる（CRITICAL）
- **実例**: anything提案書で補助率を2/3固定にしたため、還付額「約200万」・実質負担・コスト比較「約1/3」が全て固定値になり、1/2ケースで破綻していた → 古谷FBで全てレンジ化（還付「150〜200万」、コスト比「1/2〜1/3」）
- **実例**: 要件定義の単価を変更したのに総額（「20〜40万」）が未更新で不整合
- **ルール**: ベース数値（補助率・時間単価・成功報酬率等）がレンジ／変更されたら、そこから計算される全ての派生数値（還付額・実質負担・総額・コスト比較）を連動して更新する。下限ケースで崩れる金額断定は削除。完成前に「派生数値が全部整合しているか」を必ずチェックする

### NG-18: 業界・サービスのレンジ価格を単一値で書く
- **実例**: anything提案書 成功報酬「8%」→ 古谷FBで「8〜15%」に修正
- **ルール**: 成功報酬・保守費など幅のある価格を単一値で決め打ちしない。レンジで提示する（補助金の成功報酬は採択額の8〜15%が目安）

### NG-19: 金額に算出根拠がない（2026-06 古谷レビュー）
- **実例**: テクノ提案書で「要件定義準委任フェーズ / 20〜45万円 / 備考なし」→ 古谷FBで「時間単価15,000円〜 × 想定工数13〜30h」を追記
- **ルール**: 全ての金額に「単価 × 数量」または算出根拠を書く。根拠のない金額は先方の決裁者が上に説明できず決裁を通らない

### NG-20: ランニングコストが固定/変動/条件付きに分離されていない（2026-06 古谷レビュー）
- **実例**: テクノ提案書で「AIチャットボット保守+API従量：月額3〜6万円+API利用料（従量）」と一括記載 → 古谷FBで a)保守（固定）b)API従量課金（変動・実費精算）c)サーバ代（条件付き・既存同居可なら不要）に3分割
- **ルール**: ランニングコストは「毎月必ずかかる（固定）」「使った分だけ（変動・実費精算）」「条件次第でゼロになる（条件付き）」を明確に分離する。先方は予算を組む必要があり、全部まとめると稟議が書けない

### NG-21: 見積もり幅が3倍以上開いているのに理由がない（2026-06 古谷レビュー）
- **実例**: テクノ提案書で「HPリニューアル 30〜100万円」（3倍超）「AIチャットボット 〜300万円」→ 古谷口頭FBで松竹梅パターンか「要件定義後に確定」を強調すべきと指摘
- **ルール**: 見積もり幅が3倍以上開く場合は「要件定義後に確定見積りを提示」と明記するか、松竹梅パターンで最低ラインを示す。「30〜100万」だけでは「結局いくら？」と聞かれる

### NG-22: 英単語・数字の後に半角スペースが入る（2026-06 naruレビュー）
- **実例**: ワイヤ・アンド・ワイヤレス提案書で「SaaS 月額不要」「AI 駆動開発」「CRM/SFA としての」「Phase 1」など英単語・数字の直後に不要な半角スペースが26箇所 → 全削除
- **原因**: AI生成テキストは英単語・数字と日本語の間に半角スペースを挿入する癖がある（英文ライティングの習慣の混入）
- **ルール**: 日本語ビジネス文書では**英単語・数字と日本語の間に半角スペースを入れない**。`find_replace` や完成前チェックで `[A-Za-z0-9] [ぁ-ん]`・`[A-Za-z0-9] [ァ-ヶ]`・`[A-Za-z0-9] [一-龥]`・`[ぁ-ん] [A-Za-z]`・`[ァ-ヶ] [A-Za-z]`・`[一-龥] [A-Za-z]` パターンを検出し除去する。ただし固有名詞内のスペース（「Google Cloud」等）は除く

### NG-23: 伝われば十分な文脈を精緻な数値で説明する（2026-07 naruレビュー）
- **実例**: センス・インターナショナル提案書で「全国3,000人インフルエンサーネットワーク中のナノインフルエンサー層（フォロワー1,000〜19,999人）」と記載。「ナノインフルエンサー層」だけで十分伝わる箇所に、先方が当然知っている自社の規模数字と、後の機能要件セクションで詳述する登録条件のレンジを前倒しで詰め込んでいた
- **ルール**: 背景説明・ターゲット記述で、①先方が当然知っている自社の数字（ネットワーク規模・取引社数等）、②後続の機能要件セクションで詳述する具体的な数値条件（登録条件のレンジ等）は、文脈で十分伝わるなら省略する。数字を書くのは、それが提案の論拠（課題の深刻さ・打ち手の妥当性）を支える時だけにする

### NG-24: 提案書の話者が不明瞭・先方目線になっている（2026-07 naruレビュー）
- **実例**: センス・インターナショナル提案書で「本提案の目的」に先方サービスの説明文（「飲食店のリリース情報をインフルエンサー層に届けます」）を記載していた → 正しくは「本提案の目的は、Phase1（MVP）の構築です」等、Walkersが何を提案するかを主語にする。「現状整理」の課題文も主語なしで「従来型のプレスリリースは反応が薄く」と記載していた → 「御社は、〜という課題を抱えています」等、先方を明示的な主語にしてWalkersの診断として書き直した
- **ルール**: 提案書は常にWalkersが先方に向けて話す文書である。「本提案の目的」はサービスの説明ではなく、Walkersが何を（どのPhase・スコープ・制約で）提案するかを書く。「現状整理」の課題は先方を主語にして診断として書き、先方自身のセリフのように主語なしで書かない。サービス機能の説明（提案ソリューション以降）と、提案自体の目的・診断（提案概要・現状整理）を混同しない

### NG-25: 先方企画済み案件で、先方の企画をWalkersの診断のように語り直す（2026-07 naruレビュー）
- **実例**: センス・インターナショナル案件（先方が23ページの「サービス企画書兼お見積もり依頼書」を作成し、サービス名・概要・特徴・マネタイズ・ターゲット条件・業務フロー・機能要件・MVP範囲・ワイヤーフレームまで持ち込み済み。初回MTGでもWalkers側はヒアリングに徹していた）で、提案書「本提案の目的」に先方サービスの概要説明を書き、「現状整理」に「御社は、従来型のプレスリリースでは反応が薄く〜という課題を抱えています」「2026年10月の展示会でお披露目します」等、先方から聞いた話をそのまま（主語だけ変えて）反復していた。naru指摘：「先方が考えてきた内容をずっとなぜかこっちが説明（提案）するみたいな提案書になってるのが頭悪すぎる」「僕らはあくまで開発をするっていう提案じゃない？何でずっと先方目線なの？」
- **NG-24との違い**: NG-24は「主語がない／先方目線の文体」という表現レベルの欠陥。NG-25は主語を直しても解決しない、**セクションの存在自体が誤り**という構造レベルの欠陥。先方が企画・要件定義済みの案件では、「提案概要」で先方サービスを説明し直すことも、「現状整理」で先方の課題をWalkersが診断し直すことも、そもそも書くべきではない
- **ルール**: 案件が「先方企画済み案件」（判定基準はStep 1-B2）に当たる場合、「提案概要」「現状整理」は先方の企画・診断の語り直しをせず、「ご依頼内容の確認（事実の転記のみ）」に圧縮するか省略する。Walkersが提案するのは開発スコープ・技術選定・スケジュール・費用の4つだけであることを常に意識し、それ以外は先方企画のまま正確に転記するか、提案内容の説明に必要な分だけ簡潔に織り込む（詳細はStep 2「先方企画済み案件の場合の書き方」参照）

## 提案書の品質基準（過去の優良提案書から抽出）

### 良い提案書の特徴（テレック・1LC・境口・落合の優良事例から）
1. **クライアント固有の数値・事実がある**: 「20社の仕入先」「9店舗」「毎月4〜5件の誤発注」「191件/日の送信」等
2. **明確なタグライン/コンセプト**: 「発注側主導の仕入先集約型ポータル」「安心スコアで、住まい探しを変える」
3. **二段構えアプローチ**: 要件定義（準委任）→ 本見積り → 開発の段階的進行
4. **補助金/クロスセルの提案**: デジタル化・AI導入補助金・ものづくり補助金等の活用戦略を積極的に提示
5. **具体的なランニングコスト**: ユーザー規模別の段階的コスト試算（30人→100人→500人→1000人）
6. **責任分界の明確化**: Walkers側/クライアント側の担当範囲を明示

### 悪い提案書の特徴（改訂で削除されたパターン）
1. 手紙調の冒頭挨拶
2. ジェネリックな市場分析（「〇〇市場は年々拡大しており」）
3. 3つ以上のプラン選択肢
4. 冗長なフロー図（3アクター以上）
5. 「期待される効果」セクション（定量的/定性的効果の羅列）
6. テンプレート指示文の残骸
7. 初回から高額な見積もり（後で大幅削減が必要になる）
