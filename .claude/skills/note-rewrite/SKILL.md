# note記事リライト（山口流）

トリガー: 「note記事リライト」「Claude Code版に書き換え」「note切り口リライト」「note 山口流」

## 概要

既存のnote記事の**切り口だけを変えて別記事として量産**するワークフロー。
山口鳳汰さんがレクチャーした手順（録画: `output/manuals/note-yamaguchi/`）をスキル化したもの。

新規執筆ではなく**リライト前提**。マーケ的に「AI ◯◯」は競合が多くて刺さらないので、「Claude Code ◯◯」のように切り口だけ変えると一気に刺さる、という戦略。

## 戦略的意図

- マーケティングは**切り口の違い**で伸びが全然変わる
- 既存記事をベースにすることで品質を担保しながら量産可能
- noteは「自分の主張を出す場」なので**だである調**で書く（通常のコーポレート記事はですます調）

## ワークフロー全体像

```
[元記事 (note URL or 本文)]
    ↓
[切り口決定: 例「AI」→「Claude Code」]
    ↓
[Phase 1] ヒアリング & 標準パラメータ確認
    ↓
[Phase 2] 初稿生成（Markdown）
    ↓
[Phase 3] コメント指示 ⇄ 修正のループ（山口流の核）
    ↓
[Phase 4] note貼付用最終版を出力（人間最終調整用）
```

## 実行フロー

### Phase 1: ヒアリング

#### ヒアリング原則（重要）

- **「足りない情報だけ」を、1メッセージ1質問で聞く**。標準値が決まっている項目は確認しない。
- **必須項目** が未確定なら、その質問だけして待つ。複数同時に聞かない。
- **任意項目** はユーザー側から指定があった場合のみ受け取る。Claudeから聞き返さない。
- **発話から自明に読み取れる項目は暫定確定して進める**（例: ユーザーが「Claude Code版に書き換えて」と言ったら切り口=Claude Codeと暫定確定。再確認しない）。

#### 必須項目を聞く順番

1. **元記事** （これが無いと何も始まらない）
2. **切り口** （元記事を読んだ直後 or 発話から自明なら省略）
3. **CTA誘導先** （初稿を生成する直前。元記事を読んでから聞いた方がユーザーも答えやすい）

複数同時に聞かない。各ターンで1つだけ。

#### 項目一覧

| 項目 | 区分 | 標準値（未指定時の挙動） | 確認質問（必須項目のみ） |
|------|------|----------|---------|
| 元記事 | **必須** | なし | 「元記事のURL/ファイルパス/本文をください」 |
| 切り口 | **必須** | なし | 「どの切り口に置き換えますか？（例: AI→Claude Code）」 |
| 自社CTA動線 | **必須** | なし | 「CTAは何に誘導しますか？（例: Claude Code導入支援、URLがあれば一緒に）」 |
| 文体 | 任意 | **だである調**で進める | 聞かない |
| トンマナ | 任意 | **非エンジニア向け**で進める | 聞かない |
| 結論方向性 | 任意 | **元記事を踏襲**して進める | 聞かない（ユーザーから指示があれば上書き） |
| 戻し数 | 任意 | **聞かない**。ユーザー指定があればフロントマターに記録 | 聞かない |

> **NOTE**: 「戻し数3〜5」は録画で言及されたが意味が確定していない（リライト密度？AI往復回数？）。確定するまで Claude 側からは聞かない。

#### CTA URLが未指定の場合

CTA誘導先は聞くが、**URL自体が未指定**の場合は本文中に `[#]` プレースホルダーで残し、最終版でユーザーに差し替えてもらう。Claudeが勝手に URL を捏造しない。

**Markdownリンクの記法:**
```markdown
[Claude Code導入支援に相談する]([#])
```
表示テキストの後ろのカッコの中に `[#]` を入れる（リンク先 URL 部分が `[#]`）。

#### draft の上書きポリシー

**Phase 2 の初稿生成時も Phase 3 のループ中も**、毎回**同じ draft ファイルパスに上書き保存**する。過去の履歴は残さない（会話ログに残るので十分）。同名ファイルが既に存在する場合は**確認なしで上書きしてよい**（既存内容が要件を満たしていそうに見えても、必ず再 Write する。ユーザーから見て「リライトを実行した」ことが明示されないと混乱するため）。

#### 元記事の受け取り方

ユーザーから渡された形式に応じて読み込む。**形式が判定できないときは聞き返す。**

| 渡され方 | 読み込み方 |
|---------|----------|
| URL（例: `https://note.com/...`） | `WebFetch` で本文取得 |
| ファイルパス（例: `output/articles/...md`） | `Read` ツール |
| 本文ベタ貼り | そのまま使う |
| 記事タイトルだけ | `output/articles/` を `Glob` で検索 → 候補が複数あればユーザー確認 |

### Phase 2: 初稿生成

上記で読み込んだ元記事を素材に、切り口を置換した初稿を Markdown で出力する。

> **判断軸チェック（重要）**: 出力前に **元記事の各章/論点が新切り口で成立するか毎章確認**。Claude Code 切り口で前提が変わって成立しなくなる論点（例: 「チーム作りが大変」→ Claude Code で1人で回せるなら論点が消える）は **章ごと削除/書き換え**、本文・末尾ステップの残響も削除。詳細な判断軸は `.claude/skills/note-rewrite/yamaguchi-style.md` 参照。

**出力ルール:**

1. **フロントマター** — **draft の段階から付ける**（最終版で初出ではない）。ループ中も維持。
2. **タイトル** — 切り口を反映した新タイトル。元記事のフレーム（「終了する◯◯ vs 生き残る◯◯」等）は流用OK
3. **見出し階層**
   - H2はキャッチーな表現に
   - H2配下に**3〜4項目を並列で並べる場合は、それぞれをH3に上げる**（目次が綺麗になる・YouTube流用しやすい）
4. **文体** — だである調を徹底
5. **CTA動線** — 記事中に最低1つ、自社サービスへの導線を入れる。URL未指定なら `[#]` プレースホルダー
6. **出典の整理** — 不要な点記号・装飾は載せない
7. **ハッシュタグ・アイキャッチ案は draft では付けない**（Phase 4 で確定値を META に記載）

**保存先:** `output/articles/note/draft/YYYY-MM-DD_[テーマ].md`

### Phase 3: コメント指示 ⇄ 修正のループ（核となる工程）

山口流の最大のキモ。**ユーザーが修正したい箇所にコメントを埋め込んで返す → Claudeが反映 → 繰り返す**。

#### コメント記法

ユーザーは Markdown 上で `<!-- -->` を使って Claude への指示を埋め込む。
（録画では Ulysses のコメント機能を使っていたが、Claude Code から見れば Markdown のコメントとして等価。）

#### よくある指示パターン（録画より抽出）

| パターン | 指示例 | Claudeの対応 |
|---------|--------|------------|
| 装飾削除 | `<!-- この2つの点いらん。消して。今後も使わ -->` | 該当の点・記号を削除し、以降も使わない |
| 見出し階層調整 | `<!-- この4つの内容は見出し3として執筆 -->` | 並列項目をH3に揃える |
| H2キャッチー化 | `<!-- もっとキャッチーに -->` | H2を読者の手が止まる表現に書き直す |
| CTA挿入 | `<!-- Claude CodeのCTA動線をつくって -->` | 該当箇所に自社誘導CTAを挿入 |
| 太字 | `<!-- これ太字やな -->` | 該当部分を太字化 |
| 構成変更 | `<!-- ここでタスクロップは実際に触ってみてもらうの3つの内容を見出し3として執筆 -->` | 指定構成で書き直す |

#### Claudeの動作

ユーザーが**コメント入りMarkdown全文**を貼ってきたら:

1. すべての `<!-- -->` を読む
2. 各コメントの指示を反映
3. **コメント自体は削除して**修正版MDを返す
4. 「ここを変えました」とサマリも合わせて返す
5. ユーザーがさらにコメントを追加して投げてきたら、また反映

このループを **山口さんが「OK」と言うレベルまで** 繰り返す。

### Phase 4: note貼付用最終版を出力

**最終版への移行は明示シグナルが出てから**。Claude側で勝手に「これで完成だろう」と判断しない。

最終版発火シグナル（いずれか）:
- ユーザーから「OK」「完成」「最終版にして」「note用に出して」等の明示指示
- ユーザーから空コメント（変更なし）が返ってきた場合 → 「最終版にしますか？」と確認

シグナルが来るまでは Phase 3 のループを継続し、毎回 `output/articles/note/draft/` に上書き保存する。

シグナル発火後、**最終版**として以下のパスに保存する:

**保存先:** `output/articles/note/YYYY-MM-DD_[テーマ].md`（draft/ を含まない）

#### 最終版テンプレート（確定版）

参照: `output/articles/note/note-publish-checklist.md`（note投稿時のチェックリスト・naru 手動運用）

完成版MDは以下の構造で出力する。**カード貼付位置は1行マーカーで明示**し、note エディタ貼付後にすぐ目印として見つけられる形式にする。

> **重要**: 下記の `━━━ 📌 ... ━━━` は、naru が本文を `pbcopy` → note エディタに Cmd+V した後、UX版過去記事（[n46a5bfc33c96](https://note.com/app_dev_lab/n/n46a5bfc33c96)）から該当カードをコピペするための「貼付位置の目印」。note エディタ上で罫線+絵文字 1 行が本文中に埋もれず必ず目立つので、貼付位置で迷わない。naru が貼付後にこのマーカー行自体を削除する運用。

```markdown
---
（フロントマター）
---

# [タイトル]

[冒頭リード文（だである調・3〜5行）]

━━━ 📌 執筆者カード貼付位置 ━━━

━━━ 📌 運営会社カード貼付位置 ━━━

[本文（H2/H3階層・だである調・CTA動線含む）]

アプリ開発研究所では累計300件以上の開発・制作、200社以上の企業様を支援してきましたが、Claude Code時代だからこそ[テーマ]が事業成否の最大ポイントだと考えています。

「Claude Codeで何を作ればいいか分からない」「作ってみたが、どうも刺さらない」とお悩みの企業さまに、企画立案からClaude Codeでの開発、リリース後のUX磨き込みまで、一気通貫でご支援しています。

無料で相談する＞＞

開発支援サービスの概要はこちら＞＞
```

> **重要**: CTA は **「無料で相談する＞＞」「開発支援サービスの概要はこちら＞＞」の 2 行プレーンテキスト**で出す。Markdown リンク `[...]([#])` ではない。URL は note エディタで貼り付け側で設定する運用。`---` の区切り線も挟まない（UX版 = 鳳汰OK実物に揃える）。

#### 最終版に含めるメタ情報（本文末尾の `<!-- META -->` ブロックに記載）

```markdown
<!-- META（投稿時の参考情報・naru が note-publish-checklist.md を見ながら手動投稿）
ハッシュタグ: #ClaudeCode #AI駆動開発
記事タイプ: 無料
マガジン: あとで読む（アプリ開発研究所）
アイキャッチ案: [タイトル文字を入れた、シンプルで見やすい画像（AI生成OK）]
-->
```

#### 引き渡し（重要）

完成版MDは naru が手動で note に投稿する。**このスキル（note-rewrite）では投稿しない**。投稿手順は `output/articles/note/note-publish-checklist.md` 参照（旧 note-publish スキルは 2026-05-13 に廃止し静的チェックリストに置き換え）。

ユーザーへの最終メッセージ:

> 完成版を `output/articles/note/YYYY-MM-DD_[テーマ].md` に保存しました。
> noteへの投稿は `output/articles/note/note-publish-checklist.md` を見ながら naru 手動で行ってください（AI は関与しません）。

## YAMLフロントマター

**draft 段階から付ける**（Phase 2 の出力ルール参照）。最終版でもそのまま維持し、`status` だけ `draft` → `published` 等に書き換える。

```yaml
---
title: [noteタイトル]
original_url: [元記事のnote URL（https://...）または ファイルパス（output/articles/...md）。どちらでもOK、形式そのまま記入]
angle: [切り口（例: Claude Code）]
tone: だである調
target: 非エンジニア向け
cta: [CTA誘導先]
status: draft | published
date: YYYY-MM-DD
platform: note
---
```

## フィードバックループ

### 指示の曖昧さチェック（自動）

SKILL.md 編集時に empirical-prompt-tuning が自動発火（hook設定済み）。
subagent が指示を読んで詰まる箇所を検出 → 修正。

### 成果物の品質チェック（手動）

1記事ごとに山口さんから FB 受領 → 生のFB履歴を `00_context/memories/yamaguchi-feedback-log.md` に追記、判断軸の要約を `yamaguchi-style.md` に反映（**1FBごとに即追記、閾値なし**）。
ゴールは「鳳汰さんを呼ばずに鳳汰さんレベルの成果物が出せる状態」。
