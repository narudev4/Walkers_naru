## 1. タイトル

**形式**: `【個人でも作れる】〇〇開発方法 完全ガイド｜AIを用いた開発方法まで解説`

- 「作り方」ではなく **「開発方法」** を使う（記事内の検索KWは "作り方" でOK、タイトルは "開発方法"）。
- 冠詞 **「【個人でも作れる】」** を基本付与。判定: 個人事業主・小規模が自己構築するユースが成立するアプリは◯（例: 予約システム）。BtoB大規模専用で個人構築が非現実的なら△。
- 「AI」位置まで **32字以内**（例: `【個人でも作れる】社内システム開発方法 完全ガイド｜AIを用いた...` は併記で36字超 → 要調整）。
- 記事全体は「**従来型Nステップ + AI開発を後段で紹介**」。AI版に丸ごと書き換える記事ではない。

> **略語・英字テーマは「〇〇とは？」で読み方＋正式名称を提示**（鳳汰FB 2026-06-04）。例: SaaS → 「SaaS（サース）とは『Software as a Service』の略で…読み方は『サース』、『サービスとしてのソフトウェア』を意味します」。CRM・SFA・CMS・EC・LP・MVP 等も同様に読み方／正式名称／意味を冒頭定義に入れる。

## 2. 章立て（見本記事準拠・出現順）

1. 〇〇とは？
2. 【重要】**9割**のケースでは「AI・ノーコード開発」を利用すべし ← 数字は必ず **9割**（旧8割からの確定値）
3. 〇〇に実装する機能一覧
4. 〇〇開発の**手順Nステップ**（見出しは「流れ」ではなく必ず **「手順」**）
5. 〇〇を作る上での注意点
6. 〇〇の作り方N選
7. 〇〇を開発会社に依頼した際にかかる費用・期間
8. 〇〇の開発費用を安く抑えるN個の方法
9. 〇〇開発会社を選ぶ際に重視すべきNポイント

> ⚠️ **既定構成＝見本マッチング(7240)に揃える**（2026-06-01 naru 確定）。すなわち: **〇〇とは？ → 機能一覧 → 手順10ステップ → 注意点2つ → 作り方2選（手順の後）→ 費用・期間 → 安く抑える4つ → 選び方5つ**。**見本には「9割のケース」H2は無い**（上のリストの2は予約系バリアントの要素なので、見本に揃えるなら入れない）。
> 予約システム(7307)は別バリアント（9割先頭・作り方4選・とは/注意点なし・9ステップ）。**原則は見本(7240)構成**で、予約型にするのは naru が明示確認したときだけ。Phase 4 のテンプレ複製は複製元の章構成を継承するので、**7240 を複製すれば自動的に見本構成**になる。

> 新規執筆では上記を 0→1 で作る（リライトのように「流れ→手順」置換や「8割→9割」修正は発生せず、**最初から「手順」「9割」で書く**）。
>
> **費用系（6〜9）の含有基準**: 対象アプリの「開発費用系」記事が**完成済みなら**、費用2章（7=依頼費用・期間／8=安く抑える方法）は**見出し＋短い要約に留め、開発費用記事へ内部リンク**で送る。**9=開発会社を選ぶポイントは残す**（手順②の5チェックと連動するため）。開発費用記事が無いアプリは費用系も本文を書く。迷ったら naru 確認。

## 3. 手順セクション（最重要・最も差がつく箇所）

### ステップ数

- **10ステップ版（デフォルト・見本=matchingapp）**: ①企画立案 ②開発会社の選定 ③要件定義 ④外部設計 ⑤内部設計 ⑥開発 ⑦テスト ⑧リリース準備 ⑨リリース ⑩保守・運用
- **9ステップ版（社内システム・予約系）**: ⑧をリリース（準備＋提供開始を統合）にして⑨保守・運用。リリース準備を独立させない。

### 章タイトル文型（H3ブロック）

`【手順①】企画立案：どのような〇〇を作りたいのか明確にする`

- 各手順 H3 の配下に**3段落**程度の解説本文。

### AIヒアリングライン + プロンプトブロック + 動画埋め込み（手順①③④⑤の4本）

> ✅ **2026-06-01 公開実物で確定**（見本マッチング7240・予約7307）。各該当手順の本文末は次の3点セット（②は無し）:

1. **AIヒアリングライン（1行）**: `※下記のようにAIにヒアリングしてもらうのがおすすめです。`
   - **①③④⑤すべて「AIにヒアリング」**で統一（公開版で確定。ローカル下書きにあった「④⑤＝Claude Code」は誤りで、本番では使われていない）。
2. **プロンプトブロック**: `プロンプト` ラベル＋その手順用の実例プロンプト1つ（例: 手順①「予約システムを作りたいです。どのような予約システム（業種・規模・利用シーン）にすべきか、誰がどんなシーンで使うのか、提供したい機能は何か、一つずつヒアリング形式で整理してください。」）。テーマに合わせて書く。
3. **実演動画プレースホルダ**: `[YouTube動画埋め込み: 手順① 企画立案ヒアリング動画 ※録画後にURL差し込み]`（見本では「AIによるヒアリングの実演」枠。naru が後で録画→限定公開→URL差込）。

### オレンジリスト（2か所）

WPの色付きリストブロックで強調する2か所。**レビュー用mdでの表記**: `【オレンジリスト：用途】` の見出し行＋直下にリスト、で表す（Phase 4 で WP の色付きリストブロックに対応させる）。2か所:

1. **手順①の3問**: 「誰が」「どんなシーンで使うのか」「提供したい機能は何か」（企画立案で言語化する3問）
2. **手順②の5チェック**（開発会社選定の判断軸）:
   1. 過去の実績に信頼性があるか
   2. ブログ／SNS／YouTubeで有用な情報を発信しているか
   3. 問い合わせへの対応が丁寧か
   4. サポート体制が充実しているか
   5. 自社の事業や課題に基づいた提案をしてくれるか

### 太字

各手順の解説内に**1か所だけ太字**（その手順で最も重要な一文）。10ステップ版＝10個、9ステップ版＝9個。

## 4. テーマ別カスタマイズ（アプリ特性に置換する箇所）

`batch-complete` の表が雛形。最低限、以下をアプリ特性に合わせて差し替える:

| 箇所 | 内容 |
|------|------|
| 手順③ 機能要件 | そのアプリのコア機能（例 SNS=投稿/フォロー/タイムライン/通知/画像配信） |
| 手順④ 太字 | 「迷わず〇〇できるか」（例 SNS=迷わず投稿・閲覧できるか） |
| 手順⑤ スケール対象 | 負荷の焦点（例 SNS=ユーザー数増加・フィード配信） |
| 手順⑦ テスト主要フロー | 重点検証フロー（例 SNS=投稿/閲覧/通知） |

その他、各手順本文の「予約システム」等の主題語を対象アプリ名へ置換。コピペ判定回避のため言い回しも微調整（同一文言を避ける）。

## 5. 文体・表記（seo-article の共通規約のみ適用）

- 番号付き見出しには **【】**（`【手順①】`）。
- 出典は **`»出典：[サイト名](URL)`**（`（出典: ）`形式は禁止）。
- AIっぽい表現の禁止: 本文中の `---`（水平線）・`——`（emダッシュ）・強調装飾の `"..."` は使わない。
- ※ KW密度・note系の「リスト記号禁止」は**持ち込まない**（本記事は番号リスト・オレンジリストを使うため）。

## 6. 公開ステータス（厳守）

- WordPress は **status = draft 維持。publish は絶対にしない**。
- フロー: naru レビュー → 鳳汰へ Chat 共有（数本まとめて）→ FB → 動画録画 → 公開（公開は人手・スキル外）。
