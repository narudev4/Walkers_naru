# 提案書 + モックアップ チーム作成

トリガー: 「提案書とモック」「提案とデモ」「提案書とモックアップ作って」「propose-and-demo」

## 入力
$ARGUMENTS

## 概要

提案書（Google Docs）とモックアップ（Next.js + Vercel）を **1回のヒアリングで同時に作成** するチームスキル。
依存関係を正しく扱い、最終的に相互参照させる。

## 全体フロー

```
① 統合ヒアリング → ② 統合骨子策定（承認必須）
    → ③-A 提案書作成（サブエージェント）  ─┐
    → ③-B モックアップ作成（サブエージェント）─┤ 並列実行
    → ④ 統合（相互リンク・スクリーンショット埋め込み）
    → ⑤ 最終レビュー
```

> **絶対ルール**: ② の統合骨子がユーザーに承認されるまで ③ に進んではならない。

---

## Step 1: 統合ヒアリング

提案書・モックアップ両方に必要な情報を **1回で** 収集する。
聞き返しは最小限にまとめ、足りない情報は自動収集で補う。

### ヒアリング項目（統合版）

**基本情報（提案書 + モック共通）**
1. **クライアント名・担当者名**
2. **案件名 / サービス名（仮称）**
3. **提案の背景**: MTGで聞いた課題・困りごと
4. **ターゲットユーザー**: 誰が使うか（BtoB / BtoC / 社内）
5. **必要な主要機能**: クライアントが求めている機能
6. **競合・参考サービス**: 「〇〇みたいな」

**提案書固有**
7. **予算感・スケジュール感**
8. **MTG情報・Geminiメモの有無**

**モックアップ固有**
9. **必要な画面**: LP / ダッシュボード / 一覧 / 詳細 / 管理画面 等
10. **デザインの好み**: 参考サイト・テイスト・雰囲気（任意）
11. **対象ユーザー別の画面**: エンドユーザー向け / 管理者向け / 両方

### 自動収集（ヒアリングと並行）

- **memories/facts.md** からクライアント情報・商談状況を参照
- **03_projects/{クライアント名}/**: 既存の提案書・議事録・要件メモを検索
- `gcal_list_events(q="クライアント名")` からMTG情報を取得
- **Geminiメモ** がある場合は Google Drive から取得
- **Notion** に案件情報があれば取得

---

## Step 2: 統合骨子策定【承認必須】

提案書の骨子とモックアップの画面構成を **1つの統合ドキュメント** として提示する。

### 提示フォーマット

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
■ 統合骨子: {クライアント名} - {案件名}
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

【A. 提案書の構成】

■ クライアント: {企業名} {担当者名} 様
■ 支援名称（仮称）: {名前}
■ 概要: {一行で}
■ ターゲット: {誰が使うか}
■ 主要課題:
  - {課題1}
  - {課題2}
■ 求められている機能:
  - {機能1}
  - {機能2}
■ 含めるセクション: 1〜10のうち該当するもの
■ 予算感: {あれば}
■ スケジュール感: {あれば}

【B. モックアップの構成】

■ 画面一覧:
  1. テストハブ (/) — 全画面へのリンク集
  2. {画面1} (/{path1}) — {説明}
  3. {画面2} (/{path2}) — {説明}
  ...

■ デザイン方向性:
  - 美的方向性: {ラグジュアリー / ブルータリスト / ミニマル 等}
  - コンセプト: {一言}
  - カラー: {支配色 + アクセント}
  - フォント: {ディスプレイ用 + ボディ用}
  - テーマ: {ライト / ダーク}

【C. 連携ポイント】
  - 提案書の機能一覧 ↔ モックの画面が対応していること
  - モックのデプロイURL → 提案書に「画面イメージ」として記載
  - 提案書のGoogle Docs URL → モックのテストハブにリンク
```

> **この統合骨子が承認されてから Step 3 に進む。**

## Step 3: 並列実行（サブエージェント）

承認された統合骨子をもとに、**2つのサブエージェントを同時起動** する。

### 3-A: 提案書サブエージェント

Agentツールで起動する。プロンプトに以下を含める:

- 統合骨子の【A. 提案書の構成】セクション全文
- `/create-proposal` の Step 3〜4 の手順（テンプレートコピー → replaceAllText → 品質チェック）
- テンプレートID: `1SS_Xw7gGHPOpLj8x8lgUJr4gmJRE8OZUqSA7_4Fr5DA`
- 提案書フォルダID: `1k5pmN_SCWyWhjG2lPM_PT5vdtPYh9BUS`
- NGリスト全項目（create-proposal.md の NG-1〜NG-15）
- 品質チェックリスト
- **出力**: Google DocsのURLとドキュメントID

### 3-B: モックアップサブエージェント

Agentツールで起動する。プロンプトに以下を含める:

- 統合骨子の【B. モックアップの構成】セクション全文
- 統合骨子の【A. 提案書の構成】から機能一覧（画面と機能の整合性確保のため）
- `/create-mockup` の Step 3〜6 の手順（Next.js初期化 → 実装 → デプロイ）
- frontend-designガイドライン全文
- テストハブ必須ルール
- **出力**: VercelデプロイURLとプロジェクトパス

### 並列実行コード

```
Agent 1: "提案書作成サブエージェント"
  - prompt: 統合骨子A + create-proposal手順 + NGリスト
  - run_in_background: true

Agent 2: "モックアップ作成サブエージェント"
  - prompt: 統合骨子B + 機能一覧 + create-mockup手順
  - run_in_background: true
```

> **両方の完了を待ってから Step 4 に進む。**

---

## Step 4: 統合（相互リンク・参照）

両サブエージェントの成果物を相互に連携させる。

### 4-A: 提案書にモックアップ情報を追加

- 提案書の「提案ソリューション」セクションにモックアップURLを追記:
  - `google_docs_batch_update` で以下を挿入:
  - 「画面イメージ（モックアップ）: {Vercel URL}」
- 提案書のローカルバックアップにもURL追記

### 4-B: モックアップのテストハブに提案書リンクを追加

- テストハブ（`/`）のフッターまたはヘッダーに:
  - 「提案書: {Google Docs URL}」を追加
- 再デプロイ: `npx vercel --yes --prod`

### 4-C: ローカルバックアップの整理

- `03_projects/{クライアント名}/` に以下を保存:
  - `proposal/YYYY-MM-DD_{案件名}.md` — 提案書バックアップ
  - `mockup/README.md` — モックアップ情報（URL、画面一覧、技術スタック）

## Step 6: 連動修正フェーズ（フィードバックループ）

初回作成後、ユーザーからフィードバックを受けたら **影響範囲を自動判定** して連動修正する。

### 影響判定ロジック

フィードバックを受けたら、まず以下を判定する:

| フィードバック内容 | 影響先 | アクション |
|------------------|--------|-----------|
| 「この画面のレイアウト変えて」 | モックのみ | モック修正のみ |
| 「この機能削除して」 | **両方** | 提案書の機能一覧から削除 + モックの該当画面削除 |
| 「機能追加して」 | **両方** | 提案書に機能追加 + モックに画面追加 |
| 「見積もり修正して」 | 提案書のみ | 提案書修正のみ |
| 「色変えて」「デザイン変えて」 | モックのみ | モック修正のみ |
| 「スケジュール変えて」 | 提案書のみ | 提案書修正のみ |
| 「この画面の機能名変えて」 | **両方** | 提案書の機能名 + モックの画面タイトル・説明を同時修正 |
| 「ターゲット変更」 | **両方** | 提案書のターゲット記述 + モックのUI方針を修正 |

### 連動修正の実行方法

**片方だけ影響する場合**: 該当する成果物のみ修正

**両方に影響する場合**: サブエージェント2つを **並列起動** して同時修正

```
ユーザーFB: 「在庫管理機能を削除して、代わりに発注管理を追加」

→ 影響判定: 両方に影響（機能の追加・削除）

→ Agent 1（提案書修正）:
  - 機能一覧テーブルから在庫管理を削除
  - 発注管理を追加
  - スケジュール・見積もりへの影響があれば調整

→ Agent 2（モック修正）:
  - /inventory ページを削除
  - /orders ページを新規作成
  - テストハブのリンクを更新
  - ナビゲーションを更新

→ 両方完了後: 再デプロイ + 整合性確認
```

### 修正後の整合性チェック

連動修正後、以下を必ず確認する:
- [ ] 提案書の機能一覧とモックの画面が1:1で対応しているか
- [ ] 提案書に記載のモックアップURLが最新か
- [ ] モックのテストハブに全画面のリンクがあるか
- [ ] 削除した機能が両方から完全に消えているか

---

## ルール（厳守）

1. **統合骨子の承認なしに実装を開始しない**
2. **ヒアリングは1回にまとめる**（提案書用・モック用で2回聞かない）
3. **サブエージェントは並列実行する**（直列にしない）
4. **提案書の全ルール**（create-proposal.md）を遵守する（NG-1〜NG-15、品質チェックリスト）
5. **モックアップの全ルール**（create-mockup.md）を遵守する（frontend-design、AIスロップ禁止）
6. **統合ステップを省略しない**（相互リンクが提案の説得力を高める）
7. **機能一覧と画面の整合性**を必ず確認する（提案書に書いた機能がモックにない、はNG）
8. **フィードバック時は影響範囲を自動判定する**（「モックだけ直せばいい」か「両方直す必要があるか」を判断）
9. **両方影響するFBは並列サブエージェントで同時修正する**（片方ずつ直列にしない）
