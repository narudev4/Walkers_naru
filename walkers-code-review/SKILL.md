# Walkers コードレビュー

推測や一括判定ではなく、観点を1つずつ完了させる。各判定に検索・読解・実行結果などの証拠を残し、未確認を「問題なし」にしない。

## 絶対ルール

- 最初にリポジトリ内の `AGENTS.md`、`CLAUDE.md`、README、開発・テスト手順を確認する。
- レビュー依頼は読み取り専用として扱う。ユーザーが修正も依頼している場合だけコードを変更する。
- 既存の未コミット変更をユーザーの作業として保護し、レビュー対象との差を分ける。
- リポジトリへレポートを勝手に作らない。巡回状態はOSの一時ディレクトリへ置き、成果物ファイルは明示要求がある場合だけ作る。
- 変更行だけで結論を出さない。呼び出し元、呼び出し先、データフロー、設定、テスト、スキーマ、デプロイへの波及を追う。
- 検索ヒット数だけで `pass` にしない。該当コードを読み、成立条件と防御を確認する。
- 観点をまとめて完了扱いにしない。状態ファイルへ1観点ずつ記録する。
- 実行できない確認は `blocked` とし、理由と残存リスクを記録する。
- 「安全」「脆弱性なし」と断定しない。「確認した範囲では該当所見なし」と表現する。
- Critical / High は再読・反証確認してから確定する。フレームワークの既定防御や到達不能性を確認する。

## 1. モードと対象を確定する

ユーザーの指示と実データから次を決める。発見できる情報を聞き返さない。

- `pr`: PR、コミット、未コミット差分を起点に、影響範囲を含めてレビューする。旧 `quick` 指定もこのモードとして扱う。
- `full`: リポジトリ全体のベースラインレビュー。
- `security`: セキュリティ中心。ただしアーキテクチャ、テスト、運用の関連観点は省略しない。
- `release`: `full` に加え、実テスト、ビルド、マイグレーション、設定、ロールバック、実ワークフローを確認する。

次を記録する。

- 対象の基準点と終点: base/head、PR番号、コミット、ディレクトリなど
- 技術スタックと実行環境
- プロファイル: web / api / auth / multi-tenant / payments / pii / database / files / cloud / mobile / desktop / ai から該当するもの
- 重要資産、信頼境界、外部入力、権限境界、不可逆処理
- 要件・設計・画面一覧・API仕様・受入条件の所在

対象が曖昧でも、安全に推定できる場合は仮定を明記して進める。基準点の選択で結果が大きく変わり、ローカル情報から確定できない場合だけ質問する。

## 2. 状態ファイルを初期化する

必ず [references/checkpoints.md](references/checkpoints.md) を最初から最後まで読む。次にOSの一時ディレクトリを作り、同梱スクリプトで巡回状態を初期化する。

```bash
node <skill-dir>/scripts/review-state.mjs init \
  --checkpoints <skill-dir>/references/checkpoints.md \
  --state <temp-dir>/review-state.json \
  --mode pr \
  --scope "対象の説明" \
  --base "基準点" \
  --head "終点" \
  --profiles "web,api"
```

`<skill-dir>` はこの `SKILL.md` の親ディレクトリ。`<temp-dir>` はリポジトリ外の一時ディレクトリ。

## 3. 発見パスを完了する

D群を順番に処理し、次を把握してから所見を確定する。

1. 対象ファイルと変更目的
2. アーキテクチャ、境界、主要データフロー
3. 変更の呼び出し元・呼び出し先・設定・スキーマ・テストへの波及
4. 仕様、受入条件、既知の障害・過去所見
5. 実行可能な検証コマンドと実行不能な制約

## 4. 観点を1つずつ巡回する

次の未処理観点を取得する。

```bash
node <skill-dir>/scripts/review-state.mjs next --state <temp-dir>/review-state.json
```

返されたIDのセクションを `references/checkpoints.md` からその場で読み直す。以前読んだ内容や会話要約だけに頼らない。コンテキスト圧縮・中断・再開が発生した場合は `summary` と `next` を実行し、現在の観点と未完了件数を復元してから続ける。

各観点で必ず以下を行う。

1. `Applies` を判定する。
2. 参照ファイルの `確認` を実行する。
3. ヒット箇所を読み、入力から出力・副作用まで追う。
4. 既存防御、テスト、設定、型、制約による反証を探す。
5. 次のいずれかを1件ずつ記録する。

- `pass`: 確認方法、対象、具体的証拠を説明できる。
- `finding`: 再現条件または成立経路、影響、場所、修正方向を説明できる。
- `na`: 対象外である具体的理由を説明できる。
- `blocked`: 権限・環境・資料不足などで確認できず、残存リスクがある。

```bash
node <skill-dir>/scripts/review-state.mjs record \
  --state <temp-dir>/review-state.json \
  --id S4 \
  --status finding \
  --severity High \
  --locations "src/api/orders.ts:88" \
  --evidence "注文IDをURLから受け、所有者条件なしで更新している。認証ミドルウェアは本人確認のみ。" \
  --notes "別ユーザーの注文IDで更新可能"
```

`pass` では、検索語だけでなく読んだ経路・防御・テストのいずれかを証拠に含める。高リスク観点の `pass` は、コード読解とテスト／設定確認など2種類以上の証拠で裏付ける。

## 5. 実行検証する

対象とリスクに応じ、リポジトリが定めるコマンドを優先して次を実行する。

- フォーマット、lint、型検査、ビルド
- 単体、統合、E2E、セキュリティ回帰テスト
- 依存・シークレット・SAST等の既存スキャナ
- マイグレーション、設定、デプロイ、ロールバックの検証
- 実ユーザーフローの確認

既存ツールがない場合に、勝手に大規模な依存導入や外部サービス送信をしない。実行不能な検証は `blocked` にする。ツール結果を盲信せず、所見はコードへ戻って確定する。

## 6. 反証パスを行う

巡回後に次を再確認する。

- Critical / High の全所見: 到達可能性、必要権限、フレームワーク防御、実害を再確認する。
- 高リスク領域の `pass`: 別の確認方法で少なくとも1回反証を試みる。
- 変更境界: 変更外の呼び出し元、共有型、設定、スキーマ、キャッシュ、ジョブへの影響を再確認する。
- 「テストが通る」と「要件を満たす」を区別する。

誤検知は削除して件数を合わせる。判断が割れるものは severity を盛らず `blocked` または「要確認」にする。

## 7. 完了条件を機械検証する

```bash
node <skill-dir>/scripts/review-state.mjs validate --state <temp-dir>/review-state.json
node <skill-dir>/scripts/review-state.mjs export \
  --state <temp-dir>/review-state.json \
  --output <temp-dir>/coverage.md
```

`validate` が失敗している間はレビュー未完了。`pending`、証拠不足、必要情報欠落を解消する。高リスク領域に `blocked` が残る場合、クリーンなリリース判定を出さない。

## 8. 報告する

必ず [references/report-template.md](references/report-template.md) を読み、次の順で報告する。

1. 所見を重大度順に提示する。所見がなければ、その旨と残存リスクを先頭で述べる。
2. 各所見に `ファイル:行`、成立経路、影響、最小修正、必要テストを含める。
3. スコープ、基準点、実行したコマンドと結果を示す。
4. Coverage を `pass / finding / na / blocked` で示す。
5. リリース判定と、その判定を妨げる未確認事項を示す。

レビューで問題がなければ無理に指摘を作らない。スタイル上の好みは、既存規約違反や保守上の具体的影響がない限り所見にしない。

観点の追加・削除、基準の改訂、OWASP準拠範囲の確認を行う場合は [references/standards.md](references/standards.md) を読む。通常のレビューでは読み込み不要。

## 重大度

- `Critical`: 低い前提で直接悪用でき、重大な情報漏えい・権限奪取・金銭被害・不可逆な破壊につながる。
- `High`: 現実的な条件で重大な機密性・完全性・可用性・仕様逸脱が生じ、リリース前対応が必要。
- `Medium`: 限定条件での不具合、回復可能なデータ不整合、重要な保守・運用リスク。
- `Low`: 影響が小さいが、具体的な品質・安全性改善につながる。

Critical / High が検証済みで残る場合はリリース不可。Medium は影響・回避策・期限・責任者を明示して判断する。Low だけで過度にリリースを止めない。
