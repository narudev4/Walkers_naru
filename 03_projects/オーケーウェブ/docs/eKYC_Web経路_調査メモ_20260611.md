## 2. 訂正（断定が早かった点）

- ❌「TRUSTDOCK側でWEBカメラ設定が退行した」→ **誤り**。ホスト型ページの裏で `web_camera/submissions` が 201 を返しており、WEBカメラ提出は環境的に生きている
- ❌「result_configuration=false ⇒ 壊れている」→ **未確定**。6/8 に動いた時のレスポンス値を観測しておらず、false が正常値の可能性もある（別APIの `submission_modes` が現行の提出方法決定に使われている形跡）
- TRUSTDOCK への問い合わせメールは**保留**（環境異常の証拠が無いため）

## 6. 結論（2026-06-11 解決）

**原因: 検証方法の問題。実装は正しかった。**

TRUSTDOCK Browser SDK の撮影フローは、ブラウザの transient activation
（**人間の実クリック**）を前提としている。Playwright / dispatchEvent による合成クリック
（isTrusted=false）では、モーダルは開いても撮影UIの初期化が進まず「通信中…」のまま止まる。

### 証拠（対照実験）

| 操作者 | aikata (localhost:8083) | auth-test-six |
|---|---|---|
| Claude（合成クリック） | 通信中…で停止 | 通信中…で停止（**同じ挙動**） |
| naru（実クリック） | **撮影フロー起動 ✅** | **書類選択→撮影 ✅** |

- 実装差ではない（同一ブラウザ・同一plan・同一helper・同一iframe URL形式・初期化引数同型）
- `result_configuration` の `id_document_shooting: false` は撮影可否のブロッカーではなかった
  （false が返っても実クリック経由なら撮影フローが動く）
- TRUSTDOCK 環境は正常（問い合わせ不要）

### 教訓

- **eKYC/カメラ系のWebテストは自動化クリックでは検証できない**。最終確認は必ず人間の手で行う
- 「動かない」を観測したら、まず**動いた実績と同条件か**（ブラウザ・操作主体・ジェスチャ）を揃える

## 7. 新規課題（撮影フロー確認で判明）

**SDK内の書類選択リストが契約全書類（6種: パスポート/免許証/マイナ/在留/経歴証明/特別永住者）を表示する。**
アプリ側で確定4種に絞っても、SDK内の選択画面では絞られない（二重選択かつ余分な書類が出る）。

- iOS Native SDK には `excludeIdDocumentTypes` があり絞り込み可能（swiftinterface で確認済み）
- Browser SDK 側に同等の絞り込みがあるか要調査（APIドキュメント or TRUSTDOCK に確認）
- 仕様書 A-1（書類割り）の補足課題としてスプシに登録
