### 2-3. 実装の基盤（🟡 当方判断）

`/store` 配下は**共通の基盤層**の上に載っている。画面ごとに色や余白を書いていない。

- `src/app/store/_tokens.ts` … 配色・書体・寸法のトークン定義と、未確定項目の一覧（`OPEN_QUESTIONS`）。
- `src/app/store/_components/` … 16個の共通部品（`StoreShell` / `StoreHeader` / `StoreFooter` / `StoreButton` / `Price` / `StockBadge` / `ProductCard` / `ProductGrid` / `ProductSlider` / `NewsList` / `QuantityStepper` 他）。
- `src/app/globals.css` … 配色トークンの実体。Shopify の配色スキームと 1 対 1 で対応させている（第3章）。

この構造にした理由は 2 つある。第一に、**トンマナの切り替えが色値の差し替えだけで済む**（一般のお客様向けと業者様向けで同じ部品を使い、`tonmana` の指定だけを変えている）。第二に、**Shopify 移植時に「部品1つ = CSS 1ブロック」で写せる**。

加えて、制約が**部品の設計に埋め込まれている**。たとえば `Price` コンポーネントは掛率・OFF率・上代を受け取る引数を持っていない。よって、掛率を画面に出す実装は「うっかり」ではできない（意図的に迂回しない限り）。

## 3. カラートークン設計と Shopify 移植の仕組み

### 3-1. なぜ Dawn の変数名に揃えたのか

Shopify テーマ（実体は **Rise 15.4.1**。Dawn 系の同一アーキテクチャ。`config/settings_schema.json` L3-9 で実測）の管理画面には「配色」の設定欄がある。この欄は **7 つの入力**しか持たない。

`background` / `background_gradient` / `text` / `button` / `button_label` / `secondary_button_label` / `shadow`（`config/settings_schema.json` L40-101 で実測）。

この 7 つから、テーマは実行時に 14 個の CSS 変数を自動生成する（生成箇所は `assets/base.css` ではなく `layout/theme.liquid` L64-102。ここは調査で判明した点で、`base.css` の `:root` には色変数が一切ない）。

**そこで、Vercel 側のカラートークン名をこの 7 つと同名・同じ導出規則に揃えた。**

得られるものは次のとおりである。

1. **Shopify 側の作業が「管理画面に色を入れるだけ」になる。** 一般のお客様向けの色は、配色1〜5 の 7 欄に値を入れるだけで反映される。Liquid のコードを触らずに済む。
2. **テンプレート・セクションの編集が不要になる。** 配色スキームの「番号」に役割を固定したので（下記 3-2）、色を変えたいときはスキームの値を差し替えるだけで、どのセクションがどのスキームを使うかは変えなくてよい。
3. **Vercel 側とのズレが検出しやすい。** 変数名が同じなので、対応表（3-4）が 1 対 1 の表になる。

### 3-2. 配色スキームの役割固定（🟡 当方判断）

| スキーム | 役割 | 一般のお客様向け（B2C） | 業者様向け（B2B） |
|---|---|---|---|
| scheme-1 | 基本・ページ地 | 白地 `#FFFFFF` ／ 文字 `#0A0A0A` ／ ボタン `#245BFF` | ページ地 `#F5F6F8` ／ 文字 `#0E1B3A` ／ ボタン `#0E1B3A` |
| scheme-2 | カード・パネル面 | 白地 | 白面 `#FFFFFF` |
| scheme-3 | 反転面 | 黒地 `#0A0A0A` ／ 文字 白 | ネイビー地 `#0E1B3A` ／ 文字 白 |
| scheme-4 | アクセント面 | 青地 `#245BFF` ／ 文字 白 | ネイビー地（scheme-3 と同値。業者様向けに固有アクセント色が無いため） |
| scheme-5 | 予備 | 🔴 未確定（scheme-2 と同値の暫定） | 🔴 未確定（同左） |

補足（実測に基づく注意点）。

- 現テーマの配色は**旧色のまま**である（全スキームのボタンが `#4A90E2`、scheme-1 の文字が `#222222`、scheme-5 が `#334FB4`）。確定トンマナに差し替える作業が必要である。
- **scheme-4 が「フッター」と「セール表示のバッジ」の 2 役を兼用しており衝突している**（`sections/footer-group.json` と `sale_badge_color_scheme` の両方が scheme-4 を指している）。フッターを scheme-3 に移す。
- scheme-5 は現在**どこからも参照されていない**（`settings_data.json` に定義だけがある）。
- 角丸は現テーマが 16px / 40px を指定しているが、確定トンマナの参照実装（`/concept-b`）には**角丸が 1 箇所もない**。0 に変更する。

### 3-3. 2 つのトンマナを 1 テーマに載せる方法（🟡 当方判断・要検討）

**ここが移植の最大の設計論点である。**

Shopify の配色スキームは**テーマに 1 セットしかない**。一般のお客様向け（青・白・黒）と業者様向け（白・ネイビー）で scheme-1 の値が違うため、「管理画面に色を入れるだけ」では両系統を同時に表現できない。

対処方針は次のとおりである。

- 管理画面の 7 欄には**一般のお客様向けの色だけ**を入れる。
- `layout/theme.liquid` の `<body>` に、業者様向けのときだけ目印のクラスを 1 つ足す。
- 新規 CSS（`assets/store-tokens.css`）で、その目印が付いているときだけ配色スキームの値を業者様向けに上書きする。

Vercel 側は既にこの構造で実装済みである（`[data-tonmana="b2c"]` / `[data-tonmana="b2b"]` で同じ scheme-1〜5 に別の値を割り当てている）。よって上書きする値は `src/app/globals.css` からそのまま写せる。

🔴 **未確定**: 業者様向けかどうかの判定を何で行うか。既存実装（`snippets/b2b-nav-switcher.liquid`）は顧客のメタフィールドで判定しているので同じ方式が自然だが、この前提で進めてよいかを naru に確認したい。

### 3-5. 移植時に効いてくる差異（実測・注意）

| 差異 | 内容 | 対処 |
|---|---|---|
| **rem の基準が違う** | Shopify は `html { font-size: 62.5% }` により **1rem = 10px**。Next/Tailwind は 1rem = 16px。 | rem の数値を直接コピーしない。**必ず px に換算してから ÷10 する**（例: 24px → 2.4rem）。これを守らないと全体が 62.5% に縮む。 |
| **1px の罫線が設定では作れない** | グリッドの隙間設定は最小 4px・4px 刻み。参照実装の罫線 1 本は「隙間 1px + 親に罫線色」で作っている（13 箇所）。 | CSS で隙間の変数を 1px に上書きし、罫線色を敷く専用クラスを 1 つ作って共用する。 |
| **商品カードの画像が切り取られる** | テーマ既定が `object-fit: cover`。受領した実物シャトル写真は縦横比がバラバラなので切れる。 | 商品カードに限定して `contain` に上書きする。ただし **`ochiai-shuttle-1.jpg`（灰色背景）と `-2.jpg`（オフホワイト）は例外で `cover` が正しい**（Vercel 側は画像ごとに切替済み）。 |
| **ブレークポイントが違う** | Tailwind は 640/768/1024、テーマは 750/990。 | 768 → 750、1024 → 990 に寄せる。列数の切替点が 1 段ずれる箇所は目視確認が必要。 |

なお、**価格を赤字にしない**という 7/22 制約は既定で満たされる。テーマの価格 CSS は文字色の変数しか使っておらず、赤のハードコードが無い（`assets/component-price.css` L5, L61-89 で実測）。

### 6-3. Tailwind のクラスを Liquid に落とす具体手順

`/store` 配下の実測: 約 300 種のユーティリティクラス、3,641 行、状態を持つ部品は 1 個だけ。

1. **まず配色トークンを移す。** `src/app/globals.css` の末尾ブロックが Shopify の変数名と 1 対 1 の対応表になっている（コメント付き）。Shopify 側では独自変数を作らず、テーマの `--color-*` をそのまま使う。不透明度付き（例: 文字色 70%）は、テーマの変数が「R, G, B」の三つ組で出るのでそのまま `rgba(var(--color-foreground), 0.7)` と書ける。
2. **部品単位で 1 クラスに畳む。** ユーティリティを 1 対 1 で CSS 化しない（クラス数が爆発する）。「部品 1 つ = CSS 1 ブロック」にする。
   - 例: 商品カードの `flex flex-col bg-scheme-background p-6` → `.ochiai-card { display:flex; flex-direction:column; background:rgb(var(--color-background)); padding:2.4rem }`
3. **置き場所は 2 層にする。**
   - 複数セクションで共有する部品（カード・価格・在庫バッジ・ボタン・パネル・表・パンくず）→ 新規 `assets/store-components.css` に集約し、`layout/theme.liquid` で標準 CSS の直後に 1 回読む。
   - 1 セクション専用の CSS → 既存 `hp-hero.liquid` の流儀で、各 `.liquid` の `{% stylesheet %}` に同梱する。
4. **数値は必ず px を経由して rem にする（÷10）。** 直接コピーは禁止（3-5 参照）。
5. **ブレークポイントを読み替える**（768 → 750、1024 → 990）。
6. **コンテナ幅は標準の `.page-width` に置換する**（設定値 1200 と一致することを実測済み）。
7. **画像は `image_url` + `image_tag` に置換する。** 縦横比の枠はテーマ標準の比率指定で作る。商品カードの `contain` 上書きは必須（3-5 参照）。
