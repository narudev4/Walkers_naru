## ■ MF の仕様、公式ドキュメントで確定しました

[開発者サイトのチュートリアル](https://developers.biz.moneyforward.com/docs/tutorials/getting-started-api-call-manually/step-2/) にレスポンス例が載っていました。

| 項目 | 公式の記載 |
|---|---|
| アクセストークン | **1 時間**（`expires_in: 3600`）。手元の実測値と一致 |
| **リフレッシュトークン** | **540 日** |
| リフレッシュ時のレスポンス | **新しい `refresh_token` が含まれる** |

```json
{
  "access_token": "xxxxxxxxxxxxxxxxxx",
  "refresh_token": "yyyyyyyyyyyyyyyy",   ← 新しいものが返る
  "scope": "mfc/admin/tenant.read",
  "token_type": "Bearer",
  "expires_in": 3600
}
```

**リフレッシュのたびに新しい refresh_token が返るので、保存先が無いと 1 回で使い切りになる**という構造は、ご指摘のとおりでした。

なお、**古いリフレッシュトークンが即座に無効になるか**は公式に記載がありませんでした。ただし「返ってきたものを常に保存する」実装にすれば、ローテーションする／しないのどちらでも安全に回ります。

## ■ 実際にリフレッシュを叩いたら、失敗しました

手元の `.mf-tokens.json`（2026-06-19 取得）で 1 回試したところ、こうなりました。

```
HTTP 400 {"error":"invalid_grant",
          "error_description":"[A053305] The refresh token passed to the token endpoint does not exist."}
```

**有効期限 540 日に対して 40 日しか経っていないのに、「そんなトークンは存在しない」**と返ってきました。期限切れではありません。

### 原因は 2 つ考えられて、まだ確定できていません

**説 1：リフレッシュで使用済みになり無効化された**

Vercel 上で 401 → リフレッシュが走り、新しい `refresh_token` が発行されたが、Vercel Function は環境変数を書き換えられないので保存されずに消えた。古い方は MF 側で既に無効。

**説 2：検証アカウントがトライアル終了などで無効になった**

このアカウントは資料上「naru のトライアル口座」と記録されているもので、**トライアル期間が終わっている可能性**があります。その場合、アプリの認可ごと解除されていてもおかしくありません。

**最初は説 1 だと考えたのですが、根拠が「540 日以内なのに消えている」だけで、説 2 を排除できていませんでした。** 現時点では確定できていません。

なお公式には「クラウド請求書 API は追加料金なく利用可能。ただしプランに応じて機能制限があり、法人向け無料プランでは帳票作成のリクエスト上限が 100」とあるので、**無料プランでも API 自体は使えます**。今回のエラーは帳票 API ではなく認可サーバー側の応答なので、プランの機能制限とは別のレイヤーです。

### 切り分けは再認可で付きます

- **再認可（`npm run auth`）が通る** → アカウントは生きている。**説 1**。永続化の実装で解決する
- **再認可が通らない／権限エラー** → **説 2**。アカウント側の問題で、実装では解決しない

**あわせて MF の画面で「現在のプラン」「アプリポータルの連携状態」「請求書の最終作成日」を確認します。** 最終作成日が分かれば、いつから止まっていたかも特定できます。

### どちらであっても、やることは変わりません

- **再認可が必要**（今のトークンでは復活しない）
- **トークンの永続化は必須**（説 1 なら直接の対策、説 2 でも再認可後に同じ事故を防ぐため）
- 本番は落合様のビジネスプランで OAuth し直す（A-10）ので、**この検証アカウントの制約は本番に持ち越しません**

②で承認いただいた「新アカウント作成 → D1 作成 → トークンテーブル込みでスキーマ適用 → トークンを新規発行して secret put → 疎通」の段取りは、**そのまま有効**です。再認可はこの流れに乗せます。

## ■ ③の宿題：顧客アカウントは「新しい顧客アカウント」でした

ご懸念のとおりでした。

```
customerAccountsVersion : NEW_CUSTOMER_ACCOUNTS
customerAccounts        : REQUIRED
loginRequiredAtCheckout : true
```

**F-5 は Liquid だけでは完結せず、customer account UI extension が必要になります。**

しかもテーマ側には classic 用テンプレートが **7 つ揃っています**（`account.json` / `order.json` / `login.json` / `register.json` / `activate_account.json` / `addresses.json` / `reset_password.json` ＋ 対応する `main-*.liquid`）。**これが全部、今の設定では無視されている状態です。**

### 業者様向け（B2B）の発注導線は影響を受けません

`b2b-cart-checkout` は `sections/main-cart-footer.liquid` に乗っていて、**カートページなので顧客アカウントの新旧に関係なく動きます**。Phase 7 の Draft Order 検証が通ったのもこの経路です。

### ただし、F-5 の工数だけの話ではないと思っています

**classic に戻すかどうかを判断したほうがいい**と考えていて、理由が 3 つあります。

1. **新しい顧客アカウントにはパスワードがありません。** ログインは毎回メールに届く 6 桁コードです。**業者様が発注のたびにメールを開いてコードを入力する運用**になります。classic ならパスワードをブラウザに記憶させられます
2. **G-7 の「ID はメールアドレスではなく顧客番号とする方針」と噛み合いません。** どちらの方式でも顧客番号ではログインできませんが、classic ならパスワード運用で近い形にできます
3. **F-10 の「パスワード再設定メール」が新方式には存在しません。** メールテンプレート 4 種のうち 1 つが成立しなくなります

9/1 の試験運用で業者様が実際に使う導線なので、**F-5 の工数よりも使い勝手のほうが判断材料として大きい**と思っています。どちらが良さそうでしょうか。
