# 依頼：落合コーポレーション案件のバックエンドを Vercel から Cloudflare Workers + D1 へ載せ替え

## 背景

落合コーポレーション様のShopify EC。B2B卸の受注から請求書発行までを自動化するバックエンド
現在は Vercel Functions で稼働。**技術検証時にそのまま使っているだけの暫定環境**で、本番は Cloudflare へ移す方針
**9月1日から実際の受注が始まる**。それまでに移行を完了させる必要がある

## このタスクの最重要目的

単なる載せ替えではありません。**現在この仕組みには、本番で二重請求が起こり得る欠陥があります。**

api/webhook.js の processedStore はインメモリの Set で、Vercel Functionのコールドスタートごとにリセットされます。そのため同一インスタンスの連続リクエストしか重複を弾けず、コールドスタートを跨ぐと**同じ注文で請求書が二重に発行され得ます**。

この移行の主目的は、**D1による永続的な冪等性の実装**です。載せ替えはその手段です。

## 改修の基準（重要）

同じファイルが2箇所にありますが、**必ず webhook/vercel-deploy/lib/ 側を基準にしてください。**

lib 側にしかない機能があります: setOrderMetafield（請求書URL・番号を Shopify注文の b2b.mf_invoice_url / b2b.mf_billing_number に書き戻す）
src 側はこの機能が入る前の古い状態です
src 側を基準にすると、この機能が失われます

## 禁止事項

1. **Phase 6 の検証を通すまで、本番の Shopify Webhook の向き先を変更しない**
2. **検証中に実際のマネーフォワード本番アカウントへ請求書を発行しない**（テスト用の設定・ドラフトモードを使う。実発行が避けられない場合は事前に報告して指示を待つ）
3. **Vercel側は Phase 7 の切り替え完了まで停止しない**（ロールバック先として残す）
4. vercel --prod --yes / vercel --yes は実行しない
5. git push --force は使わない
6. 機能追加・リファクタリングはしない。**載せ替えと冪等性の実装のみ**がスコープ
7. 各Phaseの「停止」指示では必ず止まる

### 1-2. スキーマ

schema.sql を作成します。**この内容をそのまま使ってください**（設計は決定済みです）。
sql
-- 処理済み注文。order_gid を PRIMARY KEY にすることで
-- DBレベルで二重請求を弾く（アプリのロジックにミスがあっても防げる）
CREATE TABLE IF NOT EXISTS processed_orders (
  order_gid          TEXT PRIMARY KEY,
  order_number       TEXT,
  customer_id        TEXT,
  customer_name      TEXT,
  payment_terms      TEXT NOT NULL,
  total_price        TEXT,
  currency           TEXT,
  financial_status   TEXT,
  cancelled_at       TEXT,
  fulfilled_at       TEXT,
  mf_invoice_id      TEXT,
  mf_billing_number  TEXT,
  mf_invoice_url     TEXT,
  settled_batch_id   TEXT,
  created_at         TEXT NOT NULL,
  updated_at         TEXT NOT NULL
);

CREATE INDEX IF NOT EXISTS idx_orders_terms_fulfilled
  ON processed_orders(payment_terms, fulfilled_at);
CREATE INDEX IF NOT EXISTS idx_orders_customer
  ON processed_orders(customer_id);
CREATE INDEX IF NOT EXISTS idx_orders_settled
  ON processed_orders(settled_batch_id);

-- 締めバッチの二重実行防止
CREATE TABLE IF NOT EXISTS batch_locks (
  lock_key     TEXT PRIMARY KEY,
  acquired_at  TEXT NOT NULL,
  released_at  TEXT,
  status       TEXT NOT NULL
);

-- 締めバッチの実行記録
CREATE TABLE IF NOT EXISTS settle_batches (
  batch_id      TEXT PRIMARY KEY,
  cycle         TEXT NOT NULL,
  period_start  TEXT NOT NULL,
  period_end    TEXT NOT NULL,
  order_count   INTEGER,
  invoice_count INTEGER,
  status        TEXT NOT NULL,
  error_message TEXT,
  created_at    TEXT NOT NULL
);

適用:
bash
npx wrangler d1 execute ochiai-integrations --local --file=./schema.sql
npx wrangler d1 execute ochiai-integrations --remote --file=./schema.sql

payment_terms に入れる値は、既存コードの支払区分の表現に合わせてください（IMMEDIATE_TERMS の判定で使っている値と揃える）。既存の表現をそのまま使い、新しい命名を発明しないこと。

## Phase 2: processedStore を D1 実装に差し替え

processedStore はインターフェースが抽象化されているとのことなので、**インターフェースは変えずに実装だけ差し替えてください。**

### 冪等性の実装（ここが本丸）

INSERT ... ON CONFLICT DO NOTHING を使い、**書き込めたかどうかで処理続行を判定**します。
js
const res = await env.DB.prepare(
  `INSERT INTO processed_orders
     (order_gid, order_number, customer_id, payment_terms, created_at, updated_at)
   VALUES (?, ?, ?, ?, ?, ?)
   ON CONFLICT(order_gid) DO NOTHING`
).bind(orderGid, orderNumber, customerId, paymentTerms, now, now).run();

if (res.meta.changes === 0) {
  // 既に処理済み。請求書を作らずに正常終了する
  return { skipped: true, reason: 'already_processed' };
}
// ここから先が初回処理
**重要**: 「先に SELECT して、無ければ INSERT」という書き方はしないでください。同時に2つのリクエストが来たときに両方すり抜けます。必ず INSERT の結果で判定してください。

請求書の発行が成功したら、mf_invoice_id / mf_billing_number / mf_invoice_url を UPDATE で書き戻します。

**請求書の発行に失敗した場合の扱いを報告してください。** 行を残すと再試行できず、消すと二重発行の窓が開きます。どちらの設計にするか判断が要るので、実装前に案を出してください。

## Phase 3: 締めバッチの Cron Triggers 化

### 3-1. スケジュール

Cron Triggers は **UTC評価**です。23:59 JST = 14:59 UTC。

「月末」は cron式で素直に書けないため、**毎日実行してコード側で判定**します。
crons = ["59 14 * * *"]

コード側:
今日が **20日** なら → 20日締めサイクルを実行
今日が **その月の最終日** なら → 末締めサイクルを実行
どちらでもなければ何もせず終了

月末判定は「翌日の日付が1日か」で判定してください（月の日数をハードコードしない）。**日付計算はすべてJSTで行い、UTCとの混同に注意してください。**

### 3-2. ロック

batch_locks に INSERT ... ON CONFLICT DO NOTHING でロックを取り、取れなかったら実行しない。lock_key は settle-{cycle}-{YYYY-MM-DD} の形式にしてください。

### 3-3. 返品・キャンセルの除外（未実装分）

工程表 C-8 として残っている項目です。ここで実装します。集約対象から以下を除外してください。

financial_status が REFUNDED / PARTIALLY_REFUNDED
cancelled_at が NULL でない

対象は**フルフィルメント済みの注文のみ**です（既存の仕様どおり）。

## Phase 4: Worker 本体化

エントリポイントを export default { fetch(request, env, ctx), scheduled(event, env, ctx) } の形にする
waitUntil は ctx.waitUntil に置き換え
process.env の13変数は env から受け取る形に変更。**モジュールのトップレベルで env を読まないこと**（Workersでは動きません）。関数の引数で回してください
HMAC署名検証が Node の crypto を使っている場合は **Web Crypto API**（crypto.subtle）に置き換え。nodejs_compat フラグに頼るより移植した方が安全です

wrangler.toml（または wrangler.jsonc）:
toml
name = "ochiai-integrations"
main = "src/index.js"
compatibility_date = "2026-07-01"

[[d1_databases]]
binding = "DB"
database_name = "ochiai-integrations"
database_id = "＜Phase 1 で控えたID＞"

[triggers]
crons = ["59 14 * * *"]

シークレットは wrangler secret put で登録し、**リポジトリには入れないでください**。.dev.vars はローカル用で、.gitignore に追加します。
