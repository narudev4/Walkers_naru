## 完全移行の定義（何をもって「完全」とするか）

古谷さんの指示「完全に移行できるように」を、以下の 6 点を満たすことと定義する。**中途半端な残置を作らない。**

| # | 移行前 | 移行後 |
|---|---|---|
| 1 | Webhook 受信が Vercel Function | Workers の `fetch` ハンドラ |
| 2 | **B2B Draft Order 作成 API が Vercel Function**（301 行・業者様向け発注の本線） | Workers の同一エントリ配下 |
| 3 | 重複チェックがインメモリ `Set`（コールドスタートで消える＝二重請求の窓） | **D1 の `order_gid` PRIMARY KEY で DB レベルに** |
| 4 | 締めバッチが**どこでも動いていない**（`vercel-deploy/` に無い） | **Cron Triggers で毎日 23:59 JST に起動** |
| 5 | バッチの二重実行防止が `output/settle-runs.json` へのファイル書き込み（サーバーレスで機能しない） | D1 の `batch_locks` |

**唯一残る例外は `send-invoice.js`（Playwright）。** Workers では Chromium が動かないため移行不可で、指示書でも対象外とされている。**ただし現状どこでも動いていないため、移行によって失われる機能は無い。** この 1 点だけは請求書メールの A 案／B 案の確定待ちであり、B 案（Shopify メール 1 通に集約）に決まればスクリプト自体が不要になる。

## 1. 何を、どこへ移すのか

**Vercel の `ochiai-corp-webhook`（バックエンド）を Cloudflare Workers + D1 へ載せ替える。**

落合案件で Vercel に乗っているものは 2 つあり、移行対象は片方だけである。

| Vercel プロジェクト | 中身 | 移行 |
|---|---|---|
| `ochiai-corp-webhook`<br>`prj_hM36hdluGCuOG1ZFZzYDcKwLFo8G` | **バックエンド**。Shopify の `orders/create` Webhook を受信 → HMAC 署名検証 → マネーフォワードに請求書を作成 → Shopify 注文へ請求書 URL・番号を書き戻し。加えて業者様向け（B2B）の Draft Order 作成 API。締めバッチもここの担当。 | ✅ **対象** |
| `ochiai-b2c-concept`<br>`prj_PQGP7uwTWN9aTrNglm3mZ7r3YKfC` | `/store` のデザインモック（Next.js）。先方に画面を見せるためのもの。 | ❌ 対象外。最終的に Shopify テーマとして実装するため、役目を終えたら破棄する。 |

Shopify は「注文が入った」と通知を投げてくるだけなので、請求書を作る処理は Shopify の外に置くしかない。その置き場所が Vercel だった。**画面（フロント）はこの移行に一切関係しない。**

## 2. なぜ乗り換えるのか

コスト削減が主目的ではない。**本番で二重請求が起こり得る欠陥を塞ぐことが主目的**で、載せ替えはその手段である（指示書に明記）。

| # | 理由 | 現状 | 移行後 |
|---|---|---|---|
| 1 | **二重請求の防止**（本命） | `api/webhook.js:56` の重複チェックがインメモリの `Set`。Vercel Function のコールドスタートごとに消えるため、同一注文で請求書が 2 通発行され得る。 | D1 の `processed_orders.order_gid` を PRIMARY KEY にし、`INSERT ... ON CONFLICT DO NOTHING` の結果で処理続行を判定する。DB レベルで弾くため、アプリのロジックにミスがあっても二重発行しない。 |
| 2 | **締めバッチの定時実行** | `settle-batch.js` は `webhook/` 配下にのみ存在し、`vercel-deploy/` に無い。つまり**現在どこでも自動実行されていない**。二重実行防止も `output/settle-runs.json` へのファイル書き込みで、サーバーレスでは機能しない。 | Cron Triggers（毎日 14:59 UTC＝23:59 JST）で `scheduled` ハンドラを起動し、コード側で「20 日か」「月末か」を判定。ロックは D1 の `batch_locks` テーブルで取る。 |
| 3 | **コストと契約形態** | Vercel Hobby は商用利用不可、Pro は $20/月。二重請求防止に必要な永続ストアは Upstash Redis 等の別契約になる。 | Cloudflare は無料〜$5/月。D1・KV が標準で付く。 |

**期限は 9/1。** 9 月 1 日から実際の受注が始まるため、本番稼働後の基盤載せ替えは避ける（古谷さん判断）。

## 4. 移植の実作業量（実測値）

コードは既に Web API 標準（`Request` / `Response`）で書かれているため、大半が機械的な書き換えになる。

| 書き換え箇所 | 実数 | 備考 |
|---|---|---|
| `process.env` → `env` | **15 箇所 / 13 変数** | **全てモジュールのトップレベルで読んでいる**。Workers では動かないため、`env` を関数の引数で回す形に直す。`lib/` の関数シグネチャに手が入る |
| `waitUntil` → `ctx.waitUntil` | 2 箇所（import と呼び出し） | Cloudflare では標準 API |
| `node:crypto` の HMAC → Web Crypto | 1 関数（`verifyHmac`） | `createHmac` / `timingSafeEqual` を `crypto.subtle` へ。`nodejs_compat` に頼らず移植する |

### 🔴 リスク 0: マネーフォワードのアクセストークンが失効しており、更新しても保存されない（2026-07-29 発見）

**Phase 7 の前に解決が必要。** シークレット登録の作業中に判明した。

`moneyforward/.mf-tokens.json` のアクセストークンは **2026-06-19 取得・有効期限 1 時間**で、40 日前に失効している。リフレッシュトークンで自動更新する実装は入っているが、**更新後のトークンをどこにも保存していない**（移行元のコードにも「Vercel Function ではリフレッシュ後のトークンを永続保存できない」と明記されている）。

そのため次の状態になる。

- リクエストのたびに、失効済みのアクセストークンで 401 → リフレッシュ → リトライ、を繰り返す
- **マネーフォワードがリフレッシュトークンをローテーションする仕様であれば、2 回目以降の更新が失敗する**（1 回使うと古いものが無効になるため）

**これは移行で悪化する問題ではなく、Vercel でも同じだった構造的な欠陥である。** ただし 9/1 の受注開始までに必ず解決が要る。

**疎通テストを意図的に行っていない。** リフレッシュを走らせるとトークンがローテーションされ、ローカルの `.mf-tokens.json` と Vercel 側が同時に古くなる恐れがあるため。先に方針を決める必要がある。
