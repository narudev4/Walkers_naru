# かけ払いの入金消し込み 設計案（2026-08-03 v2）

ステータス: **naru レビュー待ち**。v1 に対する Codex レビュー（コード突合・指摘10件）と Haiku レビュー（業務運用・指摘8件）を反映済み。
E2E ウォークスルー ❓18「かけ払いの入金消し込みの手段が、設計にも工程表にも存在しない」への回答。
関連: C-5（締めバッチ）・C-8/C-11（返品相殺）・D-5（銀行振込）・A-8＋工程表 E-5（write_orders 権限）・質問 No.61〜63。

## 0. 結論（推奨）

1. **前提整備 P-0 が先**: 締めバッチが作った請求書の ID を D1 に記録していないという**実装欠落が判明**した（レビューで発見）。請求書↔注文の対応表がどこにも永続化されておらず、これを塞がないと案A・案B とも成立しない。追加提案ではなく既存実装の欠落として先に直す。
2. **9/1 は案A（手動運用）で開始**。入金の正は MF 請求書の `payment_status` に一本化し、落合様は MF 画面だけを触る。Shopify への「支払い済み」の写しは当面 Walkers が行う。
3. **10/1 までに案B（未入金アラート＋写しの自動化）を追加提案**。成立条件は解決済み — MF API v3 で入金ステータスの取得・更新・期日フィルタが可能なことを公式 OpenAPI で確認した。
4. 金額の不一致（一部入金・過入金・手数料差額）は**自動化の対象外**と最初から宣言する（§4）。

## 1. 問題定義

かけ払い（20日締め・末締め）は「締めバッチ → MF 請求書（下書き）→ スタッフ確認して送付」までは実装済みだが、その先の (a) 誰が・どこで入金を確認するか、(b) 請求書と Shopify 注文の対応をどこで持つか、(c) 未入金をどう検知して督促するか、が未定義。9/1 テスト運用の最初の締め（9/20）で必ず踏む。

## 2. スコープの前提（契約）

MF 連携は業務委託契約書 第2条2項で Phase 2 扱い（契約範囲外）。よって**案B の自動化は追加提案扱い**。ただし **P-0（請求書 ID の記録）は既存実装の欠落の修正**であり、追加提案とは別枠で扱う。

## 4. 業務フローの設計（正とするデータの宣言）

- **入金の正 = MF 請求書の `payment_status`**（落合様の経理が触る場所を1つにする）。
- **Shopify の「支払い済み」は写し**。遅れてよい。かつ**全額一致のときだけ写す** — MF の入金ステータスは請求書単位の3値で金額を持たず、Shopify のマークも注文単位の全額マークのため、1請求書=N注文の構造では all-or-nothing にしかならない。差額があるケース（一部入金・過入金・手数料差額）は自動化の対象外とし、未処理一覧に残して人が判断する。
- **D1 は突合・検知用のインデックス**（真理源にしない）。

役割分担（推奨。naru 承認で確定）:

| 誰が | 何を | いつ |
|---|---|---|
| 落合様（経理） | 銀行明細と MF 請求書を突合し、MF 上で入金済みに更新。 | 入金確認の都度（推奨: 毎週金曜。曜日は 8/4〜の確認で先方と確定）。 |
| **Walkers（当面）** | 入金済み請求書に対応する Shopify 注文（明細名の注文番号で特定）を支払い済みマーク。 | 週次。案B 稼働後は自動化。 |
| Walkers（システム） | 期日超過かつ未入金の請求書を検知して通知。 | 案A=なし（落合様が MF 一覧を「未入金」で絞って目視）／案B=日次。 |
| 落合様 | 督促: 支払期日から **7日** 超過で電話または再送メール（日数・手段は先方確認）。 | 検知の都度。 |

## 5. 段階案

### P-0: 前提整備（既存実装の欠落の修正。案A の前に必須）

締めバッチに請求書 ID の永続化を追加する。2案あり、**両方入れるのが安い**:

- (1) `settle_batches` 経由ではなく、markSettled 拡張 or 新テーブルで **注文 gid ↔ mf_invoice_id** を記録。
- (2) 締め経路にも**請求書 URL・番号の注文メタフィールド書き戻し**を追加（都度払い経路 pipeline.js:98-99 と同じ処理。これがあれば Shopify 側から単独で辿れ、F-5 のマイページ請求書リンクにも将来効く）。

### 案A: 手動運用（9/1 開始の基本形。開発は P-0 のみ）

1. 締めバッチが請求書（下書き）を作る（実装済み）→ スタッフ確認して MF から送付（決定済み）。
2. 入金があったら、落合様が MF で該当請求書を「入金済み」へ更新（MF 画面の標準操作）。
3. Walkers が週次で、入金済み請求書の明細名から注文番号を拾い、Shopify の該当注文（N 件）を支払い済みマーク。
4. 未入金の検知は、落合様が MF の請求書一覧を「未入金」で絞って週1回目視。期日7日超過で督促（§4 の表）。
5. 8/20 レクチャーでは落合様側の操作（2・4）だけを教える。Shopify 側の写しは Walkers 作業なのでレクチャー対象外 — これでレクチャー内容が確定する。

### 案B: 未入金アラート＋写しの自動化（10/1 までの追加提案）

- 既存 cron に相乗りし、`GET /billings?range_key=due_date` で期日到来分を取得。
- 新テーブル **`invoice_payments`** に payment_status・paid_at を記録（**カラム追加はしない** — schema.sql は CREATE TABLE IF NOT EXISTS のみの運用で、既存テーブルへのカラム追加は本番に反映されず環境差分事故になるため新テーブル一択）。
- 期日超過かつ未入金の一覧を通知（通知先は要 naru 判断: 真理源スプシ書き込み or メール。**cron は 23:59 発火のため深夜通知になる** — 朝に読める媒体にするか、cron をもう1本足すかを通知先と併せて決める）。
- 入金済み請求書に紐づく注文の自動マーク: P-0 の対応表 + orderMarkAsPaid の Workers 移植 + write_orders 付与（E-5）の3点セットで成立。**全額一致のみ自動、差額ありは未処理一覧へ**（§4）。
- 実装時の確認: 20日・月末は締めバッチと同一起動になるため、Workers のサブリクエスト上限（有料 1,000／無料 50）に対する余裕を想定件数で確認する（無料プランのままなら締めバッチ単体でも危険水域）。

### 案C: 銀行明細からの自動消込（Phase 2 以降・今回は提案しない）

MF クラウド側の銀行連携を先方が契約・設定すれば案B の取得値が自動で埋まる。C-11（税理士相談）の場で言及するに留める。
