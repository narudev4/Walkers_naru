## Findings（重大度順）

### [High] Q3 締めバッチの「締め済み照会」が対象 101 注文以上で D1 の上限に当たり、その締めの請求書が 1 枚も作られない

- 場所: `workers/src/lib/d1Store.js:194-202`（`findAlreadySettled`）、呼び出し `workers/src/lib/settleBatch.js:195`。
- 仕様の出典: 工程表 C-5「締め日にその期間の注文をまとめて 1 枚の請求書にする」・質問事項末尾「20 日 23:59 に対象期間にフルフィルメントされた注文を参照し下書き作成」。取引先は推定 150〜200 件（工程表 A-10 の MF 実測）。
- 成立経路: 締め対象（期間内発送・区分一致・返品除外後）の注文 GID を **1 本の SELECT の IN 句に「?」を件数分並べて bind** する → Cloudflare D1 の公式上限は「1 クエリあたりの bind パラメータ 100 個」（developers.cloudflare.com/d1/platform/limits）→ 101 件以上でエラー → `runSettleCycle` の catch で batch=failed → その締めの**全顧客分の下書きがゼロ**。さらに F6 のとおり同日の再実行口が無い。
- 反証の確認: ローカルの SQLite（miniflare）は変数上限が 32,766 のためテストでは再現しない（settleCycle テストは最大 2 注文）。9/1 の少数取引先では発火しない。しかし発火条件は本運用の通常量で、コード自身が「100 件を超えると静かに請求漏れ」を懸念して注文取得をページングしている（`settleBatch.js:18-19`）直後に、この壁がある。
- 最小修正: `findAlreadySettled` を 90 件ずつに分割して SELECT し Set に集約する（数行）。または `settled_batch_id IS NOT NULL` の行を全件取得して Set 化。
- 必要テスト: 対象 150 注文で締めが完走すること。ローカルは上限を再現しないため、「1 回の SELECT に 100 個以上 bind しない」ことをコードで保証（チャンク幅の定数）し、その分割をテストする。
