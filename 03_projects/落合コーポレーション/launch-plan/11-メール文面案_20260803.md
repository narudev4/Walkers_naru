## 1. 技術調査: 通知テンプレートで支払区分をどう参照するか

### 1-1. 結論

**`customer.metafields.b2b.payment_terms` が注文確認メールで参照できるかは、公式ドキュメントでは確認できなかった（未確認）。** 断定できる材料がないため、本命案として置きつつ、確実に動く代替案を 2 つ用意する。

### 1-2. 調査で分かったこと

| 参照先 | 通知テンプレートでの可否 | 根拠 |
|---|---|---|
| 注文オブジェクトの各プロパティ（`total_price`、`line_items` 等） | **可**。ただし `order.` を付けずに裸で書く | ヘルプセンター「Notifications variables reference」に「The order object isn't referenced by name in email templates.（メールテンプレートでは order オブジェクトを名前で参照しない）」と明記。`{{ order.shipping_method.title }}` ではなく `{{ shipping_method.title }}` と書く。 |
| `customer` オブジェクト | **可** | 同ページの Order properties に「`customer` — Customer object containing the attributes of the customer output」と記載。 |
| 注文属性 `attributes.KEY` | **可** | 同ページに「Any attributes which were attached to the order. Example: `{{ attributes.gift-note }}`」と明記。注文属性はカートで収集された値が引き継がれる（order オブジェクトの `attributes` は "Attributes are collected with the cart"）。 |
| 商品・バリエーションのメタフィールド | **可** | 同ページに `line.product.metafields.NAMESPACE.KEY` / `line.variant.metafields.NAMESPACE.KEY` と明記。 |
| 注文メタフィールド `metafields.NAMESPACE.KEY` | **記述が矛盾している** | ヘルプセンターには「Any metafields on the order. Use the following syntax: metafields.NAMESPACE.KEY」と記載がある一方、開発者フォーラムで Shopify スタッフ（Liam-Shopify）が「Only product and variant metafields are supported on email notifications currently」と回答している。どちらが現行かは未確認。 |
| **顧客メタフィールド `customer.metafields.*`** | **未確認** | 公式ドキュメントに可否の記載がない。スタッフ回答（上記）に従えば不可だが、別スレッドでは `shop.metafields` の `single_line_text_field` が「`.value` を付けずに出力すれば動く」という検証報告がある。**実機テストが必要。** |

### 1-3. `.value` を付けるか付けないか

メタフィールドが参照できた場合でも、`.value` の扱いに罠がある。開発者フォーラムの検証報告では、`single_line_text_field` は **`.value` を付けずに出力したときに動いた** とされている。一方、テーマ Liquid の作法では `.value` を付けるのが標準である。

どちらでも壊れないように、**`capture` で一度文字列に落としてから比較する**書き方を採用する（§2）。`capture` はメタフィールドが drop オブジェクトでも生文字列でも、出力結果を文字列として取得できるため、`.value` の有無に依存しない。

### 2-2. 代替案 A: 顧客タグで分岐（推奨フォールバック）

本命案が動かなかった場合の第一候補。`customer` オブジェクトは通知テンプレートで利用できることが公式に明記されており、`tags` は customer オブジェクトの標準プロパティであるため、参照できる可能性が高い（**ただし実機での動作確認は必要**）。テーマの改修が不要な点が利点。

顧客レコードに `payment:prepaid` / `payment:20th` / `payment:eom` のいずれかのタグを付ける運用にしたうえで、§2-1 の冒頭 2 行を以下に差し替える。以降の分岐はそのまま使える。

```liquid
{%- assign payment_terms = '' -%}
{%- if customer.tags contains 'payment:prepaid' -%}
  {%- assign payment_terms = 'prepaid' -%}
{%- elsif customer.tags contains 'payment:20th' -%}
  {%- assign payment_terms = '20th' -%}
{%- elsif customer.tags contains 'payment:eom' -%}
  {%- assign payment_terms = 'eom' -%}
{%- endif -%}
```

**欠点。** メタフィールドとタグで支払区分の情報が二重管理になる。顧客の支払条件を変更したときに両方を更新する運用ルールが要る。Shopify Flow でメタフィールド変更をトリガーにタグを自動同期する手もあるが、本案件で Flow を使うかは未確認。

### 2-3. 代替案 B: 注文属性で分岐（確実だがテーマ改修が要る）

`attributes.KEY` は公式ドキュメントに使用例が明記されており、**3 案のなかで唯一「通知テンプレートで動く」ことが公式に確認できている**。ただしテーマ側で値を注入する実装が必要になる。

テーマのカートフォーム内（`{% form 'cart' %}` の内側）に以下を置き、ログイン中の顧客のメタフィールド値を隠しフィールドでカート属性に流し込む。

```liquid
{%- if customer -%}
  {%- capture ct -%}{{ customer.metafields.b2b.payment_terms }}{%- endcapture -%}
  <input type="hidden" name="attributes[payment_terms]" value="{{ ct | strip | escape }}">
{%- endif -%}
```

通知テンプレート側は §2-1 の冒頭 2 行を以下に差し替える。

```liquid
{%- assign payment_terms = attributes.payment_terms | default: '' | strip -%}
```

**欠点。** カートフォームを経由しない購入経路（商品ページからの直接購入ボタン、Shop Pay の高速チェックアウト等）では属性が付かず、分岐が効かない可能性がある。採用する場合は業者様向けの動線でカートフォームを必ず通す設計かどうかの確認が要る。

### 2-4. 採否の進め方

1. まず §2-1（本命）を貼って §4 のテストを実行する。
2. 動けばそのまま採用。単一の真理源で済むため運用がいちばん軽い。
3. 動かなければ §2-2（顧客タグ）をテストする。テーマ改修が不要なので次に軽い。
4. それも動かなければ §2-3（注文属性）へ。確実性は最も高いがテーマ改修と動線確認が要る。

## 4. 管理画面での貼り付け手順

1. Shopify 管理画面で **設定 > 通知 > お客様の通知（Customer notifications） > 注文確認（Order confirmation）** を開き、**コードを編集（Edit code）** を押す。
2. テンプレート内で挨拶文のブロック（`{{ customer.first_name }}` を含む `<p>` タグ）を探し、**その直後・注文サマリーのテーブルより前**に §2-1 のコードをそのまま貼り付け、保存する。
3. 保存後、業者様アカウントで実際にテスト注文を 1 件通して受信メールを確認する（「テストメールを送信」はサンプルデータで描画されるため、メタフィールドやタグの分岐が正しく効いているかの判定には使えない）。

**検証は支払区分ごとに 3 パターン行う。** `prepaid` の顧客・`20th`（または `eom`）の顧客・メタフィールド未設定の顧客の 3 つでテスト注文し、①都度払いの案内が出る ②かけ払いの案内が出て締め日が正しい ③何も挿入されず既定文面のまま、をそれぞれ確認する。③が既定文面どおりであることの確認が、一般のお客様向け（B2C）への影響がないことの担保になる。
