## 2. OAuth 認可（A-10）

### 2-0. 分岐（1-2 の結果で決める）

| 分岐 | 条件 | やること | 推奨 |
|---|---|---|---|
| **A** | 落合様アカウントのアプリポータルで**新規作成できる** | 落合様アカウントでアプリを作成し、その client_id/secret を使う。 | **推奨**。アプリの所有が落合様側に残る（Walkers の検証口座が消えても連携が切れない）。 |
| B | 新規作成できない／ポータルに入れない | 現行アプリ（Walkers 検証口座で発行済みの `MF_CLIENT_ID`）のまま、落合様ログインのブラウザで認可だけ行う。認可後の `GET /office` が落合様の事業者名を返せば成立。 | 成立すれば動くが、アプリの所有が Walkers 側に残る。34 に「将来 A へ移行」を残す。 |

アプリ作成時の設定（A の場合。README「人手ステップ 2」と同じ）:
- 名前: `Ochiai Integrations (Production)`（Shopify 側の新アプリ名と揃える）。
- リダイレクト URI: `http://localhost:8787/callback`（`.env` の `MF_REDIRECT_URI` と 1 文字違わず一致）。
- スコープ: `mfc/invoice/data.write`。
- クライアント認証方式: `CLIENT_SECRET_POST`。
- 発行された client_id / client_secret は `credentials/ochiai-mf.md` へ。

### 2-1. ローカルで認可 → 疎通

```bash
cd 03_projects/落合コーポレーション/moneyforward
# A の場合のみ .env の MF_CLIENT_ID / MF_CLIENT_SECRET を新アプリの値に書き換える
# （MF_ACCESS_TOKEN / MF_REFRESH_TOKEN 行は空にしておく。旧トークンのフォールバックを止めるため）
npm run auth:manual        # ① 表示された URL を、落合様でログイン済みのブラウザに貼る
                            # ② 同意 → リダイレクト先 URL（...?code=...&state=...）を丸ごと貼り戻す
                            #    → .mf-tokens.json に保存される
npm run whoami             # ③ 事業者名が「落合コーポレーション」系で返ることを確認
```

- ③の直後は**ローカルで他の MF コマンドを叩かない**（401 を踏むとリフレッシュが走り、refresh_token がローテーションして Workers に渡す前に古くなる）。
- `state 不一致` が出たら最初からやり直す（URL の貼り間違い）。

### 2-2. Workers へ切替（トークンの正は D1）

```bash
cd ../ochiai-integrations/workers
# (0) 現在の D1 トークン行を退避（ロールバック用・値は scratchpad へ）
npx wrangler d1 execute ochiai-integrations --remote --command \
  "SELECT provider, obtained_at, expires_at, updated_at FROM oauth_tokens"
# (1) A の場合のみ
npx wrangler secret put MF_CLIENT_ID
npx wrangler secret put MF_CLIENT_SECRET
# (2) .mf-tokens.json の値を投入（seed 用。mfClient.js:59-72 が D1 空のとき env から insertIfAbsent する）
npx wrangler secret put MF_ACCESS_TOKEN
npx wrangler secret put MF_REFRESH_TOKEN
# (3) D1 の旧トークン行を消す（消した瞬間から次のリクエストで seed される）
npx wrangler d1 execute ochiai-integrations --remote --command \
  "DELETE FROM oauth_tokens WHERE provider='moneyforward'"
```

### 2-3. 通し確認 → 後片付け（launch-plan/31 の E2E と同じ型）

1. デモ顧客（prepaid）で発注表からテスト注文 → Webhook → **落合様の MF に請求書下書きが 1 件立つ**ことを MF 画面で確認。
2. D1 `processed_orders` に `mf_invoice_id` が入っていることを確認。
3. 後片付け: MF 下書きを削除 → D1 行を削除 → Shopify の注文・Draft を削除 → デモ顧客を復帰。
4. 取引先: この検証で MF に「デモ法人」等の取引先が**新規作成される**。1-6 の実取引先と混ざるので必ず削除し、顧客側の `b2b.mf_partner_id` もクリアする（C-12 の 8/6 と同じ手順）。

### 2-4. 切替タイミングと既知の論点（naru 判断）

- 34 前提「MF 系はログインできた今のうちに全部終わらせる」に従い**今夜切替**。以後のテスト注文は落合様の本番 MF に下書きを作るため、テストのたびに 2-3 の後片付けを行う。
- 都度払いの下書きが溜まる問題（34 §7-3・案a「残す・定期破棄」）は未決。切替とは独立に決めてよい。
- ロールバック: `MF_CLIENT_ID/SECRET/ACCESS/REFRESH` を `.env.trial.bak` の値に戻し、D1 行を削除して再 seed。検証口座の refresh_token が既に失効している可能性はある（その場合は検証口座で再認可）。
