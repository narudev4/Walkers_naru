## テーマ2: 「完全理解設計書」（Fingate 超え）

### 目的
naru がプロジェクトを完全に理解し、古谷さんのどんな抽象的 FB にも正論で返せる状態を作る。直近の具体例: 「商品ごとの掛け率を追加するとチェックが増える懸念」という FB に、影響範囲と工数を即答できること。

### Fingate 工程表にあるもの（最低ライン）
作業一覧（フェーズ▶構造）/ 実装範囲 / 画面一覧 / 機能一覧 / API設計 / DB設計 / ステージングテスト（手動・自動）/ 環境情報 / バックログ

### Fingate を超えるために足すもの（提案）
1. **データモデル完全辞書** — metafield（b2b.*全項目）/ metaobject（discount_matrix）/ Shopify 注文・顧客 / MF 請求書の全フィールドと相互参照を1枚に。「このデータは誰が書いて誰が読むか」まで
2. **仕様決定の根拠台帳（既存 Q&A の B2 を拡張）** — 各仕様について「採用方式 / 検討した代替案 / 採用理由 / 一次情報」の4点セット。launch-plan/03-briefing-qa.md の出所台帳が原型
3. **変更影響マトリクス（古谷さん FB 対応の本丸）** — 想定される仕様変更シナリオ × 影響箇所（discountEngine / Liquid 表示 / Draft Order / MF請求書 / 締めバッチ / テスト / 運用チェック工数）の表。
   例・「商品ごとの掛け率」: 現行は 顧客override（顧客×カテゴリ）→ matrix（グループ×カテゴリ）→ 正価 の3段。商品単位を足す場合は cascade に1層追加（エンジン変更は小）だが、**運用面で「商品×顧客の組合せ管理」が発生し、掛率設定ミスの検知（チェック）工数が増える** — 古谷さんの懸念はここ。対応案: 掛率設定の自動検証スクリプト（全組合せの妥当性チェック）をセットで提案すれば懸念に正論で返せる
4. **処理フロー図** — ①B2B注文→webhook→MF請求書（③都度）②締めバッチ（①②かけ）③本番移行 の3枚。各ステップに「失敗したらどうなるか/リトライは」を注記
5. **用語辞書** — トンマナ/上代/下代/掛率/御社価格/フルフィルメント等の定義（用語ゆれ事故の再発防止。案件 CLAUDE.md の用語表と連動）
6. **運用チェックリスト** — 公開後の日次/月次運用（締めバッチ確認・請求書送付・在庫）で誰が何を見るか

### 進め方（提案）
既存資産（implementation-spec.md / 03-briefing-qa.md / スプシ各タブ / コード）から 1〜6 を Fable が起草 → Codex+Haiku クロスレビュー → naru が通読して「自分の言葉で説明できない箇所」を潰す QA セッション → スプシ新タブ群に昇格。
