## 1. 業務用語（五十音順）

### 一般のお客様向け（B2C）
- **定義**: 一般消費者向けの公開ストアフロント、およびその顧客層を指す本案件の正式呼称。
- **本案件での文脈**: 先方向け文書・スプシでの B2C 側の呼称。決済はクレカ／銀行振込／後払い／代引き／PayPay（CONTEXT.md §14 で確定）。
- **誤用注意**: 「個人向け」等の表記揺れは使用禁止（CLAUDE.md 用語統一表）。

### インボイス（適格請求書）・T番号
- **定義**: インボイス制度における適格請求書と、その発行事業者の登録番号（T+13桁）。請求書に記載がないと買い手（業者様）が仕入税額控除を受けられない。
- **本案件での文脈**: MF 請求書に落合社の T番号を記載する必要がある（テスト K-07）。先方は既に MF ビジネスプランを業務利用中のため、**既存 MF の帳票設定を確認するのが先**で、未設定の場合のみ先方に確認する（CONTEXT.md §14。「T番号をください」から入らない）。
- **未確定**: 既存 MF に T番号が設定済みかは未確認。

### 売上計上=注文時・請求確定=発送時
- **定義**: 会計上の売上は注文時に立ち、請求書に載せる確定は発送（フルフィルメント）時とする本案件の請求ルール（第3回MTG 決定4）。
- **本案件での文脈**: 締めバッチ（settle-batch.js）は注文日ではなく**発送日（fulfillment の作成日時・JST）**が締め期間内にある注文を集計する。未発送の注文は締めから除外される（テスト L-04）。
- **誤用注意**: 「注文日基準で締める」と書かない。イレギュラーな繰越も受けず発送日基準で機械的に締める（決定7）。

### 卸価格
- **定義**: 正価に掛率を乗じて算出する、業者様（B2B）向けの販売価格。
- **本案件での文脈**: ストアフロントではログイン中の corporate 顧客にのみ `b2b-wholesale-price.liquid` で表示する（Phase3 完了）。注文時は Draft Order の priceOverride で適用する。priceOverride で入れた額は税抜扱いとなり消費税 10% が別途加算される（discount-system.md §7、税込で扱う場合の調整は要確認）。
- **誤用注意**: 標準カートは正価表示のため、卸価格との差異は注記で補う（テスト I-01）。

### 御社価格
- **定義**: 業者様ごとに掛率を適用した後の「その会社専用の価格」を指す顧客向けの表現（実体は卸価格と同じ）。
- **本案件での文脈**: 業者様向け画面・文書で使う呼称の候補。
- **未確定**: ストアフロントの表示文言としてこの語を採用するかは未確定（表示文言の確定はトンマナ・デモ確認の工程で行う）。

### かけ払い（①20日締め・②末日締め）
- **定義**: 締め期間内の注文をまとめて後払いする支払区分。本案件では ①20日締め（`20th`）と ②末日締め（`eom`）の2種。
- **本案件での文脈**: customer metafield `b2b.payment_terms` の値で判定する。①は期間「前月21日〜当月20日」・支払期日は翌月20日、②は期間「当月1日〜末日」・支払期日は翌月末（settle-batch.js 実装済み）。注文確認次第出荷し、請求書は締めバッチで顧客別に統合する。注文ごとの請求書は作成しない（pipeline.js）。
- **誤用注意**: ③都度払いと混同しない。かけ払いは「下書き→人手確認→送付」、都度払いは「即時自動送付」。

### 掛率
- **定義**: 正価に乗じる係数（rate、0 < x ≦ 1）。0.60 なら正価の 60%、すなわち4割引を意味する。
- **本案件での文脈**: `custom_overrides[category] ?? discount_matrix[group][category] ?? 1.0` の優先順で決定する（discountEngine.js、15テスト全パス）。現在は demo 値（例: A=0.60／B=0.70／C=0.80）で先行しており、実データは未入手（確認事項#3）。
- **未確定**: **「掛け」の基準が上代比か下代比かは未確定**（確認事項#3）。区分別の正しい値も本番前に先方確認が必要。
- **誤用注意**: 「割引率」と書かない（0.60 は「6割引」ではなく「正価の60%」）。

### 業者様向け（B2B）
- **定義**: 卸取引先（業者様）向けの招待制ストアフロント、およびその顧客層を指す本案件の正式呼称。
- **本案件での文脈**: 先方向け文書・スプシでの B2B 側の呼称。決済は請求書払い（Manual Payment・銀行振込）のみ（CONTEXT.md §14 で確定）。
- **誤用注意**: 「法人向け」等の表記揺れは使用禁止（CLAUDE.md 用語統一表）。

### 下代
- **定義**: 小売店・業者が仕入れる際の価格（仕入価格・卸価格に相当する商慣習上の語）。
- **本案件での文脈**: B2B 送料条件の基準額（下代2万円以上で送料無料。九州・北海道は3万、沖縄は5万。implementation-spec.md 質問No.4 確定）。
- **誤用注意**: 掛率の基準が上代比か下代比かは未確定のため、「下代=正価×掛率」と断定して書かない。

### 締めバッチ
- **定義**: かけ払い（①②）顧客の締め期間内フルフィルメント済み注文を顧客別に統合し、MF 請求書の**下書き**を作成するバッチ処理（webhook/settle-batch.js）。
- **本案件での文脈**: 本番では締め日 23:59 JST に cron 実行（決定6。cron 設定自体は残作業 T1-6）。下書きはスタッフが確認して送付する（決定5）。同一の締め（term+締め日）は `output/settle-runs.json` に記録され二重実行されない（やり直しは `--force`）。
- **誤用注意**: ③都度払いは締めバッチの対象外（webhook 起点で即時処理）。

### 上代
- **定義**: メーカー希望小売価格。店頭で一般のお客様に提示する定価に相当する商慣習上の語。
- **本案件での文脈**: 掛率の基準候補の一つ（上代比か下代比かは未確定・確認事項#3）。B2C の表示価格（正価）に対応する概念。
- **誤用注意**: 税込か税抜かの扱いを含め、先方との数値確認が済むまで金額例を断定しない。

### 正価
- **定義**: 掛率を適用しない定価。掛率決定ロジックのデフォルト値（rate 1.0）にフォールバックしたときの価格。
- **本案件での文脈**: B2C の表示・販売価格。B2B でも matrix 未定義カテゴリや category 未設定商品は正価に安全フォールバックする（discount-system.md §7 実証済み）。
- **誤用注意**: 「定価」「標準価格」等と揺らさず、設計文書では「正価」で統一する。

### 都度払い（③）
- **定義**: 注文1件ごとに請求書を発行し、入金確認後に出荷する支払区分（`prepaid`）。
- **本案件での文脈**: orders/create webhook を起点に MF 請求書を即時自動作成し、Playwright（A-2方式）で自動送付する（下書きなし・決定準拠）。支払期日は請求日+7日（implementation-spec.md Task1 表）。
- **誤用注意**: かけ払い（①②）と異なり出荷は「入金確認次第」。「注文確認次第出荷」と書かない。

### トンマナ
- **定義**: トーン&マナー。色・フォント・雰囲気といった見た目の調子を指す。
- **本案件での文脈**: 先方（宏樹様・ぽぽ様）に選定してもらうのは常に「トンマナ」。B2B サイト用トンマナ案の作成・共有が NA として進行中（NA-20260715-006／008）。
- **誤用注意**: **「デザイン」はレイアウト・構成まで含む別概念**であり、選定対象の呼称として使用禁止（CLAUDE.md 用語統一表）。

### 宏樹様／ぽぽ様
- **定義**: 落合 宏樹 様（社長・決定権者）と落合 ぽぽ 様（窓口）の正式表記。
- **本案件での文脈**: 対外文書・議事録・スプシでの人名表記ルール。
- **誤用注意**: 「ひろき様」等のひらがな表記は使用禁止（CLAUDE.md 用語統一表）。

### フルフィルメント
- **定義**: Shopify における注文の発送処理（fulfillment）。発送済みの記録が注文に紐づく。
- **本案件での文脈**: **請求確定の基準**（決定4）。締めバッチは fulfillment 作成日時を JST 日付に変換し、締め期間内かどうかで集計対象を判定する（settle-batch.js）。未フルフィルメント注文は締めから除外（テスト L-04）。
- **誤用注意**: 「注文確定」「決済完了」とは別のイベント。請求のトリガーはあくまで発送。

## 2. 技術用語（アルファベット順）

### Client transfer store vs Dev store
- **定義**: Shopify Partner が作成できるストアの種別。Dev store（Development ストア）は開発・デモ用で本番決済等に制約があり、Client transfer store はクライアントへ引き渡して本番プランに移行する用途のストア。
- **本案件での文脈**: 掛率検証・デモは Dev store「落合コーポレーション様 デモ」で実施。Dev store では storefront checkout が使えない制約があり、一部テストは本番ストアのみで実施可能（02-test-scenarios.md【本番のみ】、I-05 の D-1 制約）。Draft Order 方式は全プラン共通のため本番 Basic に転用可（discount-system.md §11）。
- **未確定**: 本番ストアへの具体的な移行経路（transfer の実施方法・Admin API トークンの発行経路）は要確認（discount-system.md §11 残課題）。

### cron
- **定義**: 指定時刻にプログラムを定期実行する仕組み。
- **本案件での文脈**: 締めバッチを 20日・末日の 23:59 JST に自動実行する計画（決定6）。settle-batch.js は手動／cron 両用で実装済みだが、**cron 設定自体は未実施**（残作業 T1-6、T1-1 の Vercel デプロイ完了待ち）。

### custom_overrides
- **定義**: customer metafield（`b2b.custom_overrides`、JSON 型）。特定顧客に限りカテゴリ別掛率を上書きする（例: `{"racket": 0.55}`）。
- **本案件での文脈**: 掛率決定の**最優先**（discount_matrix より先に参照）。テスト H-04/H-05 で優先とフォールバックを検証する。

### Dawn テーマ／Rise テーマ
- **定義**: いずれも Shopify の無料標準テーマ。**本案件の実装テーマは Rise**（shopify-theme/config/settings_schema.json で確認済み）。spec の「Dawn」記述は旧計画の名残であり誤り（→ 00 Z-7）。
- **本案件での文脈**: B2C 14画面・B2B 6画面の大半を Rise 標準 + セクション設定で構成し、卸価格表示等は Liquid カスタマイズ（`b2b-wholesale-price.liquid` 等）で追加する（implementation-spec.md Task2）。

### discount_matrix
- **定義**: Shopify の metaobject。group（A/B/C）× category（racket/wear/…）× discount_rate（0.0〜1.0）の組合せで掛率マトリクスを表現する。
- **本案件での文脈**: 新カテゴリ・新グループはエントリ追加のみで対応でき、コード変更不要（実機検証済み・Draft #D9）。Admin の Content → Metaobjects から GUI で編集でき、落合社の日常運用を想定。現在の値は demo 値（実データ差替え待ち・T3-1）。

### Draft Order
- **定義**: Shopify の下書き注文。管理者・API が価格を指定して作成し、確定すると通常注文に変換できる。
- **本案件での文脈**: Shopify Basic では Functions による自動割引が使えないため、**Draft Order に掛率適用価格を設定する方式**が本案件の中核（discount-system.md §11 方針転換）。B2B のカート→「法人価格で注文する」→ Draft Order 自動変換が現行方針（(b)カート方式・naru 7/14。古谷さん合意待ち=未確定）。

### HMAC
- **定義**: 共有秘密鍵を使ったメッセージ認証コード。Shopify は webhook 本文の HMAC-SHA256 署名をヘッダーで送る。
- **本案件での文脈**: webhook/server.js が署名を検証し、Shopify 以外からの偽リクエストを排除する（実装・検証済み）。

### Liquid
- **定義**: Shopify テーマのテンプレート言語。
- **本案件での文脈**: 1ストア内で `customer.metafields.b2b.customer_type` により B2C/B2B の表示を条件分岐する（Basic=1ストア制約への対応）。卸価格表示・B2B 専用ナビ・コーポレートページ導線も Liquid 分岐で実現する。

### Manual Payment
- **定義**: Shopify の手動決済方法。オンライン決済を通さず、注文を支払保留（PENDING）で確定し、入金確認後に管理者が支払済みにする。
- **本案件での文脈**: B2B の請求書払い（銀行振込）の実現手段。Shopify 決済手数料がゼロになる（質問No.3 技術調査確定）。入金確認後に Admin で「支払い済みマーク」→ PAID 遷移（テスト J-01）。

### metafield
- **定義**: Shopify の標準オブジェクト（顧客・商品・注文等）に任意の追加項目を持たせる仕組み。
- **本案件での文脈**: namespace `b2b` を使用。Customer 側= `customer_type` / `discount_group` / `custom_overrides` / `payment_terms` / `mf_partner_id` 等、Product 側= `category` / `sport`。注文への請求書 URL 書戻し（`b2b.mf_invoice_url` 等）にも使う（テスト K-03）。

### metaobject
- **定義**: Shopify でストア全体に紐づく独自データ型を定義・管理できる仕組み。metafield が「既存オブジェクトへの追加項目」なのに対し、metaobject は独立したデータエントリ。
- **本案件での文脈**: 掛率マトリクス `discount_matrix` の実体。Admin GUI で編集可能なため、独自管理画面なしで先方運用できる。

### MF（マネーフォワード）ビジネスプラン
- **定義**: マネーフォワード クラウドの契約プランの一つ。API 利用制限なし・月間請求書数無制限。
- **本案件での文脈**: 先方が**既に業務利用中**（第3回MTG 確定・2026-06-03）。本番の請求書自動発行は先方の既存 MF アカウントで OAuth 認可する前提（CONTEXT.md §14）。現在の検証環境は naru のトライアル口座であり、MF_CLIENT_ID を先方口座側で発行し直す必要があるかは**未確認**。

### OAuth
- **定義**: 第三者アプリにパスワードを渡さず API アクセス権を委譲する認可プロトコル。
- **本案件での文脈**: MF 請求書 API の認可方式。トークンは `.mf-tokens.json` に保存し（Git 管理外）、本番化には**先方管理者による接続承認操作**が必要（先方お願い事項に計上済み・CONTEXT.md §14）。

### Playwright A-2 方式
- **定義**: ブラウザ自動化ツール Playwright で MF の画面を自動操作し、請求書メールを送信する方式。自動送信化調査（真理源スプシ「自動送信化_調査」タブ）で採番された案の名称。
- **本案件での文脈**: MF API にはメール送信エンドポイントが存在しない（確定）ため、③都度払いの「即時自動送付」はこの方式で実現する（`mf-automation/send-invoice.js`、実証済み）。
- **誤用注意**: 「MF API で送信」と書かない（API では送信できないことが本方式採用の理由）。

### priceOverride
- **定義**: Shopify Admin API の `DraftOrderLineItemInput` のフィールド。Draft Order の明細行ごとに単価を上書き指定できる。
- **本案件での文脈**: 掛率適用後の卸価格を行単位で設定する手段（Basic で利用可能・実機検証済み）。**指定額は税抜扱い**となり消費税 10% が別途加算される点に注意（税込運用の要否は要確認）。

### Shopify Basic vs Plus
- **定義**: Shopify の契約プラン。Basic は下位プラン（2026-07 時点の公式料金: 月払い 4,850 円・年払い換算 3,650 円/月）、Plus は大規模向け上位プラン。
- **本案件での文脈**: 本案件は **Basic**。カスタムアプリの Shopify Functions は Plus 限定と一次情報で確定したため（shopify.dev + community staff 回答）、自動チェックアウト割引ではなく Draft Order 方式を採用した（discount-system.md §5 注記・§11）。Basic=1ストア制約のため B2C/B2B は Liquid 分岐で分離する。

### Vercel Function
- **定義**: Vercel 上で動くサーバーレス関数。公開 URL で HTTP リクエストを受けられる。
- **本案件での文脈**: webhook 受信サーバ（server.js）と B2B カートからの Draft Order 生成 API のホスティング先。**デプロイは未完了**（残作業 T1-1。以降の webhook 登録 T1-2・cron 設定 T1-6 がこれ待ち）。

### webhook
- **定義**: イベント発生時に外部 URL へ HTTP POST で通知する仕組み。本案件では Shopify の `orders/create`。
- **本案件での文脈**: 注文作成→webhook→pipeline.js が支払区分を判定し、③都度払いのみ MF 請求書を即時作成する（①②は締めバッチへ委譲）。HMAC 検証・即 200 応答・非同期処理・処理済み記録（`output/webhook-processed.json`）による二重発行防止を実装済み（テスト K-05）。
