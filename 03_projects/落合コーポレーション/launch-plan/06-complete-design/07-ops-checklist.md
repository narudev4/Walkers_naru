## 4. 異常時

### 4-1. webhook 失敗を疑うとき（③都度払いの請求書が作られない）

| 手順 | 見る場所 | 判断 |
|---|---|---|
| 1. 処理ログを確認する | Vercel ログ（確認手順は要手順化（未確定））。ローカル検証では `webhook/output/webhook-events.jsonl` | `skip`（処理済み）/ `retryable-error` / `done` のどれか。`retryable-error` の場合、pipeline.js は処理済み記録を解除するため、**再配送が来れば再処理される**（実装済み）。 |
| 2. Shopify 側の配送状況を確認する | Shopify Admin > 設定 > 通知 > webhook（配送履歴） | 配送失敗が続いていないか確認する。Shopify の自動再送仕様と手動再送の手順は**要手順化（未確定・一次情報で裏取りしてから記載する）**。 |
| 3. 再処理する（二重発行リスクは経路による） | — | **ローカル検証環境**: 再配送・再検知は永続ファイル（`webhook-processed.json`）で dedup されるため二重発行の心配なく再処理できる（テスト K-05 で検証する設計）。**Vercel 本番環境**: dedup は**インメモリのみ**（api/webhook.js:49-65）で、コールドスタート・複数インスタンスで記録が消える（04 §1-3）。再処理の前に**必ず MF 側で当該注文の請求書が既に存在しないか確認**し、既存があれば再処理しない。恒久対策（Vercel KV 等への移行）はコード内コメントに明記済みの残課題。 |
| 4. 復旧しない場合 | — | 該当注文の請求書を MF で手動作成する。手動作成の記載ルール（明細・支払期日=請求日+7日）は要手順化（未確定）。 |

### 4-2. MF トークン失効のとき

| 手順 | 見る場所 | 判断 |
|---|---|---|
| 1. 失効を確認する | Vercel ログの MF API エラー（401 等）。検証環境ではトークンは `.mf-tokens.json` に保存 | テスト K-08 の観点（自動 refresh または失敗時の通知）は**運用設計が未完了**。現状コードにはトークン保存の仕組みはあるが、失効時の自動通知は未実装（要手順化（未確定））。 |
| 2. 再認可する | MF の OAuth 認可フロー | **本番は先方の既存 MF アカウントでの認可のため、先方管理者の承認操作が必要**（CONTEXT.md §14・先方お願い事項に計上済み）。再認可の連絡経路・所要時間は要手順化（未確定）。 |
| 3. 失効中に溜まった注文を処理する | §4-1 の手順に準ずる | 処理漏れ注文の洗い出し方法は要手順化（未確定）。 |

### 4-3. 二重発行を疑うとき

| 手順 | 見る場所 | 判断 |
|---|---|---|
| 1. MF 側で重複を探す | MF クラウド請求書 > 請求書一覧（同一の注文番号・期間ラベルで検索） | 同一注文（③）または同一の締め期間+顧客（①②）で2枚以上あれば二重発行。 |
| 2. Shopify 側の記録と突合する | 注文の metafield `b2b.mf_billing_number` / `b2b.mf_invoice_url`（書戻し実装済み・テスト K-03） | 注文に記録された請求書番号が正。それ以外の1枚が余剰。 |
| 3. 実行記録を確認する | ③: `output/webhook-processed.json` ／ ①②: `output/settle-runs.json`（`--force` の実行有無） | 締めバッチの `--force` 再実行は二重作成の典型原因になり得るため、実行記録の billings と MF の下書きを突合する。 |
| 4. 余剰分を処理する | MF クラウド請求書 | 未送付なら下書きを削除、送付済みなら先方・顧客への訂正連絡が必要。**削除・訂正の手順と連絡文面は要手順化（未確定）**。 |
