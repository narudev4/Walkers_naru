## 0. 前提（現行アーキテクチャの要点）

### 掛率カスケード（現行 3 段）

```
最終掛率 = ① 顧客個別 override（顧客 × カテゴリ）   … customer.b2b.custom_overrides
        → ② マトリクス（グループ × カテゴリ）        … discount_matrix Metaobject
        → ③ 正価 1.0（フォールバック）
```

- 実装: `shopify/src/discountEngine.js:52-76`（`resolveRate`）。カテゴリ名・グループ名は一切ハードコードせず、すべてデータとして外部から受け取る設計（同ファイル冒頭コメント 5-12 行）。
- 掛率 rate は 0 < x ≦ 1 の係数（0.60 = 正価の 60%）。不正値（0 以下・1 超・非数）は `normalizeRate`（`discountEngine.js:33-38`）が null を返し、正価 1.0 にフォールバックする。

### 影響列の定義

| 列 | 対応コンポーネント | 主なファイル |
|---|---|---|
| discountEngine | 掛率計算の純粋ロジック | `shopify/src/discountEngine.js` |
| Liquid 表示 | ストアフロントの卸価格表示 | `shopify-theme/snippets/b2b-wholesale-price.liquid`・`b2b-card-price.liquid`・`b2b-cart-checkout.liquid` |
| Draft Order 生成 | カート → 卸単価適用の Draft Order 作成 | `shopify/src/createDraftOrder.js` |
| webhook・MF 請求書 | 注文検知 → MF 請求書作成（③都度払い） | `webhook/pipeline.js`・`moneyforward/src/invoiceService.js`・`mapOrder.js` |
| 締めバッチ | ①20 日締め／②末締めの月次統合請求 | `webhook/settle-batch.js` |
| テスト | `launch-plan/02-test-scenarios.md`（全 99 ケース）のうち再実施・追加が必要な範囲 | — |
| 運用チェック工数 | 落合社スタッフ・運用側の確認作業の増減 | — |

### 評価尺度

- **影響なし**: コード・データ・運用のいずれも変更不要。
- **小**: 1 ファイル内の局所変更、またはデータ追加のみ（半日以内目安）。
- **中**: 複数ファイルの整合変更、または仕様決定を伴う変更（1〜3 日目安）。
- **大**: 新規開発・外部仕様調査・セキュリティ設計を伴う変更（3 日超目安）。

### 未確定事項（本書の前提）

掛率の実値・明細粒度・返品の扱いは**未確定**（demo 値先行）。確定状況の正は真理源スプシ「確認事項」タブ。B2B（業者様向け）の発注入口は (b) カート → Draft Order 方式が現行方針（naru 7/14・古谷さん合意待ち）。

## 2. シナリオ別詳細

### 2-1. 商品ごとの掛け率を追加（本丸・最重要）

**背景**: 古谷さんの FB「商品ごとの掛け率を追加するとチェックが増える懸念」。現行 cascade は「顧客 × カテゴリ」の override（`custom_overrides`）までで、**商品単位の掛率は存在しない**。

**エンジン変更は小、が結論**。根拠:

- `resolveRate`（`discountEngine.js:52-76`）は優先順位付きの単純な if 連鎖であり、①の上（または①と②の間）に「商品個別レート」の判定を約 10 行追加するだけで済む。値の検証は既存の `normalizeRate`（`discountEngine.js:33-38`）をそのまま流用でき、不正値は従来どおり正価 1.0 フォールバックに落ちる。
- Draft Order 側は `VARIANTS_Q`（`createDraftOrder.js:27-34`）の product 部に metafield を 1 フィールド追加し、`computed` の計算（`createDraftOrder.js:98-106`）で `resolveRate` に渡すだけ。カート側スニペット（`b2b-cart-checkout.liquid:138-146`）は variantId と数量しか送っておらず価格計算はすべてサーバ側のため、**カート UI は無変更**。
- webhook・MF 請求書・締めバッチは**影響なし**。パイプラインは掛率を再計算せず、確定単価（`wholesale_unit_price` — `mapOrder.js:92`、締めバッチは注文の `discountedUnitPriceSet` — `settle-batch.js:148`）を消費するだけの構造だから。

**注意が必要なのは実装の重複**。カスケードロジックはエンジン以外に、表示側の `b2b-wholesale-price.liquid:15-25`（商品詳細）・`b2b-card-price.liquid:28-41`（商品カード）の 2 ファイル、さらに**本番 B2B 発注経路の `webhook/vercel-deploy/api/create-draft-order.js:140-158`（独自 `findRate`。discountEngine を import せず再実装）** に重複しており、層を追加する場合は **4 箇所**（エンジン + Liquid 2 本 + Vercel Function）を同期変更する必要がある。変更のたびにテスト H-09（Liquid とエンジンの価格一致検証）を必ず回すことをルール化する。

**変更手順の概略と工数感**:

1. データ設計: 商品個別レートの持ち方を決める（案 A: Product metafield `b2b.product_rate` = 全顧客共通の商品レート ／ 案 B: 顧客 metafield の override を「カテゴリ」から「商品ハンドル」キーにも拡張 = 顧客 × 商品）。案 A なら組合せは商品数のまま、案 B なら商品 × 顧客に爆発する。**どちらを求めているかの要件確認が先**。— 0.5 日
2. `resolveRate` に 1 層追加 + ユニットテスト追加。— 0.5 日
3. `createDraftOrder.js` の取得クエリ拡張。— 0.5 日
4. Liquid 2 ファイルへの同一層追加 + H-09 整合確認。— 0.5〜1 日
5. テスト再実施（T-H 9 + T-I の I-03/I-04 + 新規 4 前後 ≒ 15 ケース）。— 1 日

コード変更の実装工数は**合計 3〜4 日程度**。ここまでは小さい。

**古谷さんの懸念（チェック工数増）への返し方**:

懸念は正しい。増えるのはコードではなく**運用**であり、案 B（顧客 × 商品）の場合、掛率設定の組合せが「グループ × カテゴリ（数十）」から「商品 × 顧客（数百〜数千）」に増え、設定ミス（掛率の入れ忘れ・桁違い・カテゴリ矛盾）を人の目で検知するのは非現実的になる。

そこで**「掛率設定の自動検証スクリプト」をセット提案**する:

- `resolveRate` は Admin API 非依存の純粋関数（`discountEngine.js:3` 設計コメント）なので、全顧客 × 全商品の実効掛率を**オフラインで一括計算**できる。さらに `createDraftOrder.js` には `dryRun` モード（`createDraftOrder.js:73,113`）が既にあり、実注文を作らず計算結果だけ取り出す口も実装済み。
- 検証内容: (a) 不正値（0 以下・1 超・非数）の検出、(b) 商品個別レートがグループレートより高い/低い逆転の警告、(c) override に存在しないカテゴリ・商品キーが残っている孤児設定の検出、(d) 全組合せの実効掛率一覧を CSV/スプシに出力し、前回実行との差分を表示。
- 運用: 掛率を変更したら（または夜間 cron で）スクリプトを回し、異常だけを通知する。**「チェックが増える」を「チェックは機械がやる」に置き換える**のが回答の骨子。スクリプト自体の開発は既存部品の組合せで 1〜2 日規模。

**運用リスク**: 案 B 採用時、override JSON の手書き運用が続くと入力ミス率が上がる。中期的には設定用の簡易 UI（スプシ → metafield 反映スクリプト）まで視野に入れる。

### 2-2. 新カテゴリ追加（例: パデル用品）

**設計上コード変更不要**であり、これは実機検証済みの結論。根拠:

- `discountEngine.js:5-12` の設計コメントに明記されたとおり、カテゴリ名・グループ名はすべてデータとして外部から渡され、モジュール内にハードコードが無い（`resolveRate` は文字列一致比較のみ — `discountEngine.js:62,68`）。
- 実装仕様書（`design/implementation-spec.md` 検証結果の節）に「新カテゴリ追加: コード変更なし（matrix 行追加のみ）」が Draft #D3〜#D11 の実機検証結果として記録済み。
- matrix に行が無いカテゴリの商品は正価 1.0 フォールバック（`discountEngine.js:74-75`・source:'default'。カテゴリ metafield 自体が未設定の場合は `:57-60`・source:'no-category'）なので、matrix 行の投入が商品登録より遅れても価格事故にならない（卸価格が付かないだけ）。

**作業**: ① discount_matrix Metaobject に「新カテゴリ × 全グループ」の行を追加、② Product metafield `b2b.category` に新カテゴリ値を設定、③ 自動コレクションの条件追加（B2C 側の見せ方）。テストは H-06 相当のスモーク 2〜3 ケース。

**留意（未検証）**: Liquid 側は `shop.metaobjects.discount_matrix.values` を全件ループしている（`b2b-wholesale-price.liquid:19`）。**Liquid から参照できる Metaobject エントリ件数の上限は未検証**のため、グループ・カテゴリ追加で行数が増える前に上限を確認する（Admin API 側は `first: 250` を明示 — `createDraftOrder.js:38`）。

### 2-3. 新顧客グループ追加（D グループ等）

カテゴリ追加と同型で**コード変更不要**。`resolveRate` のグループ判定は matrix エントリとの文字列一致のみ（`discountEngine.js:67-73`）、Liquid 側も同じ（`b2b-wholesale-price.liquid:20`）。

**作業**: ① matrix に「D × 全カテゴリ」の行を追加（現行カテゴリ構成なら約 18 行）、② 対象顧客の `b2b.discount_group` を "D" に設定。実装仕様書に「グループ一括変更: A→B→A で即追従」の検証記録あり。テストは corp-d テストアカウントを作り H-01/H-03 相当を 3〜5 ケース。

**留意**: Admin API の matrix 取得は `first: 250`（`createDraftOrder.js:38`）。グループ × カテゴリの行数が 250 を超える規模拡大（例: 10 グループ × 25 カテゴリ）ではページネーション対応が必要になるが、現実的な運用規模では当面問題にならない。

### 2-4. 掛率の値変更（一括・個別）

**純粋なデータ変更でコード影響なし**。表示（Liquid）と Draft Order（エンジン）は毎回ライブでデータを読むため即時反映され、この整合はテスト H-08（グループ変更の即時追従）・H-09（matrix セル変更が表示と Draft Order 双方に反映）で検証枠が既に用意されている。

**重要な挙動**: 掛率変更は**過去の注文・作成済み請求書に遡及しない**。締めバッチは注文時点で確定した `discountedUnitPriceSet` を読む（`settle-batch.js:148`）ため、締め期間の途中で掛率を変えても、変更前の注文は旧掛率のまま請求される。これは会計上正しい挙動だが、「期間途中の変更は同一請求書内に新旧掛率が混在する」ことを運用側が理解しておく必要がある。

**運用リスク**: 一括変更時の入力ミス（桁違い・行ズレ）。ここでも §2-1 の自動検証スクリプト（変更前後の差分一覧出力）が効く。なお掛率の実値自体が未確定（demo 値先行）のため、**実データ投入時がこのシナリオの初回実行**になる。

### 2-5. 締め日変更（20 日/末日 → 15 日/25 日等）

影響は**締めバッチに集中**する。根拠:

- 締め区分は `'20th' | 'eom'` の 2 値 enum としてバリデーションされ（`settle-batch.js:37-40`）、期間・支払期日の計算 `computePeriod` も両値の分岐がハードコード（`settle-batch.js:52-78`。20th = 前月 21 日〜当月 20 日・翌月 20 日払い、eom = 当月 1 日〜末日・翌月末払い）。新しい締め日は**この関数への分岐追加 + enum 拡張**が必要（局所変更・1 ファイル内で完結）。
- 顧客側は metafield `b2b.payment_terms` の値を新値に変更。webhook パイプラインは「IMMEDIATE_TERMS（既定 prepaid,immediate）に**含まれない値はすべてかけ払い**」と判定する（`pipeline.js:94-104`）ため、新しい term 値も自動的にかけ払い扱いで素通りする（パイプライン変更不要）。
- MF 側は影響なし: 支払期日は締めバッチが `due_at` を明示して渡し、mapOrder はそれを優先使用する（`mapOrder.js:104`）。
- cron スケジュール（実装仕様書 T1-6: 20 日/末日 23:59 JST）の変更も忘れずに。

**工数感**: コード変更は 0.5〜1 日 + T-L 8 ケース再実施で計 2 日程度。

### 2-10. B2B（業者様向け）顧客の途中グループ変更・個別 override 追加

**運用上の重要挙動 2 点**:

1. **遡及しない**: 変更前に確定した注文の単価はそのまま。締めバッチは注文時点の `discountedUnitPriceSet` を読む（`settle-batch.js:148`）ため、締め期間の途中でグループを変えると、**同一の統合請求書内に旧掛率の注文と新掛率の注文が混在**する。会計上は正しいが、先方（宏樹様・ぽぽ様側の運用担当）が「請求書内で同じ商品の単価が違う」問い合わせを受け得るため、変更は締め直後に行う運用推奨をマニュアルに書く。

### 2-12. 部分発送・分納への対応（発送済み明細のみ請求）

**背景（現状の挙動）**: 締めバッチの対象判定は**注文単位**。fulfillment の**いずれか1つでも**締め期間内にあれば、その注文の**全明細（未発送分を含む）**を請求対象にする（`settle-batch.js:119-123` の filter と `:145-152` の明細展開が独立しており、明細と fulfillment を紐づけていない）。明細行の日付も先頭 fulfillment の日付で固定（`settle-batch.js:146`）。

このため部分発送（分納）の注文では次の 2 つの事故が起きる:

1. **未発送明細の先行請求**: 期間内に一部だけ発送した注文でも、未発送分を含む全明細が請求される（決定4「請求確定=発送時」と明細レベルでは不整合）。
2. **期間跨ぎの二重請求**: fulfillment が 2 つの締め期間に分かれた注文は、`shipped.some(...)` の判定が両方の期間で真になるため、**両方の締めで全明細が請求される**。実行記録（settle-runs.json）は term:closing 単位で、注文単位の請求済みマークが無い。

**変更範囲**: `settle-batch.js` に集中（1 ファイル内）。(a) orders クエリに fulfillment の lineItems（FulfillmentLineItem）を追加し、(b) 明細構築を「期間内の fulfillment に含まれる明細 × 発送数量」ベースへ変更、(c) 日付も各 fulfillment の日付を使う。③都度払い側は注文作成時点（発送前）に全明細で請求書を作る現行仕様のため部分発送の概念自体が無いが、「発送前に請求してよいか」は仕様確認の論点として残る。

**工数感**: 1〜2 日 + 境界テスト 4〜6 ケース。ただし現行の落合社運用で分納が実際に発生するかが先決の確認事項（発生しないなら「分納運用をしない」の運用ルール化で足りる）。**対応までの暫定運用**: 部分発送・複数 fulfillment の注文は S-2（月2回の下書き確認）で個別突合する。

## 3. 横断的な所見（全シナリオ共通）

1. **カスケードロジックが 4 実装に重複している**: `discountEngine.js`（正）+ `b2b-wholesale-price.liquid:15-25` + `b2b-card-price.liquid:28-41` + **`webhook/vercel-deploy/api/create-draft-order.js:140-158`（本番 B2B 発注経路の独自 `findRate`）**。掛率ルール自体を変えるシナリオ（#1 が典型）では 4 箇所の同期変更が必須で、乖離すると「表示価格と請求価格が違う」という最悪の事故になる。ルール変更を含むリリースでは**テスト H-09（Liquid とエンジンの整合）を必須ゲート**にする。**さらに検証ロジックも既に乖離している**: 正の discountEngine は `normalizeRate` で 0 < rate ≦ 1 以外（負値・0・1 超・非数）を弾いて正価 1.0 にフォールバックする（`discountEngine.js:33-38`）が、Vercel 版 `findRate` と override 適用は `parseFloat(...) || 1.0` のみで**範囲検証が無く、負値がそのまま採用される**（`create-draft-order.js:140-150, 223-227`）。負の rate は `rate < 1.0` 判定（:235-240）を通過して割引率 100% 超の appliedDiscount を生成し得る。matrix・override に不正値が入っても正には守られ、本番発注経路には守られないという非対称であり、§2-1 の自動検証スクリプト（07 M-1 に組込み）で 0 < rate ≦ 1 をデータ側で担保するまでは Vercel 版に同じ検証を移植するのが安全。
2. **Liquid の Metaobject 参照件数上限は未検証**: `shop.metaobjects.discount_matrix.values` の全件ループ（`b2b-wholesale-price.liquid:19`）が何行まで返すかは確認していない。行数が増えるシナリオ（#2・#3）の実施前に実機確認する。Admin API 側は `first: 250` が明示上限（`createDraftOrder.js:38`）。
3. **締めバッチの注文取得はプロトタイプ実装**: 直近 100 件を取得してフィルタする方式（`settle-batch.js:93-95` に「プロトタイプ」と明記）。注文量が月 100 件を超える前にページネーション（または期間クエリ）対応が必要で、これはどのシナリオとも独立した本番化の共通課題。
4. **「エンジンは変えやすく、運用は増えやすい」構造**: 掛率系の変更はエンジンが純粋関数 + データ駆動のためコード工数が小さく出る一方、増えるのは設定データの組合せ管理（= 運用チェック）。したがって仕様変更 FB への標準回答は「実装は N 日 + **検証の自動化をセットで**」であり、§2-1 の自動検証スクリプトは #1 専用ではなく #4・#10 にも効く共通投資として提案する。
5. **明細取得が `lineItems(first: 50)` 固定**: `shopify/src/orderNormalize.js:26-32`・`webhook/vercel-deploy/lib/orderNormalize.js:29-35`・`settle-batch.js:105-110` の 3 実装ともページング無しで、**1 注文 51 行以上の明細は黙って請求から漏れる**。業者様向け（B2B）のまとめ買いで現実に起き得る規模のため、大量明細の注文が想定されるなら本番前にページング対応（または行数超過の検知）が必要。暫定は 07 D-1／S-2 の目視検知。
