# 【報告】かけとこ ドメイン構成の検討結果（8/19 定例前の共有）

- 作成: 細谷（2026-08-13）。
- 対象: 古谷さん向けの事前報告。宿題「ドメイン構成の最適案（UX×SEO、リバースプロキシ統合の技術調査含む）」の結論。
- 検証体制: 実測調査（8/5）＋ 実コード確認（8/12、野呂さんからリポジトリ招待をいただき読み取りのみ実施）＋ 独立レビュー 3 本（AI レビュアー 3 系統で相互検証）。

---

## 1. 結論（3 行）

1. **ドメイン構成は今のまま変えないのが最適です**（kaketoco.com＝アプリ、shop.kaketoco.com＝Shopify）。リバースプロキシでの統合は推奨しません。
2. 定例で懸念になっていた「評価の分散」は、**shop 側を noindex にして、コンテンツ（商品情報・ブログ）を全部 kaketoco.com 側に載せる**ことで解消します。ブログは Shopify の管理画面で書いたものを kaketoco.com/magazine として配信できます。
3. ただしコードを確認した結果、**「検索エンジンに公開する準備」に穴が 3 つ**見つかりました。公開前に塞ぐ必要があります（後述）。

---

## 2. なぜ「ドメイン統合」をやらないのか

定例では「サブドメインは別サイト扱いで評価が分散する → 単一ドメインに集約」という方針でした。この**目的自体は正しく、案の中身だけを差し替えます**。

SEO の評価はドメインの数ではなく「検索対象のコンテンツと被リンクがどこに載るか」に付きます。分散が起きるのは両方のホストに検索対象コンテンツがあるときです。今回の推奨案では検索エンジンから見える世界がこうなります。

| コンテンツ | 置き場所 |
|---|---|
| 農薬ページ 3,248 件（購入ボタン付き＝実質の商品ページ） | kaketoco.com |
| ブログ（マガジン） | kaketoco.com/magazine |
| トップ・サービス説明 | kaketoco.com |
| shop.kaketoco.com に残るもの | **レジ機能だけ（noindex で検索対象外）** |

レジページはどの EC でも検索評価の対象外なので、**評価は 100% kaketoco.com に集まります**。「Shopify をアプリの配下に入れた」のと同じ状態が、URL を動かさずに実現できる、という整理です。

### リバースプロキシ案（Shopify をルートに）を推奨しない理由

- Shopify が公式ヘルプで「Cloudflare プロキシ構成（O2O）はサポートしない」と明言しており、SSL 証明書の自動更新が壊れる故障モードまで具体的に警告しています。Cloudflare 側は「できる」とガイドを出しており、**両社の公式見解が食い違っています**。動くかどうかより「壊れたとき誰も直せない」ことが EC では致命的です。
- 実測の結果、現構成に Cloudflare は入っていません（DNS は Google Cloud DNS、Shopify へは直結）。この案は設定変更ではなく「Cloudflare の新規導入＋DNS 移管＋ルートの載せ替え」という大工事になります。
- ルートが Shopify ストアになるため、上野様の「kaketoco.com はアプリであってほしい」というご要望と正反対になります。

### 逆方向（Shopify をアプリ配下の /shop に）も不成立

Shopify 公式の仕組み（App Proxy）は Cookie を強制的に除去する仕様のため、ログインとカートが動きません。また Shopify のレジはどの構成でも自社ドメインのサブディレクトリには置けません。

## 3. ブログ（古谷さんのご要望）の実現方法

「Shopify のブログ機能で書きたい」はそのまま実現できます。**編集は Shopify 管理画面のまま、配信だけをアプリ側が API で取得して kaketoco.com/magazine として表示**します。記事の見た目はアプリ側で統一でき、SEO 評価も kaketoco.com に載ります。

実装時の注意（コード確認で判明。開発チームへの引き継ぎ事項）。

- アプリが使っている Shopify API のバージョンが古く（2024-01）、サポート切れです。記事取得の前にバージョン更新と既存機能の動作確認が要ります。
- 記事に YouTube を埋め込む場合、アプリ側のセキュリティ設定（CSP）に YouTube の許可を足さないと動画が表示されません（マーケ施策で YouTube 埋め込みを想定しているため重要です）。
- 記事 HTML をそのまま表示すると XSS の穴になるため、サニタイズ（無害化処理）が必須です。

## 4. コード確認で見つかった「公開前に塞ぐ穴」

野呂さんチームの設計は方向性が正しく、公開切り替えの仕組み（環境変数フラグで robots を開放、事故防止の安全弁つき）はすでに実装済みでした。そのうえで、レビューで以下が見つかっています。

### 必須（robots 開放の前に）

1. **農薬 3,248 ページが「孤児」状態です。** トップから農薬ページへ辿れるリンクが HTML 上に 1 本もなく（検索結果は JS 実行後にしか出ないため Google からは見えません）、robots を開けるだけではインデックスが進みません。**作物別・成分別などの一覧ページ（サーバー描画）を最低 1 系統新設する必要があります**。今回の検討で一番大きい発見で、唯一のまとまった追加開発です。
2. **成分別・RAC 別などの絞り込みページ 4 本が、低品質 URL を無限に生む状態です。** 農薬ページからリンクされているのに、受け側に検索エンジン向けの設定が何もありません。公開前に noindex を付けます（小さい修正です）。
3. **robots の除外リストに記述ミスがあります。**（`/cart/` という書き方は `/cart` にマッチしない等。＋ログイン必須ページの列挙漏れ）。1 ファイルの修正です。

### 手順の順序

**shop 側の noindex を先に入れてから、アプリの robots を開放**します（逆にすると、指名検索「かけとこ」で shop だけが出続ける期間ができます）。shop のテーマもリポジトリで管理されているので、1 行追加と反映だけです。

## 5. 8/19 の定例で決めたいこと（3 点）

1. **農薬以外の商品（園芸資材など）の検索流入を捨てるか。** shop を noindex にすると、農薬以外の商品は検索結果から消えます。農薬はアプリ側のページが受け皿になるので影響ありませんが、園芸資材には受け皿がありません。→ まず「農薬に紐付かない商品が何点あるか」を確認し、少数なら割り切り、主力級なら受け皿ページを後日設計、の二択です。
2. **農薬ページの URL を今の形（英数字の ID）のまま公開してよいか。** 農薬名入りの URL への変更は検討しましたが、リリースを止めてまでやる価値はないと判断しています（順位への効果は小さく、後日の変更コストも低いことを確認済みです）。
3. **カート→レジの遷移を同一タブにするか。** 上野様の「別タブが開いて使いにくい」の原因を特定しました。確認ダイアログ＋別タブを開く共通部品が原因で、意図的な設計です。レジだけダイアログなし・同一タブにし、外部リンクは現状維持、という出し分けを提案します。

## 6. 訂正・補足（過去の議論との差分）

- 定例で参考にした「freee はルートを白紙にして LP へリダイレクト」は実測すると事実と異なりました（freee のルートはサービス紹介ページで、アプリは別サブドメインです）。この例を根拠に使うと「ルート＝LP」という上野様のご要望と逆の結論になるため、8/19 では引かない方が安全です。
- ドメインの綴りは kaketoco.com（toco）です。tl;dv の議事録に kaketoko 表記が残っているため、資料類は要修正です。
- リポジトリは野呂さんの招待を受けて**読み取りのみ**行いました。コードの変更・PR は一切していません。

## 7. 想定問答（naru 用の準備メモ。古谷さんに見せても可）

### Q1.「サブドメインは別サイト扱いで評価が分散するって話だったよね。noindex で本当に解決するの？」

A. 分散が起きるのは「両方に検索対象コンテンツがあるとき」です。noindex 後は検索対象が kaketoco.com だけになるので、集約の目的は達成されます。Google の公式仕様でも、サイト名の認識はドメイン/サブドメイン単位なので、放置すると shop が「別サイト」として指名検索に出るリスクがあり、noindex はそれを消す手段でもあります。

### Q2.「リバースプロキシ、WordPress ではできると調査した。なぜ Shopify はダメ？」

A. できる・できないで言えば「動く可能性はある」です。ただ Shopify 自身が公式に非サポートを明言し、SSL 更新が壊れる故障モードを警告しています。WordPress は自分のサーバーなので壊れても自分で直せますが、Shopify は先方のインフラで、壊れたときにサポートを受けられない構成に EC の決済を載せるのはリスクに見合いません。しかも現構成に Cloudflare 自体が入っておらず、導入からやる大工事になります。

### Q3.「ブログは Shopify で書きたいんだけど、それは変わらない？」

A. 変わりません。書く場所は Shopify 管理画面のままで、表示だけをアプリ側が API で取得して kaketoco.com/magazine に出します。むしろテーマの制約から自由になり、見た目をアプリと統一できます。

### Q4.「robots を開ければ SEO は始まるんでしょ？」

A. ここが今回の一番大きい発見で、始まりません。農薬ページへのリンクが HTML 上に 1 本もない「孤児」状態なので、一覧ページ（サーバー描画）の新設が必要です。逆に言うと、ドメインをどういじってもこれを作らない限り効果が出ません。

### Q5.「追加の開発工数はどれくらい？リリースに影響する？」

A. 必須項目のうち 2 つ（robots 修正・noindex 付与）は小さい修正です。まとまった開発は「一覧ページの新設」と「/magazine の実装」の 2 つで、これは中規模です。リリース自体を止める必要はなく、「robots を開ける（＝検索エンジンに公開する）タイミング」までに揃っていればよい、という整理ができます。サービス公開と検索公開は別々に切れる設計になっています。

### Q6.「園芸資材が検索から消えるのは困るのでは？」

A. だから 8/19 の判断事項に入れています。まず非農薬商品の点数を数えるのが先で、少なければ割り切り、多ければ受け皿ページをフェーズ 2 で作ります。中間の手当として、農薬に対応する商品 URL はアプリ側の農薬ページへ転送する小さい修正もあります。

### Q7.「今すでに shop が Google に載っているけど、どうなる？」

A. noindex を先に入れてからアプリを公開する順序にすれば、shop の掲載は徐々に消え、入れ替わりでアプリ側が載っていきます。移行期は Search Console（ドメインプロパティ）で両方の推移を監視します。

### Q8.「3,000 ページ以上を一気に公開して、質の低いページ扱いされない？」

A. リスクとしては認識しています。対策は 2 つで、(1) 農薬ページには適用表・独自指標など実データが載っており「薄い自動生成ページ」ではないこと、(2) 上野様の農薬解説（数十本）を個別ページに統合してテキストの厚みを足すこと。解説の取り込み（既存 NA）が SEO 面でも効く、という接続になります。

### Q9.「レジが shop.kaketoco.com になるのは変えられないの？」

A. 変えられません（Shopify の仕様で、どのドメイン構成を選んでも同じです）。ただし同一ドメイン配下なので Cookie・計測は共有できており、実害は薄いです。ダイアログを挟まず同一タブで遷移させる改善で体感は大きく変わります。

### Q10.「この結論、誰がどう検証したの？」

A. 8/5 に DNS・HTTP の実測調査、8/12 に野呂さんの招待でコードを直接確認（読み取りのみ）、さらに独立した AI レビュー 3 系統（うち 1 つは結論を否定する役割）で相互検証しました。3 者とも「構成は現状維持」で一致し、相違点はスラッグ化の是非だけでした（→ 見送りで裁定）。

### 弱点として正直に持っておくこと（聞かれたら認める）

- 「noindex ページのリンクは長期的に辿られなくなる」という Google 側の挙動があり、shop 経由でリンク評価を流す設計は使えません。ただし今回の案は shop からの評価流入に依存していないので実害はありません。
- shop の掲載が検索結果から消えるまでの期間は Google 次第で確約できません（数日〜数週間）。
- 一覧ページ新設の具体的な工数は開発チームの見積もりが必要です（こちらで断定できるのは「必要である」ことまでです）。
