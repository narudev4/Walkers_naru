# カケトコ（kaketoco.com）ドメイン構成調査 — UX × SEO の最適解

- 調査日: 2026-08-05
- 調査: 株式会社Walkers 細谷
- 提示先: 上野園芸社 古谷様（PM）・野呂様（テックリード） / 2026-08-19 定例
- 対応 NA: NA-20260805-001
- 目的: 自社開発システム（Vercel）と Shopify（shop.kaketoco.com）のドメイン構成を、UX と SEO の観点から確定させる

> **ドメイン名の訂正**: tl;dv の AI 要約には `kaketoko.com` とありますが、**正しくは `kaketoco.com`（"toco" 綴り）** です。`kaketoko.com` は .com に登録が存在しません（DNS で NXDOMAIN を確認）。本書は実在する `kaketoco.com` を実測して書いています。

本書では **【事実】** = 一次情報・実測で裏が取れたもの、**【二次情報】** = 出典はあるが検証が不十分なもの、**【判断】** = 調査者（細谷）の推測・推奨、を明示的に区別しています。

## 0. エグゼクティブサマリー

1. **最優先事項はドメイン構成ではありません。`kaketoco.com/robots.txt` が `User-Agent: * / Disallow: /` になっており、アプリ全体が全クローラーから遮断されています。** 一方で `shop.kaketoco.com`（Shopify）は普通にクロール可能で noindex も入っていません。**目的（アプリを指名検索トップに、Shopify は隠す）と現状が完全に逆転しています。** リリース時にこれを外し忘れると、上野様の要望は構造的に達成不可能になります。

2. **アプリ側の sitemap.xml には 3,247 件の URL が登録されており、その大半が `/pesticides/{UUID}` 形式の農薬個別ページです。** これは長尾キーワードを取りにいける本命の SEO 資産ですが、現在は 1 件もインデックスされ得ません。**ドメイン構成をどう組み替えるかより、この 3,247 ページを開放することのほうが桁違いに効きます。**

3. **古谷様の仮説「Shopify をルートに置き、Cloudflare のリバースプロキシで自社システムをサブディレクトリにねじ込む」は推奨しません。** Cloudflare は Shopify 向け O2O を公式サポートすると書き、Shopify は公式に「サポートしない」と書いており、**両社の公式ドキュメントが真っ向から食い違っています**。加えて実測の結果、**現構成に Cloudflare は一切入っていません**（権威 DNS は Google Cloud DNS、Shopify へは A レコード直指し）。この案は「設定を変える」話ではなく「稼働中のスタックに Cloudflare を新規導入し、apex ドメインを Vercel から Shopify に移す」話であり、MTG で想定されていたより大幅に重い変更です。

4. **逆パターン（Shopify を自社ドメインのサブディレクトリに）も Shopify 公式の App Proxy では成立しません。** App Proxy は `Set-Cookie` / `Cookie` ヘッダを除去する仕様で、ログイン・カートを持つアプリを通せません。URL も `/apps` `/a` `/community` `/tools` の 4 プレフィックス限定です。

5. **推奨は案 C です。ドメイン構成は現状のまま一切変えず、(a) robots.txt を開放し、(b) Shopify 側を noindex にし、(c) ブログを Storefront API 経由で `kaketoco.com/magazine` として自社側で配信する。** アプリが Next.js on Vercel であること、Storefront API 連携が既にあることを実測で確認済みなので、いずれも既存スタックの延長線上で実装できます。

6. **Hydrogen / Oxygen 移行は却下を推奨します。** カケトコの価値の中心は農薬検索・混用可否チェックという独自ロジックで、Hydrogen に載せ替えても増えません。実質全面書き直しになります。

7. **上野様の「別タブが開いて UX が悪い」という不満は、ドメイン構成とは別問題の可能性が高いです。** カート→レジのリンクが `target="_blank"` になっているだけなら、外すだけで解決します。議論の前にここを潰すべきです。

## 1. 実測で確認した現況（2026-08-05）

【事実】以下はすべて 2026-08-05 に DNS 照会と HTTP リクエストで直接確認した実測値です。

### 1.1 DNS

| 対象 | 実測結果 |
|---|---|
| `kaketoco.com` NS | `ns-cloud-b1〜b4.googledomains.com`（**Google Cloud DNS**） |
| `kaketoco.com` A | `216.150.1.1` |
| `www.kaketoco.com` | CNAME → `24de5ca7b50153fd.vercel-dns-016.com` → `216.150.1.193` / `216.150.16.193`（**Vercel**） |
| `shop.kaketoco.com` A | `23.227.38.69`（**A レコード直指し**。CNAME ではない） |

【事実】**Cloudflare は現構成に一切使われていません。** 権威 DNS は Google Cloud DNS で、上野園芸社側の Cloudflare ゾーンは存在しません。`shop.kaketoco.com` のレスポンスに現れる `cf-cache-status` / `nel` ヘッダは **Shopify 自身が使っている Cloudflare**（O2O でいう 2 つ目のゾーン）であり、上野園芸社側のものではありません。

### 1.2 `kaketoco.com`（自社アプリ）

【事実】HTTP レスポンスヘッダから確認できたこと:

- `server: Vercel` / `x-powered-by: Next.js` / `x-nextjs-prerender: 1` / `x-nextjs-stale-time: 300` / `x-vercel-cache: HIT`
  → **Next.js on Vercel で、ISR（増分静的再生成）が稼働している**
- `content-security-policy` の内容が構成を雄弁に語っています:
  - `connect-src` に **`https://*.myshopify.com`**（→ Storefront API を叩いている強い証拠）、`https://api.stripe.com`、`https://www.jma.go.jp`（気象庁）、`https://maps.googleapis.com`
  - `img-src` に `https://cdn.shopify.com`（Shopify の商品画像を直接表示）
  - `frame-src` に `https://js.stripe.com`、`https://hooks.stripe.com`
  - GTM・GA4・Microsoft Clarity が導入済み

【事実】ページの `<head>`:

- `title`: `カケトコ - AI農薬検索アプリ｜作物・病害虫から最適な農薬を検索`
- `description`: `農家・園芸事業者向けのAI農薬検索アプリ。作物・病害虫・使用方法から登録農薬を検索し、カケトコスコアでおすすめ順に表示します。有効成分や系統（RACコード）が一致する農薬、希釈倍率・使用回数・収穫前日数などの適用情報も確認できます。`
- `canonical`: `https://kaketoco.com`（自己参照。適切）
- `og:title` / `og:url`: 設定済み
- **`<meta name="robots">`: なし**

【事実】構造化データ（JSON-LD）は**実装されています**。ページ全文（`<body>` 内を含む）で計測した結果:

| ページ | JSON-LD ブロック | `@type` |
|---|---|---|
| トップ `/` | 1 件 | `WebApplication`（`name: カケトコ`、`alternateName: kaketoco`、`applicationCategory: BusinessApplication`、`inLanguage: ja`、`isAccessibleForFree: true`、運営者として「有限会社上野園芸社」を記載した description） |
| 農薬個別ページ `/pesticides/{id}` | 2 件 | `WebApplication` + `Audience` + `Organization` / `Product` + `Brand` + `PropertyValue`×4 + `BreadcrumbList` + `ListItem`×2 |

【判断】**構造化データの実装品質はむしろ良好です。** 農薬個別ページに `Product` と `BreadcrumbList` が入っているのは適切です。残る論点は 1 点だけで、**トップページが宣言しているのは `WebApplication` であって `WebSite` ではない**ことです。Google の「Site Names in Google Search」がサイト名の宣言に指定しているのは `WebSite` 型で、`WebApplication` は `SoftwareApplication` の下位型であり `WebSite` の下位型ではありません。**サイト名を確実に伝えるには `WebSite` を併記するのが安全**です（`alternateName: kaketoco` は既に入っているので、表記ゆれの追加は容易です）。

【事実】**`https://kaketoco.com/robots.txt` の全文**:

```
User-Agent: *
Disallow: /
```

【事実】`https://kaketoco.com/sitemap.xml` は HTTP 200 を返し、**`<loc>` が 3,247 件**含まれます。中身はトップページ（priority 1）と、`https://kaketoco.com/pesticides/{UUID}` 形式の農薬個別ページ（priority 0.7、changefreq monthly）が大半です。

【事実】`https://kaketoco.com/magazine` と `https://kaketoco.com/blog` はいずれも **404**（未実装）。

【事実】404 の扱いを実測した結果は次のとおりです。

| パス | ステータス | サイズ |
|---|---|---|
| `/consult`、`/alert`、`/magazine`、`/zzz-not-exist-9x8y7z` | **404** | 46,856 バイト（共通の 404 ページ） |
| `/pesticides/{実在ID}` | 200 | 153,577 バイト |
| **`/pesticides/{不正なID}`** | **200** | 88,055 バイト |

【事実】存在しないパスは正しく HTTP 404 を返します。一方 **`/pesticides/` 配下だけは、存在しない ID でも HTTP 200 を返します**（`x-matched-path: /pesticides/[id]`）。そのページの `<title>` は `農薬が見つかりません | カケトコ` で、**`<meta name="robots" content="noindex">` が付与されており canonical はありません**。

【判断】これは厳密には soft 404（実体がないのに 200 を返す状態）ですが、**`noindex` が入っているためインデックスされる事故は防がれています。** 残るコストはクロールバジェットの浪費だけで、緊急度は高くありません。とはいえ `/pesticides/` は 3,247 ページを抱える名前空間なので、**ステータスコードを 404 に変更しておくのが本来の姿**です。robots.txt を解放してクロールを許可するタイミングで併せて直すのが効率的です。

【判断】**sitemap.xml を出力しているのに robots.txt で全面 Disallow している**のは整合していません。ステージング用の設定が本番に残っているか、リリース前の意図的な遮断のどちらかです。前者なら事故、後者なら「いつ外すか」が決まっている必要があります。**野呂様への最優先の確認事項**です。

### 1.3 `shop.kaketoco.com`（Shopify）

【事実】

- レスポンスヘッダに Shopify 固有のもの多数（`x-dc: gcp-asia-southeast1`、`shopify-complexity-score`、`shopify-digital-wallet`）
- ストアは**公開稼働中**。パスワード保護なし。ストア名「カケトコ」、農薬・園芸資材の通販として 12 商品以上を表示（アクタラ顆粒水溶剤、プレバソンフロアブル5、アニキ乳剤ほか。価格帯 850円〜11,000円）

- `robots.txt` は Shopify のデフォルト（`Disallow: /cart/`、`/checkout`、`/orders`、`/admin` 等）で、**`Sitemap: https://shop.kaketoco.com/sitemap.xml` を宣言**

【事実】Shopify が発行する Cookie の一部が **`domain=kaketoco.com`**（親ドメイン）で設定されています（`_shopify_y`、`_shopify_s`）。

【判断】これは見逃せない利点です。**`shop.kaketoco.com` という同一登録ドメイン配下の構成のおかげで、アプリとストアの間でクロスサブドメインの計測・識別が既に成立しています。** Shopify を別ドメイン（`*.myshopify.com` など）に追い出すと、この利点を失います。現状のサブドメイン配置は、決済導線としては良い設計です。

## 2. 問い別の調査結果

### Q1. Shopify をルートに置き、Cloudflare リバースプロキシで自社アプリをサブディレクトリ配信する構成は実用に耐えるか

#### 結論

【判断】**技術的には成立しうるが、採用を推奨しません。** 理由は技術的不可能性ではなく、**ベンダー間のサポート方針の衝突**と、**現構成からの乖離の大きさ**です。

#### Shopify 公式のスタンス（明確に「非サポート」）

【事実】Shopify ヘルプセンター「Troubleshooting issues with domains connected to Shopify」より:

> "Orange-to-Orange (O2O): O2O is a Cloudflare configuration where a merchant's own Cloudflare zone sits in front of Shopify's Cloudflare zone."

> "Shopify doesn't support the setup of services such as Cloudflare DNS and Orange-to-Orange (O2O)."

> "Cloudflare proxies and other similar services can interfere with Shopify's network and affect your store's connectivity."

【事実】同ページは SSL 証明書の発行・更新への影響を具体的な故障モードとして警告しています。

> "Shopify needs to verify domain ownership through HTTP challenges (ACME) to issue SSL certificates. A Cloudflare proxy can block or interfere with these challenges, which delays or prevents certificate issuance and renewal."

【事実】さらに、追加のプロキシが Shopify 側の障害対応能力を阻害し、ストアが長時間利用不能になりうるとも述べています。

#### Cloudflare 公式のスタンス（「サポートする」・手順まで公開）

【事実】Cloudflare は「Cloudflare for Platforms > SaaS customers > Provider guides」に **Shopify 専用の O2O 設定ガイド**を公開しており、内容は Shopify の主張と食い違います。

- 設定: CNAME レコード（Target = `shops.myshopify.com`、Proxy status = **Proxied**）
- 利用可能な機能として **Caching・Workers・Rules** が挙げられている
- ただし **"Workers and Snippets are disabled on the `/checkout` URI path"**
- **"Always Use HTTPS" を有効にしてはいけない**。`/.well-known/acme-challenge/*` を含む全リクエストにリダイレクトを強制し、Shopify の Let's Encrypt 証明書の自動更新を失敗させるため。代わりに Redirect Rules で検証パスを除外して HTTPS を強制する
- Enterprise プランの Zone Hold が有効だと Shopify 側でのカスタムホスト名認可がブロックされる
- O2O では顧客側ゾーンの設定が先に適用され、その後 SaaS プロバイダ側ゾーンの設定が適用される

【判断】**この食い違いが本件の核心です。** Cloudflare は自社製品として「動く」と書き、Shopify は自社サービスの可用性に責任を持つ立場から「サポートしない」と書く。**動くかどうかと、壊れたときに誰が直すかは別問題**であり、EC では後者のほうが重い、というのが調査者の判断です。

#### 実測を踏まえた追加の論点 — 想定より大幅に重い

【判断】1.1 で確認したとおり、**現構成に Cloudflare は存在せず、権威 DNS は Google Cloud DNS、Shopify へは A レコード直指しです。** したがってこの案は次のすべてを同時に行うことになります。

1. Cloudflare をゾーンごと新規導入し、権威 DNS を Google Cloud DNS から移管する
2. apex ドメイン `kaketoco.com` の指す先を Vercel から Shopify に切り替える（＝**現在トップページに出ているアプリを apex から降ろす**）
3. Shopify のホスト名をオレンジクラウド化する（＝Shopify 非サポート構成に入る）
4. 3,247 ページを持つ Next.js アプリを `basePath` 化してサブディレクトリ配下に収める
5. 旧 URL（`/pesticides/{UUID}` 3,247 件）から新 URL への 301 マッピングを設計する

**今週末フィックス・リリース間近というタイミングで踏む変更としては明らかに過大です。**

#### 参考として指定された URL の内容

【事実】指定された Shopify コミュニティスレッド「How to use CDN reverse proxy on Shopify?」:

- 質問者（rafaelcg）は Cloudflare プロキシでドメインの `/fr` パスを Shopify に、他パスを既存サイトにルーティングしたかった
- Shopify から `"Your domain uses a Cloudflare proxy, which is not supported by Shopify. This can cause connection issues."` という警告が出た
- 回答者は 3 つの回避策（サブドメイン利用 / グレークラウド化 / オリジンサーバ側でのリバースプロキシ）を提示
- 質問者はいずれも実装不可能と回答し、**スレッドは未解決のまま終了**
- **Shopify は `/fr` のようなサブパスからのアクセスをマスキングできない**ことが言及されている

【判断】このスレッドは「解決策が見つかった記録」ではなく「行き詰まった記録」です。仮説を支持する材料としては使えません。

#### その他の既知の問題

【二次情報】Cloudflare Workers SDK の GitHub Issue #11270 で、**O2O の DNS レコードでは Worker のルートマッチングが期待どおり動かず `*/*` パターンしかマッチしない**という報告があります。未解決の不具合報告であって公式仕様ではありませんが、「`/app/*` だけを Worker に流す」設計を素直に組めない可能性を示します。

【二次情報】複数のコミュニティ投稿で、Cloudflare Workers を Shopify 前段のリバースプロキシに使うと "You do not have permission to access this website" となり Shopify のファイアウォールにブロックされる、という報告があります。

#### 構成上の根本的な矛盾

【判断】技術面を措いても、**この案はルートが Shopify のストアページになります**。実測のとおり現在の apex は「AI農薬検索アプリ」であり、上野様の「ルートはアプリであってほしい」という要望をすでに満たしています。**それをわざわざ崩す案**です。ルートから `/app` へリダイレクトすれば要望に近づきますが、毎日使うユーザーに 1 ホップ増やすことになり UX は悪化します。

**この案の唯一の実質的な利点は「Shopify ブログが素で `kaketoco.com/blogs/...` になる」ことですが、これは案 C で同じ結果が得られます。** 選ぶ理由が残りません。

### Q2. 逆パターン（自社システムをルート、Shopify をサブディレクトリ配下）は可能か

#### 結論

【判断】**Shopify 公式の仕組み（App Proxy）では成立しません。ただし「Vercel 側でコンテンツを取り込む」別ルートは成立し、これが推奨案の土台になります。**

#### Shopify App Proxy — 公式手段だが本件では使えない

【事実】App Proxy は Shopify ストアの URL へのリクエストを外部アプリにプロキシする公式の仕組みです（`https://<shop_url>/apps/my-custom-path/child-route` → `https://<application_url>/my-app-proxy/child-route`）。制約:

- **使えるプレフィックスは `a` / `apps` / `community` / `tools` の 4 つのみ**。`/app` のような任意パスは指定不可
- サブパスは 30 文字以下、英数字・ハイフン・アンダースコアのみ
- **1 アプリにつき設定できるプロキシルートは 1 つのみ**
- `write_app_proxy` アクセススコープが必須
- `Content-Type: application/liquid` を返すとテーマのコンテキストで Liquid がレンダリングされる
- **セキュリティ上の理由から `Set-Cookie` および `Cookie` を含む多数のヘッダがレスポンスから除去される**（原文: "Due to security concerns, the following headers are stripped from app proxy responses"。列挙に `Set-Cookie`、`Cookie`、`Server`、`Connection` 等を含む）

【判断】**`Set-Cookie` / `Cookie` の除去が決定打です。** カケトコのアプリはログイン（ナビに「マイページ」「マイ畑」あり）・カート・Stripe サブスクを持つため、セッション Cookie なしでは成立しません。App Proxy 越しにアプリ本体を配信する選択肢は、この 1 点で消えます。

【事実】この方向の実例として、WordPress ブログを Shopify のサブフォルダに出す「Post Bridge」アプリがありますが、**App Proxy の制約により URL は `domain.com/a/blog` にしかならず `domain.com/blog` にはできない**と報告されています。投稿者は「移行後に順位への悪影響は見られなかった」とも述べていますが、これは 1 事例の自己申告です。

#### Vercel 側のリライト — こちらは成立する

【事実】Vercel の Rewrites は**外部オリジンへのリライトに対応しており、全フレームワークで動作します**。API プロキシ、マイクロフロントエンド、外部オリジンのコンテンツ配信を Vercel のネットワーク経由でリバースプロキシとして提供する用途が公式に想定されています。ワイルドカードによるパス転送（`{ "source": "/docs/:path*", "destination": "/help/:path*" }`）も可能です。

【事実】Next.js では `basePath` と `rewrites` を組み合わせたマルチゾーン構成が公式にサポートされています。

【事実】実測のとおり、**アプリは Next.js on Vercel で稼働している**ため、これらはそのまま使える手段です。

【判断】ただし **Shopify の HTML をそのままリライトで出すのは推奨しません。** 理由は 2 つ:

1. 実測で確認したとおり Shopify のテーマは `<link rel="canonical" href="https://shop.kaketoco.com/">` を出力します。そのままプロキシしても SEO 評価は集約されません（テーマ編集で上書き可能ですが、もっと素直な方法があります）
2. テーマ内のリンクが `shop.kaketoco.com` や `/blogs/...` を指すため HTML の書き換えが必要になり、Shopify のテーマ更新のたびに壊れうる保守負債になります

【判断】**HTML をプロキシするのではなく、Storefront API でデータを取得して自社側でレンダリングするほうが実装も保守も明確に楽です。** しかも実測（CSP の `connect-src` に `https://*.myshopify.com`）から、**アプリは既に Storefront API を叩いていると強く推定されます**。つまり土台は既にあります。

### Q3. Hydrogen / Oxygen への移行に意味はあるか

#### Hydrogen / Oxygen とは

【事実】公式サイト（hydrogen.shopify.dev）より:

- **Hydrogen** は Shopify のヘッドレスコマース向けフレームワーク。React Router チームが作った Remix ベース
- **Oxygen** は Shopify の統合グローバルホスティング。300 以上のエッジロケーションを持ち、**Starter 以外のすべての Shopify プランで追加費用なしに利用可能**
- Storefront API から商品・カートデータを取得する
- デフォルトルートに `/`、`/products/:handle`、`/collections/:handle`、`/cart`、`/:handle`、`/search`、アカウント関連を含む
- カート、Shop Pay、アナリティクス、カスタマーアカウント、ディスカウントリンクが組み込み済み

#### 本件での評価

【判断】**移行を推奨しません。**

1. **価値の中心が違う。** カケトコの競争力は農薬検索・混用可否チェック・カケトコスコア（description に記載）・マイ畑・アラートといった農業ドメイン固有の機能にあります。Hydrogen が提供するのはコマース周りの定型部品で、この中核には何も寄与しません
2. **実質的な全面書き直しになる。** 3,247 ページを持つ稼働中の Next.js アプリを Remix ベースに載せ替える工数は、リリース直前に負える規模ではありません
3. **Vercel を捨てることになる。** Oxygen は Shopify のホスティングです。Stripe・気象庁 API・Google Maps を組み合わせた現在の構成（CSP から確認）を、Shopify のホスティング上で組み直す必然性がありません
4. **現行方針で目的は達成できる。** 実測上アプリは既に Storefront API を叩くヘッドレスストアフロントとして動いています。Hydrogen はヘッドレスを実現する手段の 1 つであって、前提条件ではありません

【判断】**「Shopify フロントを完全に隠す（noindex・必要画面のみ）」という現行方針で十分です。** ただし noindex は**まだ実装されていない**（実測）ため、実装方法には Q5 の注意点があります。

- Shopify のブログエディタが実運用の編集体験に耐えない（画像管理、下書きプレビュー、予約公開など）

【判断】なお、上野様が用意される農薬解説ページ（数十本・NA-20260805-007）の置き場所も同じ判断に乗ります。**農薬解説は `/pesticides/{...}` の個別ページに統合するか、`/magazine` に記事として置くかで SEO 上の意味が変わります。** 前者は既存 3,247 ページの中身を厚くする方向、後者は新規ページを増やす方向です。**個別農薬に紐づく解説なら前者を推奨します**（検索意図が「その農薬について知りたい」なので、1 URL に集約したほうが強くなります）。

### Q5. SEO 根拠 — サブドメイン vs サブディレクトリ、noindex / canonical / リダイレクト設計

#### Google 公式の見解

【事実】Google の John Mueller は、**アルゴリズムはランキングにおいてサブドメインをサブディレクトリより優遇しない**と述べており、「自分のセットアップと長期的な計画に合うほうを使え」というのが一貫した公式見解です。同時に「まとめられるものはできるだけまとめ、本当に少し性質が違うものにサブドメインを使え」とも述べています。

【事実】Google の多地域サイト運用ドキュメントは、国別ドメイン / サブドメイン + gTLD / サブディレクトリ + gTLD を**並列に**提示し、どちらか一方を明示的に優先する記述はありません。

#### サブドメインを分けることの、明確に不利な点（公式仕様）

【事実】Google「Site Names in Google Search」は、**サイト名がドメインまたはサブドメイン単位でのみ認識される**と明記しています。

> "Google Search only supports one site name per site, where a *site* is defined by the domain or subdomain"

- サポート対象: `https://example.com`、`https://www.example.com`、`https://m.example.com`、`https://news.example.com`
- **非サポート: `https://example.com/news`（サブディレクトリレベルではサイト名を持てない）**
- `www` や `m` で始まるサブドメインは一般にドメインレベルと同等に扱われる
- 実装はトップページに `WebSite` 構造化データ（`name` と `url` が必須、`alternateName` で別名も指定可）を置く

【判断】**これが本件で最も実務的に重要な公式仕様です。** `shop.kaketoco.com` は Google から見て `kaketoco.com` とは**別のサイト**であり、独自のサイト名を持ちうる存在です。**現状は Shopify 側だけがクロール可能なので、「かけとこ」の指名検索で `shop.kaketoco.com` が独立して出てくるリスクが現実に存在します。** 逆に `kaketoco.com/magazine` はサブディレクトリなので独立したサイトにはならず、サイト名は `kaketoco.com` に一本化されます。

【判断】**ただし実測のとおり、`kaketoco.com` のトップが宣言しているのは `WebApplication` であり、Google がサイト名の宣言に指定する `WebSite` ではありません。** `WebApplication` は `SoftwareApplication` の下位型で `WebSite` の下位型ではないため、これでサイト名が認識される保証はありません。**`WebSite` を併記するだけで済む、低コストかつ指名検索に直結する改善項目です。**

【事実】Google Search Console の**ドメインプロパティ**は、そのドメイン配下の全プロトコル・全サブドメイン・全パスのデータを含みます。

#### 「サブディレクトリのほうが伸びる」という主張の実証状況 — 両論あり

【二次情報】移行で成果が出たとする事例（いずれも SEO ベンダー/事業者のブログで、一次データの検証はできていません）: Buffer（6 か月で自然検索 2 倍）、Obility（上位 5 記事 +37%、トップ +36%）、Monster.com.uk（可視性 +116%）、Pink Cake Box（+40%）。

【二次情報】反証（Ahrefs）: 「サブディレクトリがサブドメインより優れる」は**神話**であるとし、Matt Cutts（2012）と John Mueller（2017）の「基本的に同等」という発言を引用。mention.com の流入増は移行時ではなく**コンテンツ追加後**に発生していること、GitHub は 3 度構造を変えたが影響は限定的だったことを挙げ、実際の差は内部リンク・コンテンツ追加・インデックス設定ミス・技術改善に帰せられると分析。「SEO だけを理由とした移行は再考すべき」と結論づけています。

【判断】**この論争は本件の意思決定を左右しません。** ブログ記事はまだ 0 件で、移行すべきものが存在しないからです。Ahrefs の警告は既存サイトの移行についての話であり、これから置く場所を決める本件には当てはまりません。**移行リスクがゼロで、統合側に公式仕様上の確実な利益（サイト名の一本化）があるなら、統合側を選ばない理由がありません。**

#### チェックアウトが別ドメインになることの影響

【事実】ヘッドレス構成では、フロントエンドは Storefront API でカートを作り `cart.checkoutUrl` へリダイレクトします。チェックアウト UI は Shopify がホストし、PCI 準拠・不正対策・Shop Pay / Apple Pay / Google Pay に対応します。実測でも `shop.kaketoco.com` はこれらに対応済みです。

【二次情報】`checkout.yourdomain.com` のような専用チェックアウトサブドメインには Shopify Plus 相当が必要という記述が複数の事業者ブログにありますが、金額・プラン要件は情報源によって食い違っており、**Shopify への直接確認が必要です**。

【判断】SEO 上の影響は実質ありません。チェックアウトは Shopify のデフォルト robots.txt で `Disallow: /checkout` されており、そもそもインデックス対象外です。UX 上も、`shop.kaketoco.com` は登録ドメインが一致し、実測のとおり Cookie も `domain=kaketoco.com` で共有されているため、現状で十分良好です。

#### noindex / canonical / リダイレクトの設計指針

【事実】Shopify での noindex 実装:

- テーマの `theme.liquid` の `<head>` に `<meta name="robots" content="noindex">` を出力する（Shopify ヘルプセンター「Hiding a page from search engines」の公式手順）
- `robots.txt.liquid` は管理画面（Online Store > Themes > Edit code > Templates）で編集でき、なければ新規作成できる。ただし Shopify は「提供された Liquid オブジェクトをできる限り使うこと」を推奨（デフォルトルールが SEO のベストプラクティスに追従して更新されるため）

【判断】**設計上の落とし穴が 2 つあります。**

**落とし穴 1: `robots.txt` で `Disallow` してはいけません。** クロールをブロックすると Google が `noindex` メタタグを読めず、URL がインデックスに残り続ける可能性があります。**クロールは許可したうえで `noindex` メタタグを出す**のが正解です。

**落とし穴 2: これは今まさに `kaketoco.com` で起きている問題の裏返しです。** アプリ側の `Disallow: /` は「インデックスさせない」目的なら機能しますが、**リリース後にこれを外すのを忘れると、3,247 ページが永久に検索から消えたままになります。**

【判断】推奨する具体的な設計:

| 対象 | 指示 | 理由 |
|---|---|---|
| **`kaketoco.com/robots.txt`** | **`Disallow: /` を削除し、`Sitemap: https://kaketoco.com/sitemap.xml` を宣言する** | **最優先。現状ここが全体のボトルネック** |
| `kaketoco.com` のトップ | `WebSite` 構造化データ（`name: カケトコ`、`alternateName` に表記ゆれ）を追加 | サイト名を Google に明示。指名検索に直結。現状 JSON-LD が 0 件 |
| `shop.kaketoco.com` の全ページ | `<meta name="robots" content="noindex,follow">` を `theme.liquid` に追加 | 同等コンテンツをアプリ側が配信するため。`follow` でリンク追跡は維持 |
| `shop.kaketoco.com` の `robots.txt` | Shopify のデフォルトのまま。`Disallow` を追加しない | 追加すると上の noindex が読まれない |
| `kaketoco.com/magazine/[handle]` | 自己参照 canonical | 正規 URL を明示 |
| `kaketoco.com/pesticides/*` | 自己参照 canonical（トップは設定済み） | 3,247 ページ全体で確認 |
| `www.kaketoco.com` | `kaketoco.com` へ 301 | 実測では www も Vercel を指しており両方到達可能。片方に寄せる |

【判断】noindex と cross-domain canonical を**併用してはいけません**。矛盾したシグナルになります。本件では「Shopify 側の URL は検索結果に出したくない」という意図が明確なので、noindex 一本で設計するのが判断しやすく、Search Console での検証も容易です。

【判断】**追加の改善提案: `/pesticides/{UUID}` という URL 形式は見直す価値があります。** Google の「URL Structure Best Practices」は、URL をできるだけシンプルにし、**人間にとって理解しやすい形で論理的に構成すること**を推奨しています。`/pesticides/17432e1a-2df6-4a9c-84fa-51ed2f8632fc` は UUID なので、農薬名のスラッグ（例: `/pesticides/actara-granule`）のほうが望ましいです。**ただしこれは 3,247 ページの URL 変更を伴うため、まだインデックスされていない今のうちにやるなら無コスト、インデックス後にやるなら 301 マッピングが必要**という性質の判断です。**今が最も安いタイミングです。**

### Q6. 指名検索「かけとこ」でアプリを検索結果トップに出す構成

#### 事実として押さえるべきこと

【事実】サイトリンクは Google が自動生成します。**サイト運営者が直接コントロールする手段はありません**（公式に「現在のところサイトリンクは自動化されている」と明記）。削除したい場合はページを削除するか `noindex` を使う、というのが唯一の介入手段です。推奨されるベストプラクティスは:

- ページタイトルと見出しのテキストを情報量が多く関連性が高くコンパクトにする
- ユーザーが簡単にナビゲートできる論理的なサイト構造を作る
- 内部リンクのアンカーテキストを簡潔で関連性のあるものにする
- コンテンツの重複を避ける

【事実】サイト名は `WebSite` 構造化データでトップページに指定します。ドメイン/サブドメインごとに 1 つだけです。

#### freee の例について — MTG での認識は事実と異なります

【事実】`freee.co.jp` のルートを実際に確認したところ、**白紙のリダイレクトページではなく、サービス紹介のトップページ**でした。アプリ本体（freee 会計）のログインは **`secure.freee.co.jp` というサブドメイン**にあります（人事労務は `p.secure.freee.co.jp`、士業向けは `adv.freee.co.jp` の別サイト）。

【判断】**したがって freee の例を根拠に使うと、結論は「ルート = LP、アプリ = サブドメイン」になり、上野様の要望と正反対になります。** freee は B2B SaaS で、検索流入はマーケティングコンテンツが担い、既存ユーザーはブックマークでログインします。カケトコは「毎日使うユーザーが楽にアクセスできること」を重視する要件なので前提が異なります。**根拠としては採用すべきでない**というのが調査者の判断です。

#### 推奨する構成

【判断】**現状の「ルート = アプリ画面」を維持することを推奨します。** 実測のとおり `kaketoco.com` のトップは既に AI農薬検索アプリで、title・description・canonical も適切に設定されています。**構成としては既に正解に近く、足りないのは以下の 3 点だけです。**

1. **robots.txt の解除**（最優先。これがなければ何も始まらない）
2. **`WebSite` 構造化データの併記**（サイト名「カケトコ」の宣言。現状は `WebApplication` のみ）
3. **ルート下部にサービス説明テキストを持たせる**。アプリ UI 主体でテキストが少ないページは指名検索の受け皿として弱くなりがちです。現状の description と `WebApplication` の description は良く書けているので、同等の内容をページ本文にも展開する

【判断】LP（NA-20260805-002）については、**ルートをリダイレクトさせない前提で設計します。** LP が必要という MTG の合意と、ルート = アプリという上野様の要望は両立します。具体的には次のいずれかです。

- **推奨**: ルート = 上部に検索 UI・下部にサービス説明セクションを持つ 1 枚構成。リダイレクトは挟まない
- 非推奨: ルートを別 URL の LP へリダイレクト（毎日使うユーザーに 1 ホップ増。上野様の要望に反する）

【判断】B2B（農薬業者）向けの動線は、**ルート下部の説明セクション内に控えめに置き、ヘッダーには常駐させません。** そのうえで独立した **`/business`** ページを用意し、PR・被リンクの着地点はそこを直指定してルートを経由させない運用にします。ルート上部（検索 UI）は B2C の視界を保ち、PR 経由でルートに着地した B2B 層も下部で拾える形です。

> 【追記 2026-08-05・並行調査との整合】LP 構成調査（`2026-08-05_LP構成調査.md` 第 8 章 論点 3・第 6-14 章）と突き合わせた結果、両調査の推奨は実質同一の形に収束した（**ルート＝上部に検索 UI・下部にサービス説明を持つ 1 枚構成。リダイレクトなし**。呼び方が「アプリに説明を足す」か「LP に検索窓を埋める」かの違いのみ）。B2B 動線については、当初案（独立 LP を `/lp` に置き、そこへ B2B を寄せる）から**ルート下部の説明セクション内に控えめに置き、独立の `/business` ページを被リンク・PR 着地の受け皿として用意する**形に改め、本節の本文も書き換え済み。パス名は LP 構成調査と `/business` で統一した。

【判断】サイトリンクは制御できませんが、ルートから `/magazine`・使い方・商品一覧への論理的な内部リンクを簡潔なアンカーテキストで張っておくことが、公式に推奨されている唯一の働きかけです。

## 4. 推奨案と実装ステップ

### 4.1 第1候補: 案 C

**ドメイン構成は現状（ルート = Vercel アプリ、`shop.kaketoco.com` = Shopify、権威 DNS は Google Cloud DNS のまま）を一切変えず、SEO の向き（クロール可否）を目的どおりに反転させ、ブログを `kaketoco.com/magazine` として自社側で配信する。**

【判断】この案を推す理由を一言でいえば、**関係者 3 者の要望が競合せずに全部通り、かつ現構成からの差分が最小だから**です。

- 上野様: ルートがアプリのまま。指名検索の受け皿もアプリ。Shopify への遷移はレジのときだけ
- 古谷様: Shopify 管理画面でブログを書ける。SEO 評価は `kaketoco.com` に集約される
- 野呂様: Shopify が非サポートと明言する構成を踏まない。DNS・証明書・apex に触らない。失敗しても影響が局所に閉じる

### 4.2 実装ステップ（優先度順）

#### ステップ 1（最優先・所要数分）: robots.txt の解放

`kaketoco.com/robots.txt` の `Disallow: /` を削除し、sitemap を宣言する。

```
User-Agent: *
Allow: /

Sitemap: https://kaketoco.com/sitemap.xml
```

【判断】**これだけで 3,247 ページがインデックス候補になります。本調査で見つかった中で、投下工数あたりの効果が最大の項目です。** ただし「リリース前に意図的に遮断している」のであれば、解除タイミングを明示的にリリース手順書へ載せることが必須です。**外し忘れが最大のリスク**です。

#### ステップ 2（低コスト・高効果）: 指名検索対策

- トップページに `WebSite` 構造化データを**併記**（`name: カケトコ`、`url: https://kaketoco.com`、`alternateName` に「かけとこ」等の表記ゆれ）。既存の `WebApplication` は残してよい
- ルート下部にサービス説明テキストを配置
- 農薬個別ページの構造化データ（`Product` + `BreadcrumbList` + `Organization`）は既に適切なので変更不要

#### ステップ 3: Shopify 側を隠す

- `theme.liquid` の `<head>` に `<meta name="robots" content="noindex,follow">` を全ページで出力
- `robots.txt.liquid` には `Disallow` を追加しない（追加すると noindex が読まれない）
- **DNS は現状のまま触らない**（`shop.kaketoco.com` A = `23.227.38.69` の直指し。Cloudflare を挟まない）
- Shopify のプライマリドメインが `shop.kaketoco.com` であることを確認（チェックアウトがこのドメインになる）

#### ステップ 4: ブログを `/magazine` として実装

- Storefront API のアクセストークンに **`unauthenticated_read_content` スコープ**を付与（記事取得に必須）
- `/magazine`（一覧）と `/magazine/[handle]`（詳細）を追加し、`blog.articles` / `blog.articleByHandle` から生成
- 取得フィールド: `title`、`contentHtml`、`excerpt`、`handle`、`image`、`publishedAt`、`seo`、`tags`、`authorV2`
- レンダリングは ISR（既にアプリで稼働中。`x-nextjs-stale-time: 300` を実測）
- 各記事に自己参照 canonical、`sitemap.xml` に `/magazine` 配下を追加、`Article` 構造化データを付与
- CSP の `connect-src` は既に `https://*.myshopify.com` を許可済みなので変更不要

#### ステップ 5: URL 設計の見直し（今なら無コスト）

- `/pesticides/{UUID}` を農薬名ベースのスラッグに変更するか検討する
- **インデックスされる前の今なら 301 マッピングが不要**。ステップ 1 の前に判断するのが最も安い

#### ステップ 6: UX の即時改善

- カート → レジは `cart.checkoutUrl` へ**同一タブで**遷移（`target="_blank"` を外す）

#### ステップ 7: 計測

- Search Console を `kaketoco.com` の**ドメインプロパティ**で登録する（全サブドメイン・全プロトコルを一括で見られる）
- `shop.kaketoco.com` の URL がインデックスから消えていくこと、`kaketoco.com` の URL が増えていくことを継続確認する

### 4.3 条件付き第2候補: 案 C-2

**ブログのデータソースを Shopify から microCMS 等のヘッドレス CMS に差し替える。配信側（`/magazine`）は案 C と共通。**

【判断】切り替えの判断条件は Q4 に記載のとおりです。**最初からこちらを選ぶ必要はありません。** 案 C で運用を始め、編集体験に実際の不満が出た時点でデータ取得層だけを差し替えれば移行できます。この「後から差し替えられる」性質が、HTML をプロキシする案（B-2）ではなく API で取得する案（C-1）を推す理由の 1 つです。

### 4.4 案 B を採るとしたら、満たすべき条件

【判断】古谷様の仮説を通すのであれば、最低限これらが揃っている必要があります。逆にいえば、揃わないうちは着手すべきではありません。

1. リリース後、トラフィックが安定してから着手する（リリース直前には行わない）
2. Cloudflare をゾーンごと新規導入し、権威 DNS を Google Cloud DNS から移管することを許容する
3. apex をアプリから Shopify に明け渡すことを上野様が了承している（**現時点の要望とは矛盾します**）
4. `/checkout` で Workers が無効化される制約を踏まえたルート設計ができている
5. "Always Use HTTPS" を恒久的に無効にし、Redirect Rules で `/.well-known/acme-challenge/*` を除外した HTTPS 強制を組む運用を、担当者交代後も維持できる
6. Shopify のサポートを受けられない構成であることを上野様が明示的に了承している
7. Next.js アプリを `basePath` 化し、3,247 URL の 301 マッピングを設計できる

### 4.5 リリース前チェックリスト

【判断】ドメイン構成の議論と切り離して、**リリース前に必ず潰しておくべき項目**を実測ベースで抽出しました。1 と 2 はドメイン構成をどう決めても必要です。

| # | 項目 | 現状（実測） | 対応 | 優先度 |
|---|---|---|---|---|
| 1 | `kaketoco.com/robots.txt` | `Disallow: /`（全遮断） | `Disallow` を削除し `Sitemap:` を宣言 | **最優先。外し忘れ厳禁** |
| 2 | `shop.kaketoco.com` の noindex | 未設定（フルにインデックス可能） | `theme.liquid` に `noindex,follow` を追加 | 高 |
| 3 | トップの `WebSite` 構造化データ | `WebApplication` のみ | `WebSite`（`name`・`alternateName`）を併記 | 高 |
| 4 | `/pesticides/{不正ID}` | HTTP 200 +`noindex` | 404 を返すよう変更 | 中（`noindex` で事故は防止済み） |
| 5 | `/pesticides/{UUID}` の URL 形式 | UUID | 農薬名スラッグ化を検討 | 中（**インデックス前の今なら 301 不要**） |
| 6 | `www` の正規化 | 両方が Vercel を指し到達可能 | 片方へ 301 | 中 |
| 7 | カート→レジの遷移 | 未確認 | `target="_blank"` なら外す | 中（UX 不満の原因候補） |
| 8 | Search Console | 未確認 | `kaketoco.com` のドメインプロパティで登録 | 中 |

【判断】**1 と 5 には順序があります。** URL 形式を変えるなら robots.txt を開放する前に決めてください。開放後に変えると 3,247 件の 301 マッピングが必要になります。

### 上野様へ

1. 「別タブが開いて UX が悪い」と感じたのは具体的にどの画面のどの操作ですか
2. レジ（チェックアウト）の URL が `shop.kaketoco.com` になることは許容できますか
3. ブログ記事は誰が、どれくらいの頻度で書きますか。Shopify の管理画面で書くのが実際に楽そうですか
4. 共有予定の農薬解説ページ（数十本）は、個別農薬ページに統合する形と、マガジン記事として独立させる形のどちらを想定されていますか
5. 指名検索の表記ゆれ（「カケトコ」「かけとこ」「kaketoco」）のうち、主に使われるのはどれですか（構造化データの `alternateName` に反映します）

### 古谷様へ

1. ドメイン構成の変更はリリース前に確定させますか、リリース後の改善項目としますか
2. 「Shopify のブログ機能を使いたい」の主眼は、**編集のしやすさ**ですか、**追加コストをかけないこと**ですか。どちらが主かで案 C-1 / C-2 の選択が変わります
3. Shopify の商品ページ（現在フルにインデックス可能）を noindex にする方針は確定でよいですか
4. サービス説明はトップページ下部への統合で進めてよいですか。あわせて B2B 向けの独立ページを `/business` で用意する方針で合意いただけますか（NA-20260805-002 の前提になります。LP 構成調査と揃えたパス名です）
