# チタンからの物件取得 API 仕様（整理メモ）

## エンドポイント

物件取得は次の URL のスクリプトに対して行います。

`https://www.1lcinc.com/syuuekibukken/php/json_output.php`

## リクエスト

- **メソッド**: POST
- **ボディ**: FORM 値のリストに含まれるパラメータを用いてリクエストする。種別など、取得したい物件の条件を指定できる。

FORM 値の一覧は、ワンエルシー様共有のスプレッドシートにまとまっている。

- [FORM 値リスト（Google スプレッドシート）](https://docs.google.com/spreadsheets/d/12h9G54aXjOxWz5K_ko4GdN3H-xQjvu59oHEpPOKsLTo/edit?gid=0#gid=0)

## エリア単位の取得

ワンエルシー様のご要望により、エリアごとに分けて取得している。`物件エリア` テーブルの値を入力条件に用い、エリアごとに API リクエストを実施する。

- [物件エリア（Airtable）](https://airtable.com/appksEWIuKl7N2ftS/tblzcwsQyKYP6AFtN/viw2PaofDtqfvxTMJ?blocks=hide)

## データフロー（構造）

1. **Airtable**（Automation / Scripts）
2. **チタン DB**（上記エンドポイント経由）

流れは次のとおり。

1. Airtable 側からチタンに API リクエストを送る。
2. チタン側が物件データをレスポンスで返す。
3. Airtable のスクリプトで受け取ったデータを **`チタン物件一覧`** テーブルに格納する。

**テスト結果**:

### v2.5（ドラフト・2026-07-11作成 / 本番未反映）

**背景**: チタン様より、URLパラメータ `hkensu={件数}` を追加すれば1リクエストで50件超のデータが取得できるよう対応完了したと連絡あり（2026-07-07チタン様MTGで宿題になっていた「50件上限の必要性確認」への回答）。500〜1000件あたりから様子を見るよう案内あり。

**ローカル検証結果**（東京都・価格帯5,000〜200,000万円、POST + JSON body方式で現行の `jusyoc` 配列渡しはそのまま）:
- hkensu無し（現行同様）→ 50件（打ち切り）
- hkensu=200 → 200件（まだ打ち切り）
- hkensu=500 → **248件（打ち切りなし＝東京都の真の全件）**
- JSON構造（フィールド名）は変化なし。応答速度は248件で約1.9秒、大きな遅延なし
- 検証スクリプト: セッションスクラッチパッドの `test_hkensu.mjs`（本ファイルには未配置）

**改修方針**（`automation_script_v2.5_draft.js`）:
1. 価格帯7分割ロジック（SUB_RANGES）を全廃 → 1エリア1リクエストに統一
2. 全リクエストに `hkensu=500` を付与
3. Airtable Automationのfetch回数上限（50回/実行）に対し、エリア数38に対してFETCH_BUDGETを47→45へ緩和（価格帯分割が無くなり1エリア1回で済むため大幅に余裕ができる）
4. 返却件数がHKENSU値に到達した場合の警告ログを新設（将来の上限到達＝取りこぼし再発を検知するため）
5. ランタイム汚染対策（selectRecordsAsync先行実行・fetch例外検知・汚染時書き込みスキップ）はv2.4のまま維持

**未検証・要確認**:
- 東京都以外の37エリアでの実件数（HKENSU=500で足りない大規模エリアが無いか。警告ログで検知可能な設計にはしているが初回実行時の実測が必要）
- Airtable Automation環境での実行時間（180秒制限に対する実測。ローカル検証は参考値に留まる）
- 欠落していた約3,200件（チタン様MTGで判明）は、本スクリプトの通常実行で既存のURL単位create/updateロジックにより自動的に新規createされる想定。専用の再取得処理は設けていない
- **Airtable本番Automationへの反映・実機テストは未実施**（naruによる実施が必要。Airtable UI上でのスクリプト差し替えのため代行不可）

**実機テスト結果（2026-07-11・2回実施）**:
- ローカル検証では東京都以外の主要4エリア（神奈川29件・埼玉27件・大阪19件・愛知34件、いずれもHKENSU=1000で試行）も含め全件HKENSU=500を大きく下回り、上限到達の警告は0件
- しかし**Airtable Automation本番環境で2回とも`socket hang up`のfetch例外が発生**（1回目: 東京23区で発生・35回目のfetch。2回目: 千葉県で発生・7回目のfetch。失敗する場所・タイミングに規則性なし）

- 実行履歴では2026-06-25（v2.4より前）にも "Your script threw an error" で失敗した記録があり、この不安定性はhkensu導入前から存在していた可能性がある

### v2.6（ドラフト・2026-07-11作成 / 本番未反映）

**目的**: v2.5実機テストで判明した「1エリアのfetch失敗で全エリア分の成果が消える」問題への対応

**改修方針**（`automation_script_v2.6_draft.js`）:
1. 「ランタイム汚染」フラグによる全体停止・書き込みスキップを廃止
2. フェーズ1: 全38エリアを1回ずつ試行。fetch失敗したエリアは記録するだけで、他のエリアの処理には影響させず続行
3. フェーズ2: フェーズ1で失敗したエリアのみ、残りのfetch予算（上限50回/実行）内で再試行
4. 取得できたデータは、一部エリアが失敗していても必ず書き込む
5. 再試行しても失敗したエリアは次回の定期実行（6時間後）に委ねる。1回の実行で100%揃えることを狙わない設計に変更

**あえてやらないこと（2026-07-11 naruと合意）**:
- Airtable Automation自体の分割（エリアをグループ分けして複数Automationにする等）による延命的な設計改善は行わない。理由: 2026-07-15(火)の1LC定例で新サーバーのアーキテクチャ・費用感を協議予定で、合意が取れ次第Airtable自体からの移行が近い見込みのため、Airtable内で作り込みすぎるのは非効率と判断
- fetch失敗の根本原因（Airtable Automation環境特有の問題かチタン側サーバーの問題か）の特定も本バージョンのスコープ外。チタン側への確認は別途実施予定

**v2.6実機テストで新たに発覚した問題（2026-07-11）**:

1. **選択肢フィールドの未登録値エラー**: 新規作成167件が「建物構造」フィールドの値`ＡＬＣ`（全角）でエラー（`Field "fldO4kXbavhK89iBC" cannot accept the provided value.`）。Airtable Scripting（Automation内のScript）の`createRecordsAsync`はREST APIと異なりtypecastをサポートせず、未登録の選択肢値を渡すとエラーになり、かつ`updateOptionsAsync`もAutomationからは呼べない（"Cannot update field config from scripting automation"）。
   - 原因の検証: 該当物件（埼玉県、価格2.5億円）はレスポンス内25番目に位置し、v2.4の50件上限でも取得可能な範囲だった。かつ該当URLは削除前のAirtableに一度も存在していなかった。つまり「hkensu導入で初めて見えた」のではなく、**「未登録選択肢によるcreate失敗という問題自体はhkensu導入以前から潜在していたが、ログに出るだけで誰も気づいていなかった」**というのが正確な理解（fetch失敗時のランタイム汚染と同じ「ログは出るが誰も見ない」構造）。
   - 対応: naruがAirtable UI上で「建物構造」フィールドの選択肢に`ＡＬＣ`を手動追加。恒久対策（事前チェック等）は未実装、今後also同様の未登録値が出る可能性は残っている。

2. **テスト実行の繰り返しによる重複レコード作成**: v2.5・v2.6のテストを短期間に何度も繰り返した結果、「スクリプト実行開始時点の既存レコードスナップショットと照合してcreate/updateを判定する」設計の弱点を突いてしまい、同一URLが複数回create された。2026-07-11時点で255種類のURLが重複（167グループが3重複・88グループが2重複、余剰422件）。原因は複数回のテスト実行（+Automationのオン/オフ切り替えタイミングの問題）が重なったことで、同じ物件が「まだ存在しない」と誤判定され続けたためと推定。
   - 対応: 422件の全フィールドをバックアップ後、各グループで「新規登録日が最も古い」1件を残して削除。削除後の重複ゼロを確認済み。
   - 教訓: 通常運用（6時間ごとの自動実行のみ、手動テストと重複させない）であれば起きないはずの問題。今後Airtable Automation上でテストする際は、可能な限り単発で行い、直後に自動実行と重ならないよう注意する。

**重要な設計判断**: 上記2点目は、「所有権以外は一切ingestしない」という単純な実装だと矛盾が生じる。既存レコードが`ingest`段階で弾かれると、既存レコードとの照合(`urlMeta`)自体の対象から外れてしまい、「既存にあるかどうか」の判定が行われず、更新すらされない（土地権利フィールドが永遠に空欄のまま放置される）。岩下様は「既存レコードの値は更新されてほしい」と明言しているため、フィルタは**新規作成の可否判定にのみ適用し、既存レコードの更新には適用しない**設計にする必要がある。

**改修内容**（`automation_script_v2.8_draft.js`）:
1. `HKENSU`: 500 → 1,000
2. creates/updates振り分けで、`meta`（既存レコード）がある場合は無条件で更新、無い場合（新規作成）のみ「土地権利が所有権以外なら作成しない」フィルタを適用

**未対応**:
- 岩下様メールに登場した「普通借地」「定期借地」という値は実測で未確認のため、選択肢への事前追加は見送り。未登録値エラーが出た場合は都度追加する運用とする

**実機テスト結果（2026-07-13）**: naruがAirtableに「土地権利」フィールド（Single select、選択肢: 所有権/旧法賃借/旧法地上）を作成後、本番反映してテスト実行（1回のみ）。
- フェーズ1: 全38エリア成功（fetch失敗なし）
- 新規作成57件 / 更新100件 / 土地権利で新規除外0件、全てエラーなく成功
- 全エリア合計157件（前回テスト時459件から減少。ローカル検証でも東京都51件・所有権46件/空欄5件と同条件で再現したため、Airtable側の問題ではなくチタン側在庫の時間帯変動と判断）
- 土地権利フィルタのロジック自体はコードレビューで正当性を再確認（空欄・所有権は通し、所有権以外の明示値のみ除外）。今回「除外0件」だったのは対象データにたまたま所有権以外が含まれていなかっただけ

### v2.9（2026-07-25 本番反映済み）

**背景**: 2026-07-22〜25 の4日間、新規物件の取り込みが全停止する事故が発生（岩下様からの指摘で発覚）。原因は土地権利（single select）に未登録値「普通賃借」が1件出現し、Airtable Automationの仕様「書き込みが1回失敗すると以降の全書き込みが `Request processing is disabled` で無効化される」が発動、毎実行で新規create全滅。Automationは「成功」表示のため検知が遅延した（7/11のＡＬＣ事故と同じ「ログは出るが誰も見ない」構造の再発）。土地権利対処後のテストで建物構造の未登録値「軽量気泡コンクリート」でも同型の全滅を確認し、個別対処でなく構造対策に切り替えた。

**実測**: 過去60日で新規0件の日は 7/22〜25 の4日間のみ（それ以前の欠落日ゼロ。日次実測済み）。

**改修内容**:
1. **土地権利フィールドを single select → single line text に型変更**（naruがUI操作で実施。既存値は文字列として保持を確認済み）。スクリプトの書き込みを `{name:...}` → 文字列に、新規作成フィルタを `landRight.name` → `landRight` 文字列比較に変更
2. **select型サニタイザ**: 実行時に `table.fields` から全select型（建物構造・種別・広告可否・売主・過去紹介済｜成約済 の5フィールドを自動検出）の登録済み選択肢を読み、書き込み前に照合。NFKC正規化で表記ゆれ（全角ＡＬＣ等）は正式名に変換して通し、真に未知の値のみ間引いて警告ログ。**未知の値が来てもレコード自体は登録される**（従来: 1件の未知値で全書き込み全滅）
3. **数値ガード `num()`**: NaNを書き込まない（価格null物件でのスクリプト即死・積算価格の妥当性等のNaN書き込み全滅、というレビューで発見した潜在バグ2件も同時に修正）
4. **URL欠落物件のスキップ**、**安全弁**（未登録値比率20%超なら書き込み中止=チタン側フォーマット変更対策）、**新規0件警告ログ**、**output.set によるサマリ出力**（created/updated/writeErrors/unknownTokens/aborted。通知連携用）

**テスト結果（2026-07-25 未明・1回実行後に本番公開）**: 全38エリアfetch成功 / 新規作成63件・更新28件・書込エラー0バッチ / 4日ぶりに新規取り込み再開を確認

**運用**: 「未登録の選択肢値を検出」の警告が出たら、Airtable UIで該当フィールドの選択肢に値を追加すれば、次回実行（最大6時間後）から自動で埋まる（掲載終了済み物件は埋まらない点に注意）。

**バックログ回収（2026-07-25 実施済み）**: `inai` パラメータが「◯日以内の掲載/更新」の期間指定であることを実測で特定（inai=2:28件 → inai=7:322件 → inai=30:1000件上限、東京都）。現行パイプラインは inai=2 のため、停止4日間に掲載された物件は掲載継続中でも定期実行では回収不能だった。そこで inai=7 で全38エリアを照会し、Airtable未登録の399件のうち通常ルール適用後の**392件をREST API（typecast有効）で一括登録**（エラー0・重複0・新規登録日自動設定OK）。当日の通常実行63件と合わせ**計455件を回収**。残る恒久欠落は「停止中に掲載され、かつ回収前に掲載終了した物件」のみ（Airtable側からは観測不能。確定にはチタン様への照会が必要）。回収スクリプト: `backlog_recover_dryrun.py`（差分集計）→ `backlog_recover_exec.py`（登録実行）。今後同種の停止が起きた場合はこの2本で再回収できる。

**未対応（Phase 2 予定）**: ①writeErrors/unknownTokens を使った異常時の実通知（メール等） ②「24時間新規0件」のデッドマンスイッチ ③事故期間の恒久欠落件数の確定（チタン様への掲載終了分照会）
