# AWS（新サーバー）移行 要件整理

作成日: 2026-07-25。前提: 2026-07-07 の1LC定例で「新規サーバー構築の方向」が決定（月1万円以内で提示予定）、07-15 定例で新サーバーのアーキテクチャ・費用感を協議予定だった文脈。Airtable は即解約せず**2〜3ヶ月の段階移行**方針。以下は現行実装（v2.9・監査吸い出し 2026-07-25 時点）から抽出した要件と**論点**であり、アーキテクチャの断定は行わない。

### 1.5 運用上の暗黙前提

- チタンAPIは**認証なし**・レスポンスは在庫の時間帯変動あり（同条件でも件数が揺れる）・`hkensu` 上限到達＝取りこぼしの検知が必要
- Airtable の Interface（toBボタン・確認画面）と各テーブルUIは**1LC側が現役で業務利用中**。データの置き場所を移しても、1LCの操作面を急に奪えない（段階移行方針の根拠）
- 未登録select値が出た場合の運用（警告→Airtable UIで選択肢追加→次回実行で自動反映）は Airtable 固有。移行後は不要になるべき運用（→2章）

## 2. 現行の既知の穴 — 移行で構造的に解消すべきもの

| # | 穴 | 現行の状態 | 移行での解消方針（構造的） |
|---|---|---|---|
| H1 | **未登録select値で書き込み全滅** | v2.9 のサニタイザで緩和（未知値は空欄で登録・警告ログ）。ただし根本原因は Airtable select型＋Automation の typecast 不可 | 移行先DB（RDB等）は文字列で受けて正規化はアプリ層で実施。**「選択肢を人手で追加しないと値が入らない」運用自体を廃止**。NFKC正規化ロジック（G11）は資産として移植 |
| H2 | **書き込み1失敗→以降全滅（"Request processing is disabled"）** | Airtable Automation 固有仕様。7/11・7/22 の2事故の根本原因 | 移行先では**レコード単位のupsert＋失敗分離**が普通に書ける。バッチ失敗の連鎖という制約自体が消える |
| H3 | **失敗しても「成功」表示・通知なし**（ログは出るが誰も見ない） | v2.9 で output サマリまで実装、**通知は未接続**（Phase 2） | 実行基盤の標準機能（CloudWatch アラーム等）で **失敗＝通知** を構造化。「24時間新規0件」デッドマンスイッチを一級の要件に昇格 |
| H4 | **掲載終了検知がない** | inai=2 は新着/更新のみ。掲載終了物件は最大90日マッチング対象に残り、**終了物件をメール紹介するリスク** | 掲載終了チェッカー（全在庫照会 or URL生存確認）を新設する論点（→3章）。Airtable の fetch制約下では作れなかったもの |
| H5 | **停止期間のバックログが自動回収不能** | inai=2 のため、取得停止が2日を超えると恒久欠落。7/25 に inai=7 の手動スクリプトで回収した | 取得ワーカー側で「最終成功時刻」を永続化し、**停止期間に応じて inai を自動拡大**する等の自己回復設計が可能になる |
| H6 | **fetch 45回/実行・30秒タイムアウト・180秒・512MBの枠内に全処理を押し込む設計** | 優先順位・予算管理・2フェーズ再試行という複雑さはすべてこの制約対策 | 実行時間・リクエスト数の制約が消えれば、**エリア逐次+指数バックオフの素直なリトライ**に単純化できる。socket hang up 問題（Airtable環境特有と推定）も切り分けられる |
| H7 | **べき等性がスナップショット照合頼み**（実行が重複すると同一URLが多重create。7/11 に422件重複の実績） | 運用ルール（テストと定期実行を重ねない）で回避中 | **DB側の一意制約（URL unique）**で構造的に排除。実行の排他制御（ロック）も標準手段で可能 |
| H8 | **履歴照合キーが「メール埋め込み」整形文字列** | 表示文言を変えると重複除外が壊れる脆い結合。過去には履歴更新がコメントアウトされ未稼働だった時期もあり | 履歴は**物件ID×顧客ID**で持つ。表示文言と照合キーを分離 |
| H9 | **③⑤の履歴挿入がベストエフォート**（失敗してもメールは飛ぶ、型不整合の疑いもコード上あり） | エラーは catch してログのみ | 「履歴記録に成功してから送信する」等、**送信と記録のトランザクション順序**を設計で保証 |
| H10 | **シークレットの平文ハードコード**（Postmarkトークンがスクリプト内・引き継ぎ資料内に露出） | ローテーション推奨のまま | Secrets Manager 等での管理を移行の必須要件に |
| H11 | **チタンAPIが認証なし** | チタン側へ認証/暗号化を依頼中 | 移行と同時期の論点。新サーバー側は固定IP化できるため**IP制限**等の選択肢が生まれる（チタン側対応が前提。断定不可） |
| H12 | **画像HEADチェックがfetch予算を消費**・画像は透かし問題で凍結 | ENABLE_IMAGES=false | 画像の取得・検証・（必要なら）加工プロキシはサーバー側なら制約なく実装可能 |
| H13 | **125,000件上限のための90日削除ローテ** | auto_archive が2日おきに削除 | 移行先ではレコード上限が実質消えるため、**「削除」を「アーカイブ/非表示」に変えられる**。紹介履歴を消さずに済めば H8 の重複紹介防止も強くなる（90日超えの再紹介が現行は防げていない点に注意） |

補足（移行で自動解消はしないが記録）: 利回りフィールドの大規模欠落（過去に配信不発の原因）、toC/toB の築年不等号の逆転（1.2の要確認）、「バス・徒歩」条件が読み取りのみで未使用、という**データ品質・仕様確定系**の課題は、移行作業とは独立に仕様確認が必要。

## 3. 移行アーキテクチャの論点（断定しない）

07-15 定例（新サーバー協議）の前提整理。**月1万円以内**という費用枠が7/7に示されている。

### 論点1: 取得ワーカーの分離
- 物件取得（①）を Airtable Automation から最初に切り出す案。事故履歴（H1/H2/H6）が集中しており、切り出し効果が最大。
- 実行形態の選択肢: cron型（EC2/軽量VPS上のcron、ECS Scheduled Task、Lambda+EventBridge 等）。38エリア×6時間ごと・1回あたり数十秒〜数分の処理であり、要求スペックは小さい。
- 過渡期の書き込み先は Airtable REST API（typecast有効・バックログ回収スクリプトで実績あり）にする案と、最初から新DBに書いて Airtable へ同期する案がある。**段階移行（2〜3ヶ月Airtable併用）方針と整合するのは前者→後者の順**か。

### 論点2: 掲載終了チェッカー（新設）
- 現行に存在しない機能（H4）。案: (a) inai を大きくした定期全量照会と突き合わせて「消えた物件」を終了扱い、(b) 公開URLの生存確認、(c) チタン側に終了フラグAPIを依頼（村田さん/タクトと直接連絡体制あり）。
- どの案も**チタン側の仕様確認が先**（終了物件がAPIレスポンスからいつ消えるか未確認）。

### 論点3: 通知・監視基盤（新設）
- 最小構成: 実行失敗・新規0件24時間・未知トークン検出・Postmark送信失敗をメール/Chatwork へ。v2.9 の output サマリ項目（created/updated/writeErrors/unknownTokens/aborted）がそのまま監視メトリクスの候補。
- GitHub Actions（auto_archive）には失敗通知の実装実績が既にあり、方式を揃える選択肢もある。

### 論点4: べき等性・リトライ・トランザクション
- URL unique 制約＋upsert（H7）、履歴=物件ID×顧客ID（H8）、送信前履歴記録 or 送信ログの一意キー（H9）、エリア単位リトライ＋指数バックオフ（H6）。
- Postmark 側の冪等性（同一人物への同日重複送信の防止）をアプリ層でどう担保するかも設計項目。

### 論点5: マッチング・配信の移行順序
- toC 配信（②）は「動いていて収益に直結」のため、取得（①）より後に移す案が保守的。逆に「マッチング精度検証・トラッキング強化（クリック率0.9%改善）をやるなら新基盤で作り直す方が早い」という考え方もある。優先順位は古谷氏整理（可視化→クリック改善→マッチング精度）と接続して判断。
- ⑥（企業メール・OFF）は**移行対象に含めるか廃止するか**を岩下様と確定させる（1年近く未稼働。手作業運用で回っている実態）。

### 論点6: Airtable に残すもの / 移すもの
- **残す候補（当面）**: Interface（toBボタン・営業の確認画面）、`★個人投資家`・`★企業一覧` の顧客マスタUI、`物件エリア` のメンテUI。1LC側の日常操作面であり、段階移行方針とも一致。
- **移す候補（先行）**: ① 取得ワーカー（論点1）、`チタン物件一覧` の一次格納（25,000件超・全書き込み負荷の発生源）、履歴の長期保存（H13。Airtable には直近90日分だけミラーする等）。
- 中間形態では「新DB=真実源、Airtable=ビュー/操作面（同期ミラー）」という役割分担がありうるが、**同期の方向・頻度・競合解決は未設計**。Fillout→Airtable の希望条件更新フローをどこで受けるかも同枠の論点。
- Airtable 解約可否の判定条件（何が移り終わったら解約できるか）を定例で合意しておくと段階移行のゴールが明確になる。

### 論点7: コスト・運用主体
- 月1万円以内の枠。現行の固定費要素: Airtable Business（段階移行中は併用）＋Postmark。新規: サーバー/DB/監視。
- 保守の運用主体（Walkers naru/池田の分担、岩下氏のClaude Code並行運用との整理）、およびチタン/タクト（村田さん）との技術窓口をどう使うかは体制論点として別途。

## 4. 移行前に確定させる質問リスト（岩下様・チタン様向け）

1. 築年数条件の正: toC「築 years 年**超**」/ toB「築 years 年**以内**」の逆転はどちらが正か（1.2 要確認）
2. ⑥ 企業メール自動配信は復活させるか廃止か
3. 掲載終了物件は チタンAPI レスポンスからいつ・どう消えるか（掲載終了チェッカーの設計前提）
4. チタンAPI の認証（IP制限・キー等）対応の予定と方式
5. 履歴の保持期間: 90日削除は Airtable 上限対策だったが、移行後は長期保持に変えてよいか（90日超の再紹介防止にも効く）
6. `viwPDkWFB8zHPraRL`（toB母集団view）の絞り込み条件の実体（Airtable UI から吸い出し要）
7. 5,000万円フィルタの境界（未満/以下）の最終確定（config.py 上も「岩下さん確認待ち」注記あり）
