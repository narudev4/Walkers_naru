# メール→物件ページの識別・個人情報保護・計測アーキテクチャ

2026-08-01 作成。A案（素のURL）・B案（リダイレクタ）がいずれも不採用となったため、
3つのモデル（gpt-5.5 / Claude Sonnet / Claude Haiku）に独立で設計させ、その結果を統合したもの。

---

## 1. B案がダメだった理由（ここが出発点）

**302 のリダイレクト先URLはアドレスバーに表示される。**
`/p/{token}` → `/property/R123?uid=recABC` と転送する限り、
リダイレクタを挟んでも**最終的に uid が丸見えになり、A案と同じ状態**になる。

隠すべきなのは「URL文字列」ではなく**識別子の運搬手段**。
3モデルとも同じ結論に到達した:

> **リダイレクト時に HttpOnly Cookie を発行し、転送先URLからは識別子を完全に落とす。**

Cookie はアドレスバー・ブラウザ履歴・スクリーンショット・共有されたURLのいずれにも現れず、
HttpOnly なので JavaScript からも読めない（XSS でも盗めない）。

## 2. 却下: HMAC 署名トークン方式（Haiku 案）

「Automation 側で uid/pid/exp を HMAC 署名し、DBを引かずに検証する」案。
fetch 増分ゼロという長所があるが、**前提が成立しない。**

| 前提 | 実態 |
|---|---|
| `process.env.TOKEN_SECRET` で秘密鍵を注入できる | **Airtable Automation に環境変数・シークレット機能は無い。** 現行 `02b_メール配信を行う.js` の Postmark トークンも `const POSTMARK_API_TOKEN = '...'` の平文定数で保持されている（＝これが H10 / ローテーション未実施の課題そのもの） |
| `crypto.subtle` が使える | 未検証 |

秘密鍵が平文でスクリプトに載るため、**Airtable にアクセスできる人（1LC 様のカスタマーサポートアカウント含む）は
任意の投資家のトークンを偽造できる**。しかも署名方式は**失効ができない**。
DB 引き当て方式なら「そのトークンだけ無効化」で済む。よって不採用。

## 3. 採用: 2段構え

### Step 1 — Airtable を一切触らずに R1〜R3 を満たす（先行実装）

メールのリンクは**今のまま**（`?uid=...` 付き）でよい。AWS 側だけで完結する。

```
/property/R123?uid=recABC&src=email  ← メールから着地
   ↓ Route Handler / middleware
   1. sessions テーブルに不透明な session_id を作成（→ record_id をサーバー側だけで保持）
   2. Set-Cookie: sid=<opaque>; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=90d
   3. 307 → /property/R123?src=email   ← 識別子ゼロのURL
```

**なぜ Step 1 を Airtable 変更ゼロで設計するか**
現在この Automation は 182回連続で "Failed to run" しており（`30_適用記録` 追記3）、
180秒の実行時間上限が現に問題になっている。
**この状態で投資家1人あたり +1 fetch を足すのは危険。** Airtable 側の変更は引越し後に回す。

**やること**

| # | 内容 |
|---|---|
| 1 | DynamoDB `sessions` テーブル新設（PK: `session_id` / 属性: `record_id`, `created_at`, `ttl`）。TTL で自動掃除 |
| 2 | 着地時に Cookie を発行して uid を落とすリダイレクト（Route Handler 1本 or middleware） |
| 3 | **`GET /api/investor/{uid}` を廃止** し `GET /api/investor/me` に置換。Cookie の `sid` からサーバー側で解決する。クライアントは record_id を一切知らない・送らない |
| 4 | `POST /api/events` を Cookie ベース識別に変更（フロントから uid を受け取らない） |

**Cookie の中身は record_id ではなく不透明な session_id にする。**
HttpOnly は JS からのアクセスを防ぐだけで、devtools・ブラウザ拡張・端末を触れる第三者からは Cookie 値が読める。
ここに record_id を直置きすると「URLに出さない」だけで同じ穴が別の場所に開く。

**SameSite=Lax。** メールクライアントからのクリックはトップレベルナビゲーション＋GET なので Lax でも送信される。
Strict にすると外部からの遷移で送られず再訪時の継続性が壊れる。`Secure` `HttpOnly` は必須。

**この Step 1 だけで B-22（内部遷移で uid が消える）も解決する。**
Cookie は内部遷移で自動的に送られるため、sessionStorage の実装が不要になる。
そもそも sessionStorage は (a) 302 の時点では書けない (b) サーバーから読めない (c) XSS で盗める、の3点で不適。

### Step 2 — 引越し後に失効と有効期限を獲得する

```
/p/{token}  →  links テーブル参照（expires_at / revoked）→ セッション発行 → 302
```

- `links` に `revoked` 属性を追加。配信停止希望者は即時失効できる
- リンクトークンの寿命（長め・例395日）とセッションCookieの寿命（90日）を分離する
- メールは数ヶ月受信箱に残るため、失効の概念は必要。ただし Step 1 が動いていれば緊急性はない

**Step 2 で「Automation からトークン発行APIを叩く」問題は、引越しが済めば消える。**
マッチングが AWS 側で走るようになれば、リンク発行は同じプロセス内でできる。
M2M 用の `/api/links/issue`（Bearer 認証の口）を作る必要すらなくなる。
＝ **Airtable に残したまま計測を作り込むのが一番コストが高い**。急いで作らない方が安い。

## 4. プリフィル（R4）— 決める必要がある1点

**リンクを持つ人に氏名・メール・電話を表示すれば、転送された第三者にも見える。**
「URLを持っていること」は本人証明にならないので、ここは避けられない選択になる。

| 案 | 摩擦 | 個人情報 | 弱点 |
|---|---|---|---|
| **A: 画面に出さず、送信時にサーバーが付与**（推奨） | ゼロ | 表示しない＝漏れない | 第三者が本人を騙って問い合わせを送れる（害は小さく検知も可能） |
| B: メール認証してから自動入力 | 大 | 最も安全 | CV率が落ちる。Phase2 のログインと統合すべき |
| C: 名前だけ「○○様」表示、連絡先は本人が入力 | 小 | 名前だけ露出 | 入力の手間が残る |

推奨は A。フォームに「ご登録の連絡先で送信されます」と明記すれば説明もつく。
B は Phase2 のマジックリンク認証と同時に入れるのが自然。

## 5. 計測データに持たせる区別

転送されたリンクの閲覧を元の投資家の行動として数えることは原理的に避けられない。
イベントに確度を持たせておく。

- `link_attributed` — メールのリンク経由（本人らしい、が未確認）
- `verified` — 本人確認済み（Phase2 のログイン後）
- `anonymous` — 識別なし

## 6. ドメインの注意点（R8）

`amplifyapp.com` は Public Suffix List 登録済みドメイン。
`Domain` 属性を省略すればブランチサブドメイン限定の host-only Cookie として**正常に動く**（実害なし）。

**唯一の実害は独自ドメイン切替時。** amplifyapp.com で発行済みの Cookie は新ドメインに引き継がれず、
発行済みのメール内リンクも切れる。

→ **暫定運用でも `*.amplifyapp.com` のURLをメールに載せてはいけない。**
ドメインが決まるまでは現行の土地大臣URLを載せ続ける（AWS 側と干渉しない）。

## 7. Phase2 への発展（R6）

Step 1 で作る `sessions` テーブルと Cookie の仕組みは、**そのまま Phase2 のログイン基盤になる**。
既存の「ID/PW 自動送付」は機能不全のため、Phase2 はマジックリンク（使い捨てリンクをメール送信）で作り直す。
Step 1 は捨てる作業にならない。

## 8. 実装順序

1. `sessions` テーブル新設
2. 着地時 Cookie 発行 + uid を落とすリダイレクト ← **ここまでで R1〜R3 が成立**
3. `/api/investor/me` へ置換、フォームの呼び出し先切替。旧 `/api/investor/{uid}` は動作確認後に削除
4. `/api/events` を Cookie 識別に変更 ← R1 の計測が完成
5. （引越し後）`/p/{token}` + `links.revoked` + 失効画面
6. （Phase2）`sessions` をログインセッションへ拡張

2 の時点で「個人情報が漏れる」という一番の不満が消える。3・4 はその上の互換維持作業。

## 10. 3モデルの一致点・相違点（記録）

| 論点 | gpt-5.5 | Sonnet | Haiku |
|---|---|---|---|
| リダイレクタで HttpOnly Cookie を発行し最終URLから識別子を落とす | ○ | ○ | ○ |
| Cookie の中身を不透明な session_id にする（record_id を入れない） | ○ | ○ | ✕（record_id を直置き） |
| PII 開示に追加の本人確認を要求する | ○（メール認証） | △（Cookieで解決） | ✕（リンク所持で開示） |
| Airtable に HMAC をやらせない | ○ | ○ | ✕（前提が成立しない） |
| 失効・有効期限の設計 | ○ | ○（リンクとセッションを分離） | △（署名内 exp のみ・失効不可） |
| PSL / ドメイン切替で Cookie が切れる指摘 | ○ | ○（PSL の意味まで正確） | △ |
