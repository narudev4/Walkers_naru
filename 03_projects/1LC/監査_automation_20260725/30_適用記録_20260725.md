# 追記: 2026-07-26 — 毎日の実行失敗（180秒タイムアウト）を発見・対処

## 発見
7/26 朝の実行結果を確認した際、この Automation が **2026-07-10 以前から毎日
"Failed to run"** になっていることが判明した（私の変更前から継続）。

実行履歴のエラー本文:
```
Your script exceeded the 180s run time limit.
失敗した繰り返し: 希望条件ID 1515（吉田 理 様）
  years: 9999 / area: 埼玉県+東京都の96市区町村 / budgetLower: 100,000,000
```

## 原因
築年数が `9999`（フォームの「下限無し」）の投資家は、条件 `age > 9999` により
**1件も一致しない**。そのため 5件で break できず 25,908件を最後まで走査し、
180秒の上限を超過してスクリプトが失敗 → **Automation 全体が停止し、
以降の投資家にはメールが届かない**。

つまり「築年数の反転」は配信内容の問題であると同時に、**配信そのものを
止めている原因**でもあった。

## 実測（日別に「実際にメールが届いた投資家数」／紹介許可ONは322人）

| 日付 | 届いた人数 | 割合 |
|---|---|---|
| 2026-07-17〜20 | 約180人 | 約56% |
| 2026-07-21〜25 | 約85人 | 約26% |

7/20 のバックログ一括登録（+2,786件）で走査対象が増え、より早い順番の投資家で
180秒を超えるようになったため、届く人数が半減したと考えられる。

## 対処（v3.1・本番反映済み）
v3 で追加した `sort()`（getCellValue を伴い高コスト）が走査時間をさらに
悪化させていた（実測 3.6分/人 → 4.7分/人）ため、以下2点で走査コストを削減:

1. `sort()` を廃止し `reverse()` に変更（getCellValue 呼び出しゼロ）
2. 掲載終了の判定をループ先頭に移動し、他の値を読む前に `continue`
   （13,779件＝53%を1回の getCellValue で早期に除外できる）

## 残る根本問題
上記は緩和であり、根治ではない。`years=9999` の投資家は依然として全件走査する。
**築年数の条件を修正すれば（9999/-1 を「条件なし」として扱う）、これらの投資家は
即座に5件見つけて break するため、タイムアウトは構造的に解消する。**
→ 岩下様への確認（新規登録フォームの保存値）を優先度「高」に引き上げるべき。
