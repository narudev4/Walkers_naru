## 0-B. 岩下様がログインし、画面共有で進める場合

4. 会議ツールが**リモート操作に対応していれば操作権をもらう**（Google Meet・Zoom は可）。

   **デバイスが登録されていたら削除**（naru が持っていないため入れない）。無ければ何もしない

> naru の IAM ユーザーが見つからない場合は、岩下様に新規作成してもらう。
> 「ユーザーの作成」→ 名前を入力 → 「AWS マネジメントコンソールへのユーザーアクセスを提供する」にチェック

## 1. naru の権限（管理者）

既存の IAM ユーザーがあるならそれを使う（パスワード紛失中なので再設定する）。

- アタッチするポリシー: **`AdministratorAccess`**（AWS 管理ポリシー）
- 加えて **`DenyNonTokyoRegion`**（下記）をインラインで付ける

`AdministratorAccess` だけを付けると「国内リージョン限定」の要件が担保されなくなる。
1LC 様には「IAM ポリシーで他リージョンを Deny して担保している」と回答済み
（システム周り決定事項 2026-07-16）なので、管理者にも同じ制約を残す。

### DenyNonTokyoRegion（インラインポリシー）

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "TokyoRegionOnly",
      "Effect": "Deny",
      "NotAction": [
        "iam:*",
        "sts:*",
        "organizations:*",
        "account:*",
        "support:*",
        "budgets:*",
        "ce:*",
        "cur:*",
        "route53:*",
        "route53domains:*",
        "cloudfront:*",
        "cloudformation:ValidateTemplate"
      ],
      "Resource": "*",
      "Condition": {
        "StringNotEquals": { "aws:RequestedRegion": "ap-northeast-1" }
      }
    }
  ]
}
```

**NotAction に並べたものは「グローバルサービス」で、リージョンを持たない。**
AWS はこれらの API 呼び出しを内部的に `us-east-1` として扱うため、除外しないと
東京リージョン限定の Deny に巻き込まれて使えなくなる。

特に **Route 53 は必須**。サブドメインを Route 53 に委任する案（`40_AWSで作るもの一覧.md` 参照）を
採る場合、除外していないと DNS の設定が一切できなくなる。

未除外で意図的に残しているもの:

- **`acm:*`** — ACM はリージョナルサービス。Amplify の独自ドメイン機能は
  ap-northeast-1 の ACM を自分で発行するため東京だけで足りる。
  将来 CloudFront を自前で前段に置く場合のみ us-east-1 の証明書が必要になるので、
  そのときに `"acm:*"` を NotAction へ追加する

### 適用後の動作確認

1. **東京が使えること**: マネジメントコンソールで DynamoDB のテーブル一覧が見える
2. **他リージョンが拒否されること**: 右上のリージョンを「バージニア北部」に変えて
   DynamoDB を開く → アクセス拒否のエラーが出れば正しく効いている
3. **Route 53 が使えること**: Route 53 のホストゾーン一覧が開ける

3 が開けない場合は NotAction の `route53:*` が抜けている。

### 締め出しの逃げ道

インラインポリシーは**自分で削除できる**（`iam:*` を Deny の対象外にしているため、
IAM の操作だけは常に通る）。誤って業務が止まっても、同じ画面からポリシーを消せば戻せる。

それでも不安なら、**Deny を付けない管理者ユーザーをもう1つ作っておく**（break-glass 用）。
今回のように「管理者が1人しかいなくて詰む」状態を二度と作らないための保険になる。

## 2. 古谷さん（daiki.furutani）の権限

**`41_iam-policy-deployer-修正版.json`** をインラインポリシーとして貼る。

元の `infra/iam-policy-deployer.json` は**そのままでは足りない**。
CloudFormation テンプレート（`infra/amplify-hosting.yaml`）が作るものと突き合わせた結果:

| テンプレートが作るもの | 元のポリシー | 修正版 |
|---|---|---|
| Amplify アプリ・ブランチ | ✅ | ✅ |
| IAM ロール `*-amplify-service-role` | ✅ | ✅ |
| IAM ロール **`*-amplify-compute-role`** | ❌ Resource パターンに一致しない | ✅ パターンを追加 |
| **DynamoDB 4テーブル**（events / inquiries / links / settings） | ❌ `dynamodb` の許可が無い | ✅ 追加 |
| **PITR の有効化**（4テーブルすべて `PointInTimeRecoveryEnabled: true`） | ❌ | ✅ `UpdateContinuousBackups` を追加 |

元のポリシーのままだと**スタック作成が途中で失敗し、岩下様に再度ログインを依頼することになる。**

検証用の Walkers アカウントでは naru が管理者だったため、この2つが
「明示的に必要な権限」として表面化しなかったと考えられる。

### 修正版の Resource パターンについて

- IAM ロール: `*-amplify-service-role` / `*-amplify-compute-role` の2パターン。
  AppName に依存しないので、アプリ名を変えても効く
- DynamoDB: `table/1lc-property-*`。**AppName を変える場合はここも変える**
  （CloudFormation の `AppName` パラメータの既定値が `1lc-property`）

## 3. 権限が正しいことの確認方法

古谷さんに以下を実行してもらう。すべて通れば権限は足りている。

```bash
aws sts get-caller-identity
aws cloudformation deploy \
  --template-file infra/amplify-hosting.yaml \
  --stack-name onelc-property \
  --capabilities CAPABILITY_NAMED_IAM \
  --region ap-northeast-1 \
  --parameter-overrides OauthToken=<GITHUB_TOKEN> AirtableToken=<AIRTABLE_TOKEN> \
  --no-execute-changeset
```

`--no-execute-changeset` を付けると**実際には作らずに、作れるかだけ**を確認できる。
ここで Access Denied が出れば、その API を権限に足す。

## 4. ログインできなかった場合（フォールバック）

Walkers アカウント（926634327651）で運用を継続し、AWS 実費を運用保守費に上乗せして請求する。

技術的には問題なく動く。ただし**次の2点は先に整理しておく必要がある。**

### (1) 保守契約の引継ぎ条項との整合

2026-07-13 の構成報告書で 1LC 様へ次の通り回答している。

> AWS アカウントの root／請求責任者は**岩下社長**で開設。Walkers 側は IAM ユーザー
> （限定権限）で作業し、**保守運用契約の引継ぎ条項（第17条の2）と整合させる**。

Walkers アカウントで運用すると、契約終了時に 1LC 様がインフラを引き継げない。
アカウント名義を岩下様にした設計は、まさにこれを避けるためだった。

→ **恒久ではなく暫定として合意し、移管する条件（例: ルートアクセスが確保できた時点）を
明文化しておく。** 明文化しないと暫定がそのまま恒久になる。

### (2) 個人情報の保管場所

`inquiries` テーブルには問い合わせ者の**氏名・メールアドレス・電話番号**が入る。
これは 1LC 様の顧客の個人情報であり、Walkers のアカウントに保管されることになる。

→ 受託者としての取扱いを合意しておく（どちらでも運用可能だが、暗黙にしない）。
