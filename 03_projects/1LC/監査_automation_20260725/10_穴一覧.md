## 重大度: 高

### A-01｜掲載終了物件がマッチング・メール送信対象のまま（既知3・4の残存確認）
- **対象**: 02a_物件データのマッチング.js:20, 60-71 ／ 04_企業物件マッチング.js:17-19, 61-83
- **内容**: 02a は `table.selectRecordsAsync()` で **view 指定なし・全レコード**を母集団にし、マッチ条件（履歴・エリア・種別・構造・価格・利回り・築年・URL有無）に**鮮度条件（更新日・新規登録日）が一切ない**。04 は view `viwPDkWFB8zHPraRL` を通すが、view の絞り込み内容はコードから検証不能（掲載中を判別できるフィールド自体が存在しないため、view でも絞れないはず）。掲載終了の検知機構はシステム全体に存在せず、削除は auto_delete の「更新日90日超 or 5,000万未満」のみ。
- **実害シナリオ**: 掲載終了（成約済）物件が最長90日間マッチング対象に残る → 実測で紹介物件の30〜55%が掲載終了、顧客クレーム発生（現実に発生済み）。
- **修正案**: ①inai なしの全掲載スイープ（full_sync.py の titan_fetch 流用）を定期実行し、チタン物件一覧に「最終確認日」を刻む ②「最終確認日が直近N日以内」をマッチ条件に追加 ③02b の送信直前に URL 生存 or 最終確認日の再検証を入れる（二重ガード）。
- **緊急度**: 今すぐ（クレーム直結）。

### A-02｜「過去紹介済｜成約済」フィールドが存在するのに誰も参照しない
- **対象**: 02a 全体（参照ゼロ）／ 04 全体（参照ゼロ）。フィールド実在は REST GET で確認済み
- **内容**: 手動で成約済とマークする受け皿はあるが、マッチング条件に含まれていないため、マークしても紹介が止まらない。書き込む自動経路も見当たらない（v2.9 のサニタイザ対象として名前が挙がるのみ）。
- **実害シナリオ**: 運用側が「成約済にしたのに送られ続ける」。クレーム対処の手段が実質存在しない。
- **修正案**: 02a/04 の条件に `過去紹介済｜成約済 が空欄` を追加（1行）。A-01 の恒久対策が入るまでの応急処置として最速で効く。
- **緊急度**: 今すぐ（コード1行で応急止血できる）。

### A-03｜「古いレコード優先」の選定バイアス（新発見）
- **対象**: 02a:41-42（`matchedRecords.length >= 5` で break）／ 04:42-43（`>= 10` で break）
- **内容**: `selectRecordsAsync()` の返却順（実質作成順＝古い順）で先頭から走査し、5件/10件に達したら打ち切る。つまり**最も古い＝掲載終了確率が最も高い物件から優先的に紹介**する構造。ソート・ランダム化なし。
- **実害シナリオ**: 掲載終了率30〜55%という異常値の増幅要因。新着の生きた物件が母集団後方にいて永遠に紹介されないケースも起きる。
- **修正案**: マッチ候補を全走査して `新規登録日`（or 更新日）降順に sort してから上位N件を採用。全走査が重い場合は view で降順ソートを定義してそこから読む。
- **緊急度**: 今すぐ（A-01 と同時に入れると効果大）。

### A-04｜空欄・非数値の希望条件で「静かに0件マッチ」（新発見）
- **対象**: 02a:36-39, 65-69 ／ 04:36-38, 66-82
- **内容**: `parseFloat(budgetUpper)` 等が空欄・「こだわらない」・全角数字なら NaN になり、`recordPrice <= NaN` は常に false → **全物件不一致**。エラーは出ず、02b は「No matched records. Skipping email.」で正常終了扱い。02a は `profitUpper` まで必須（上限未入力の投資家は全滅）。`years` が空欄/こだわらないでも同様に全滅。
- **実害シナリオ**: 希望条件の一部を空欄にした投資家には**永遠に1通もメールが届かず、誰も気づかない**。「配信されていない」系の静かな機会損失。
- **修正案**: 各数値の parse 後に `Number.isFinite()` を判定し、NaN は「条件なし＝制約をスキップ」に倒す（01 の `num()` と同思想）。0件マッチが連続する投資家の検知ログも追加。
- **緊急度**: 1週間以内。

### A-05｜築年条件の向きが 02a と 04 で逆（新発見・仕様確認要）
- **対象**: 02a:69（`age > parseFloat(years)`）／ 04:82（`age <= parseFloat(years)`）
- **内容**: 04（企業）は「築 years 年**以内**」、02a（個人）は「築 years 年**超**」。同じ `years` という入力名で判定の向きが逆。02a のコメントは「マッチングロジック(7条件)は一切変更なし」とあり、意図的な差か移植ミスかコードからは判別不能。個人投資家向けが「指定より古い物件だけマッチ」だとすると通常の希望条件と逆。
- **実害シナリオ**: 02a が誤りの場合、個人投資家は「希望より古い物件だけ」を受け取り続けている（新しめ希望の顧客ほど紹介の質が壊れる）。
- **修正案**: フォームの文言（「築◯年以内」か「築◯年以上」か）と突き合わせて正しい向きを確定し、両スクリプトの意味を統一・コメント明記。
- **緊急度**: 1週間以内（仕様確認は今すぐ）。

### A-06｜01 の無条件更新が既存値を null/[] で消す → auto_delete との合わせ技で掲載中物件を削除（新発見）
- **対象**: 01_エリア別物件取得_v2.9.js:178-192（fields に常に 価格/建物構造/種別 キーを含める）, 266-291（既存は無条件更新）／ config.py:10（`{価格} < 50000000`）
- **内容**: 更新時、チタン応答で価格が「要相談」等なら `価格: null` が**既存の正しい価格を消す**。Airtable の数値比較で BLANK は 0 扱いのため、auto_delete Phase 1 の `{価格} < 50000000` に該当し**掲載中物件が次回実行で即削除**される。同様に、建物構造の全トークンが未登録なら `sanitizeMS` が `[]` を返し**既存の構造値を空欄で上書き**（v2.9 が「該当項目のみ空欄で登録」と明記している挙動）。空欄になった物件は、構造を指定した顧客のマッチ対象から消える（A-04/B-02 参照）。実測: 現在 価格 BLANK は0件（未発火）だが、建物構造 BLANK は実在。full_sync.py:191 は「None/空は送らない」対策済みで、01 だけが未対策。
- **実害シナリオ**: チタン側の一時的なデータ欠落1件で、掲載中物件の削除（＝紹介機会の恒久喪失＋履歴リンク切れ）が起きる。
- **修正案**: ①01 の更新ペイロードから null/[] のキーを除外（full_sync と同じ `v not in (None,"",[])` フィルタ）②auto_delete の式を `AND({価格}>0, {価格}<50000000)` に修正し「価格空欄=削除」を止める。
- **緊急度**: 1週間以内（①②とも小改修）。

### A-07｜「更新日」が掲載状態の代理指標として両方向に壊れている（既知3の構造的裏面）
- **対象**: 01:66（`inai: 2` — 直近2日に掲載/更新された物件しか取得しない）／ config.py:10
- **内容**: 01 は inai=2 のため、**継続掲載中でもチタン側で更新のない物件は fetch に現れず、Airtable の更新日が進まない** → 90日で「掲載中なのに削除」。逆に掲載終了しても更新日はそこで止まるだけなので **90日間はマッチ対象に残留**。「更新日90日超=掲載終了」という auto_delete の前提が両方向に誤る。full_sync.py の docstring 自身が「取りこぼしの原因は inai:2」と認定している。
- **実害シナリオ**: (a) 長期掲載の優良物件が90日で消えて紹介不能、(b) 成約済が90日間紹介され続ける（A-01 の根本原因）。
- **修正案**: A-01 の「最終確認日」方式に置き換え、auto_delete の削除条件も「最終確認日ベース」に変更。掲載終了は削除ではなく「掲載終了フラグ」でソフトデリートにする（履歴リンク切れも防げる）。
- **緊急度**: 今すぐ設計、実装は A-01 と一体で。

### A-08｜03/05: エラー握りつぶし + 1回失敗後の全滅連鎖が残存（既知1・2の残存）
- **対象**: 03_紹介履歴作成.js:10-17 ／ 05_企業物件紹介提案.js:10-17
- **内容**: `createRecordAsync` を try/catch で包み `console.error` に流すのみ。Airtable Automation は書き込み1回失敗で以降 "Request processing is disabled" になるため、**1件目の失敗で残り全件も失敗し、それが全部握りつぶされて Automation は成功表示**になる。01 が受けた事故（既知1+2）と同一構造。select 書き込みは無いので「未登録select値」起点にはならないが、リンク先レコード削除直後（auto_delete との競合）や無効 ID で同じ連鎖が起きる。
- **実害シナリオ**: 履歴が丸ごと作られない日が発生 → historyInfos が更新されず**同じ物件が翌日以降も再紹介され続ける**。誰も気づけない。
- **修正案**: catch 内で失敗件数をカウントし、最後に `output.set("errors", n)` + 失敗があれば **throw して Automation を明示的に失敗させる**。失敗通知（B-12）とセット。
- **緊急度**: 1週間以内。

### A-09｜Postmark サーバートークンのハードコード（セキュリティ）
- **対象**: 02b_メール配信を行う.js:20 ／ postmark_code/v2_test_send.js:10（同一トークン `<<REDACTED>>`。v3_email_script.js / v3_test_send.js にも同様の記載が濃厚）

- **実害シナリオ**: リポジトリ流出・画面共有・引き継ぎ資料経由でトークンが漏れると、`info@1lcinc.com` 名義で任意のメールを第三者が送信可能（フィッシング・ドメイン評判毀損）。
- **修正案**: Postmark でトークンをローテーションし、Airtable Automation の input variable（または AWS 移行後は Secrets Manager）に移す。Git 履歴からの除去（もしくはローテーション済みであることの記録）。
- **緊急度**: 1週間以内（ローテーションは即日可能）。

### B-02｜建物構造・種別の「完全一致」比較と空欄の扱い
- **対象**: 02a:46-47, 63-64 ／ 04:47, 72-80
- **内容**: `getCellValueAsString("建物構造")` は multi-select を**カンマ結合した1本の文字列**で返すため、物件が複数値（例「鉄骨造, 鉄筋コンクリート」）を持つと `structures.includes(結合文字列)` は一致せず**サイレント不一致**。また空欄("")は「こだわらない」以外の顧客には常に不一致 → v2.9 サニタイザが未登録値を間引いて空欄化した物件（実在確認済み）は、構造を指定した全顧客のマッチ対象から消える。
- **実害シナリオ**: 物件が正しく登録されているのに紹介されない（静かな機会損失）。未登録select値1件 → 空欄化 → マッチ除外、という既知1の「弱毒化した後遺症」。
- **修正案**: `record.getCellValue()` で配列を取り、`recordValues.some(v => structures.includes(v.name))` の重なり判定に変更。空欄物件の扱い（除外か通すか）は仕様として明文化。
- **緊急度**: 1週間以内。

### B-03｜土地権利（借地）の除外がマッチング側に無い
- **対象**: 02a 条件式（61-71）／ 04 条件式（61-83）— いずれも土地権利を参照せず
- **内容**: v2.8 の設計で「既存の借地レコードは削除せず、岩下様側のマッチングシステムで除外する」前提を置いたが、監査対象のマッチングには土地権利の条件が無い。01 は新規作成のみフィルタするため、既存の旧法賃借等レコードはマッチ対象のまま。
- **実害シナリオ**: 「所有権のみ取り込む」運用方針に反し、借地物件が個人投資家・企業に紹介される。
- **修正案**: 02a/04 に `土地権利が空欄 or 所有権` の条件を追加（v2.8 と同じ「空欄は通す」ルール）。
- **緊急度**: 1週間以内。

### B-04｜紹介済み判定が「メール埋め込み」文字列一致で脆い
- **対象**: 02a:27-32, 61 ／ 04:27-32, 63
- **内容**: 紹介済みかどうかを record ID ではなく `メール埋め込み`（formula 文字列）の完全一致で判定。①01 が価格等を更新すると文字列が変わり**同じ物件が再紹介**される ②物件レコードが auto_delete で消えると履歴側 lookup も消え、判定材料が消失 ③auto_delete Phase 2 が90日で履歴自体を削除するため、90日を超えた再掲載物件は再紹介される（これは仕様かもしれないが明文化なし）。
- **実害シナリオ**: 「同じ物件が何度も届く」クレーム。掲載終了クレームと複合すると信頼毀損が加速。
- **修正案**: 履歴を `airtable_record_id`（または問合わせ番号）ベースの判定に変更。履歴テーブルに物件の問合わせ番号をテキストで冗長保存し、物件削除後も判定可能にする。
- **緊急度**: 1週間以内。

### B-05｜履歴 webhook の HTTP エラー未確認
- **対象**: 02a:147-151 ／ 04:104-113
- **内容**: 履歴作成 webhook への POST は `res.ok` を見ない。Airtable webhook 側が 4xx/5xx（レート制限等）を返しても fetch は throw しないため、**メールは送られるのに履歴だけ作られない**。逆にネットワーク例外で throw した場合は 02a ステップごと失敗し、repeat 中の**以降の投資家全員が未処理**になる（B-08）。
- **実害シナリオ**: 翌日以降の重複紹介（履歴欠落）または朝バッチの部分停止。どちらも無通知。
- **修正案**: `if (!res.ok)` でエラー内容を output に記録し throw。恒久的には「履歴作成 → メール送信」を1本のスクリプトに統合し webhook 連鎖自体を廃止（AWS 移行時）。
- **緊急度**: 1週間以内。

### B-06｜履歴作成がメール送信成功より先（順序の穴）
- **対象**: 02a:147-151（webhook＝履歴作成）→ 02b:90-92（Postmark 失敗で throw）
- **内容**: 履歴は 02a の時点で作成が走り、メール送信（02b）はその後。Postmark が失敗（inactive recipient・422・障害）すると、**顧客には届いていないのに紹介済み扱い**になり、その物件はその顧客に二度と紹介されない「欠番」になる。
- **実害シナリオ**: バウンス歴のある顧客ほど紹介機会が静かに消費されていく。
- **修正案**: 送信成功レスポンス（MessageID）を確認してから履歴を作る順序に変更。Airtable 内で順序変更が難しければ、履歴レコードに「送信結果」列を追加し、02b 成功時に更新・失敗時は未送信マークで再紹介可能にする。
- **緊急度**: 移行時対応で可（ただし設計要件に必ず入れる）。

### B-07｜エリア正規表現の未エスケープ・空配列・型不一致
- **対象**: 02a:35 ／ 04:35（`new RegExp("^(" + area.join('|') + ")")`）
- **内容**: ①area の値をエスケープせず正規表現化 → 括弧等の特殊文字が入るとスクリプト即死 or 誤マッチ ②area が空配列なら `^()` となり**全国の物件がエリア一致**扱い ③04 のコメントは「カンマ区切りの文字列として受け取る」だが `.join` は配列前提 — 実際に文字列が来たら `area.join is not a function` で**ボタン押下が丸ごと失敗**。
- **実害シナリオ**: エリア未設定の投資家に全国の物件が5件届く／企業マッチングが入力1つで無反応。
- **修正案**: 正規表現エスケープ関数を挟む・空配列時は「エリア条件なし」を明示分岐・入力を必ず配列に正規化（`typeof area === 'string' ? area.split(',') : area`）。
- **緊急度**: 1週間以内。

### B-08｜repeat 内の1人の失敗で以降の投資家全員が停止（自動化レベルの連鎖全滅）
- **対象**: 00_automation構造一覧.txt:10-12（Repeat for each → 02a → 02b）＋ 02a/02b の throw 経路全部（02a:35 の型エラー、02b:91 の throw 等）
- **内容**: Airtable の Repeat はイテレーション内のアクション失敗で run 全体が失敗し、残りのイテレーションは実行されない。1人の投資家の不正データ（area 型不一致、メールアドレス不正で Postmark 422 等）が、**その日その人以降の全投資家の配信を止める**。未登録select値1件で全滅した既知1と同型の「1件の毒データ→全体死」構造が、自動化レベルに残っている。
- **実害シナリオ**: 特定の1顧客の登録不備で、毎朝の配信が途中の同じ場所で止まり続ける（ソート順が安定なら毎日同じ人で死ぬ）。
- **修正案**: 02a/02b 内で throw しうる箇所を捕捉して「この投資家はスキップ + output に記録」に倒す（Postmark 失敗だけは記録必須）。恒久的には AWS 移行で per-customer try/catch のワーカーに。
- **緊急度**: 1週間以内。

### B-09｜Find records の100件上限（暗黙の制限）
- **対象**: 00_automation構造一覧.txt:9（Find records — ★個人投資家）
- **内容**: Airtable の Find records アクションは最大100件しか返さない仕様。紹介許可の投資家が100人を超えた瞬間、**101人目以降はサイレントに配信対象外**。
- **実害シナリオ**: 事業成長とともに静かに発火する時限爆弾。誰にも通知されない。
- **修正案**: 当面は投資家数の監視（100接近で警告）。恒久的には AWS 移行でページネーション取得に。
- **緊急度**: 監視は今すぐ（人数確認のみ）、実装は移行時。

### B-10｜debugLog が出力されない死蔵変数（既知2の亜種）
- **対象**: 02a:24, 102-105 ／ 04:24, 95-98
- **内容**: レコード単位の例外を `debugLog.push` で溜めるが、**console にも output にも一切出していない**。フィールド名変更などでループ内が全件例外になっても、外形上は「マッチ0件の正常終了」。
- **実害シナリオ**: フィールドのリネーム1つで全マッチングが静かに止まり、既知2（成功表示のまま停止）が再演される。
- **修正案**: `output.set("debugLog", debugLog.join("\n"))` + 件数が閾値超なら throw。
- **緊急度**: 1週間以内（1行）。

### B-11｜04 の利回り単位変換 ×100 が 02a と不整合
- **対象**: 04:38（`parseFloat(profitLower)*100`）／ 02a:38（変換なし）
- **内容**: 同じ「利回り」フィールド（例 8.5）に対し、04 だけ入力を100倍して比較。企業フォームの利回りが 0.08 形式なら正しいが、8（%）形式なら閾値800となり**全件不一致**。個人と企業でフォーム形式が違うのか、バグなのかコードから判別不能。
- **実害シナリオ**: 企業マッチングが利回り条件で常に0件（またはほぼ全通し）になっている可能性。
- **修正案**: 企業フォームの実データ形式を1件確認して確定。単位はコメントで明記。
- **緊急度**: 1週間以内（確認は10分）。

### B-12｜実行時エラーの通知経路がゼロ（誰も気づけない）
- **対象**: 全 Automation 共通（01 の output.set サマリも通知未接続 = v2.9 の「Phase 2 予定」のまま）
- **内容**: 各スクリプトの失敗検知手段は Airtable の実行履歴画面のみ。auto_delete（GitHub Actions）だけ失敗通知あり。エラー時に気づける人が誰か: **01=誰も（サマリ未通知）／02a・02b=誰も／03・05=誰も（握りつぶし+成功表示）／04=ボタンを押した本人が output を見れば／06=OFF**。
- **実害シナリオ**: 今回の4日間停止と同じ「静かな死」があらゆるスクリプトで再演可能。
- **修正案**: ①各スクリプト末尾の output（errors/matched/sent 件数）を Chatwork/メール通知アクションに接続 ②「24時間新規0件」「履歴作成0件の日」のデッドマンスイッチ（外部から Airtable を GET する監視 cron が確実）。
- **緊急度**: 今すぐ（デッドマンスイッチだけでも先行導入）。

### B-13｜冪等キーの不統一と重複レコード → 同一物件の重複紹介
- **対象**: 01:176-196（公開用URL キー）／ full_sync.py:212-217（問合わせ番号キー）／ 02a・04（マッチ結果の URL 重複排除なし）
- **内容**: 01 と full_sync/バックログ回収で冪等キーが異なるため、URL 表記が変わった同一物件は二重登録されうる（v2.6 で実際に 255 URL・422件の重複事故が発生した前歴あり）。02a はマッチ結果を URL で重複排除しないため、重複レコードがあれば**同じ物件が1通のメールに2枠**入る。01 の「実行開始時スナップショットと照合」設計上、並行実行でも重複が生じる。
- **実害シナリオ**: メール品質の毀損 + 履歴判定（B-04）のすり抜け。
- **修正案**: 冪等キーを問合わせ番号に統一（URL はパラメータ変動があるため不適）。02a に URL/問合わせ番号での dedup を1行追加。定期の重複チェック（GET のみ）を監視に追加。
- **緊急度**: dedup 1行は1週間以内、キー統一は移行時。

### B-14｜03/05 のリンク生成 `{id: record}` は Automation の UI 設定に依存（既知5の検証結果）
- **対象**: 03:13 ／ 05:13（`[{ id: record }]`）＋ 02a:150／04:110 の POST ペイロード（オブジェクト配列）
- **内容**: 02a/04 が POST する `matchedRecords` はオブジェクト配列だが、03/05 は要素をそのまま `{id: record}` に入れる。**実測では 2026-07-25 の履歴が正しい rec ID でリンクされており、現時点では動作している** — つまり webhook トリガーの input マッピング（UI 設定）が `matchedRecords[].airtable_record_id` の値リストを抽出していると推定される。ただしこの整合性はコード外の UI 設定1つに依存し、02a 側のペイロードキー名変更・マッピング再設定ミスで壊れた場合、エラーは catch で握りつぶされ（A-08）**履歴0件化が静かに起きる**。
- **実害シナリオ**: 将来の改修時に無自覚に破壊 → 重複紹介の再発。
- **修正案**: 03/05 側で `typeof record === 'string' ? record : record.airtable_record_id` と防御的に解決し、解決不能なら throw。UI マッピングの現設定をスクリーンショットで監査フォルダに保存。
- **緊急度**: 1週間以内（防御コード数行）。
