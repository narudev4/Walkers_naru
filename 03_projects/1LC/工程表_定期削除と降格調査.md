# 工程表A: 定期削除（自動アーカイブ）の実装

## A-0. 背景と目的

**問題**: Airtableベースは毎日自動的にレコードが増加する構造（物件取得4回/日 + マッチング履歴~300-900件/日）。今回の手動削除（76,059件）で上限を下回っても、**数週間〜1ヶ月で再び上限125,000件を超過**する。手動削除を毎月やるのは持続不可能。

**目的**: 「古いデータを定期的に自動退避・削除する仕組み」を構築し、レコード数を恒常的に上限以下に維持する。

**スコープ外**: プラン降格（工程表B）、Airtable以外のDBへの移行（将来施策）、Automationのロジック改修。

## A-2. 要件定義（所要: 1日）

### A-2-1. 削除対象テーブル・基準の確定

| テーブル | 削除基準（案） | 根拠 | 確認事項 |
|----------|---------------|------|----------|
| ★物件紹介履歴 | 紹介日時 < (実行日 − **90日**) | 3ヶ月超前の紹介は対象物件がほぼ消滅済み。dedup用途としても90日あれば十分（同一物件が90日以上経って再度マッチすることは再紹介として妥当） | 岩下様に「90日」で問題ないか確認。業務上「半年前の紹介履歴を見返す」ことがあるか |
| チタン物件一覧 | 更新日 < (実行日 − **90日**) AND 紹介履歴=空 | 3ヶ月以上フィードに来ない=売却/掲載終了。紹介履歴なし=孤児化ゼロ | 「90日」が短すぎないか。長期掲載の現役物件の誤削除リスク（ゼロ孤児セットなので実害は限定的） |

### A-2-2. 実行頻度の決定

| 頻度 | メリット | デメリット | 判定 |
|------|---------|-----------|------|
| **毎日** | 常に余裕が最大 | API負荷高、ログが膨大 | × 過剰 |
| **週1回**（推奨） | 余裕を維持しつつ負荷適正。例: 毎週日曜 03:00 JST | 最悪ケースで7日分(~6,300件)が溜まる | ◎ |
| **月1回** | 負荷最小 | 30日分(~27,000件)が溜まり、余裕が薄い月は超過しうる | △ |

### A-2-3. バックアップポリシーの決定

| 方式 | 内容 | コスト | 推奨 |
|------|------|--------|------|
| **A. CSVエクスポート → クラウド保存** | 削除対象レコードをCSV化しS3/Google Driveに保存 | ストレージ費用のみ（微小） | ◎ 推奨 |
| B. Airtableスナップショット | 手動でスナップショット取得 | 無料だが自動化不可 | △ 補助的 |
| C. バックアップなし（ログのみ） | 削除件数・日時のログだけ記録 | 0 | △ リスク許容なら |

**保存期間**: 6ヶ月（6ヶ月経過で自動削除 or 手動整理）
**保存先**: `03_projects/1LC/archive/` + Google Drive（1LC共有フォルダ内に `archive/` を作成）

### A-2-4. 通知ポリシーの決定

| イベント | 通知先 | 方法 |
|----------|--------|------|
| 定期削除 正常完了 | naru | ログファイル（能動確認） |
| 定期削除 エラー | naru + 池田 | Chatwork or Slack通知 |
| ベース件数が閾値（110,000件）超過 | naru | 通知 + 緊急削除トリガー |

### A-2-5. 安全機構の要件

- **削除上限キャップ**: 1回の実行で最大 **60,000件** まで（暴走防止）
- **保護期間**: 直近30日以内の更新/紹介は絶対に削除しない（ハードコードされたガードレール）
- **dry run モード**: `--dry-run` で件数確認のみ。初回は必ず dry run で検証
- **実行ロック**: 同時実行を防ぐ（前回が終わっていなければスキップ）

**完了基準**: 上記すべての要件について岩下様/チーム内で合意が取れていること。

## A-3. 技術選定（所要: 0.5日）

### 比較表

| | A. Airtable Automation + Script | B. 外部cron + REST API (Python) | C. GitHub Actions + REST API |
|---|---|---|---|
| **自動実行** | ◎ Airtable内蔵スケジューラー | ○ Mac launchd / crontab | ◎ GitHub Actions cron |
| **タイムアウト** | △ Script 30秒制限（Business=拡張あり？要確認） | ◎ 無制限 | ◎ 6時間まで |
| **大量削除** | △ 30秒で50件×N回=最大~1,500件/実行 | ◎ 数万件OK（既存スクリプト実証済み） | ◎ 同上 |
| **PAT管理** | ◎ 不要（Automation内で完結） | △ PAT必要（credentials管理） | △ PAT必要（GitHub Secrets） |
| **実行環境の安定性** | ◎ Airtableが落ちない限り動く | △ Macが起動していないと動かない | ◎ クラウドで常時利用可能 |
| **ログ・監視** | △ Automation実行ログのみ | ○ ファイルログ | ◎ GitHub Actions ログ + 通知 |
| **CSVバックアップ** | × Automation Scriptから外部保存は困難 | ◎ ローカル/S3に保存可 | ◎ Artifact保存可 |
| **デバッグ** | △ Airtable Script UIでしかデバッグ不可 | ◎ ローカルで自由にテスト | ○ push→実行のサイクル |
| **追加コスト** | 無料（Automation枠内） | 無料 | 無料（public repo or Free枠） |

### 推奨: **方式B（外部cron + REST API）を主軸、方式Aを補助**

**理由**:
1. 既存の `airtable_delete_api.py` / `airtable_delete_api_chitan.py` が動作実証済み（503リトライも実装済み）
2. 大量削除（数万件）に耐える（Automation Scriptの30秒制限では不足）
3. CSVバックアップをスクリプト内で一体化できる
4. PAT管理は `credentials/airtable-1lc-pat.txt` で既に運用中

**補助（方式A）**: Airtable Automationで「ベース件数監視 → 閾値超過時にnaru通知」を設定（アラートのみ、削除は外部スクリプトに委譲）

**将来的にはC（GitHub Actions）に移行**するのが望ましい（Mac非依存）。ただし現時点ではB+Aで十分。

**確認事項**:
- [ ] Mac launchd での週次実行が安定するか（スリープ時の挙動）
- [ ] PAT の有効期限と更新運用
- [ ] GitHub Actions に移行する場合のリポジトリ構成

## A-4. 設計（所要: 1日）

### A-4-1. 全体フロー

```
[週次 cron (日曜 03:00 JST)]
  │
  ├─ 1. ベース件数チェック
  │     └─ 総件数 < 閾値（例: 90,000件）→ スキップ（ログ記録のみ）
  │
  ├─ 2. 削除対象レコードの収集
  │     ├─ ★物件紹介履歴: 紹介日時 < (today − 90日)
  │     └─ チタン物件一覧: 更新日 < (today − 90日) AND 紹介履歴=空
  │
  ├─ 3. 安全チェック
  │     ├─ 件数がキャップ（60,000件）以下か
  │     ├─ 直近30日のレコードが含まれていないか
  │     └─ 異常検知（前回より極端に多い/少ない → 警告）
  │
  ├─ 4. CSVバックアップ（削除対象のみ）
  │     └─ archive/YYYY-MM-DD_rireki.csv / archive/YYYY-MM-DD_chitan.csv
  │
  ├─ 5. 削除実行（順序厳守）
  │     ├─ ① ★物件紹介履歴（子テーブル・先に削除）
  │     └─ ② チタン物件一覧（親テーブル・後に削除）
  │
  ├─ 6. 結果ログ記録
  │     └─ logs/auto_delete_YYYY-MM-DD.json
  │
  └─ 7. 通知（エラー時のみ外部通知、正常時はログのみ）
```

### A-4-5. エラーハンドリング

| エラー種別 | 対処 | 通知 |
|-----------|------|------|
| 503 / 429（一時エラー） | 指数バックオフリトライ（1,2,4,8,16,30,30,30秒・最大8回） | リトライ成功: ログのみ / 上限到達: エラー通知 |
| 401 / 403（認証エラー） | 即停止。PATの期限切れの可能性 | **即時通知**（PAT更新が必要） |
| 通信エラー | リトライ（同上） | 上限到達時に通知 |
| 削除件数が異常に多い | 警告ログ + 通知。削除自体は実行（キャップ内なら） | 警告通知 |
| スクリプト途中停止 | ログに「削除済みID」を記録 → 次回はスキップ or 続行可 | エラー通知 |

## 両工程表の関係と進め方

```
 工程表A: 定期削除の実装           工程表B: プラン降格調査
 ─────────────────────           ─────────────────────
 A-1 前提確認 ←──────────────── B-2 はA-1の結果を使う
 A-2 要件定義                    B-1 費用確認（並行可能）
 A-3 技術選定                    B-3 API調査（並行可能）
 A-4 設計                        B-4 添付調査（並行可能）
 A-5 実装                        B-5 Automation調査（並行可能）
 A-6 テスト                      B-6 機能差分（並行可能）
 A-7 デプロイ ──────────────→ B-2 定期削除後の安定件数が確定
                                  B-7 外部移行検討（必要な場合）
                                  B-8 判断材料まとめ ← 最終判定
```

**推奨進め方**:
1. **工程表Aを先行着手**（定期削除はプラン関係なく必要）
2. **工程表BのB-1/B-3〜B-6はAと並行**で調査可能
3. **B-2（レコード数ギャップ）はA-7（デプロイ）後に確定**（定期削除の安定運用を確認してから、50,000件に収まるかを実測）
4. B-8の最終判定は**Aが安定稼働してから**（最短で工程表A完了の2〜3週間後）

**合計所要**: A + B並行 = **約2〜3週間**（Bの一部はAと並行するため単純合算より短い）
