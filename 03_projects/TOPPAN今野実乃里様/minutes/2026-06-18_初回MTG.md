## 1. 概要

スーパーマーケット向け会員アプリにクーポン配布機能を追加する Web アプリケーション開発プロジェクトの初回打ち合わせ。クライアント企業（スーパー）が地元企業と連携し、複数業種で使用可能なクーポンを会員向けに配布するシステムの構築を検討。弊社はノーコード開発と AI 駆動開発を活用した安価で迅速な開発を提供する企業として紹介され、要件定義・技術的実現可能性・予算・スケジュール・運用体制について詳細に協議。

## 2. プロジェクト概要と要件

- クライアント企業はスーパーマーケット。既存の会員アプリを保有しており、その会員向けに多業種クーポン配布機能を提供したい
- クーポン配布システムは Web アプリとして構築。既存会員アプリとは別システム
- クーポン配布キャンペーンに参加する企業（ガソリンスタンド、地元企業など）を事前に募集し、各企業で使用可能なクーポンをアプリ内で配布
- 既存アプリの会員数は **約 30 万人**。クーポンシステムのユーザー数もほぼ同規模
- 既存システムの保守運用は Toppan 様が実施

## 3. 技術要件と連携仕様

- **ログイン認証**: 既存アプリの会員番号を API 連携し、既存アプリサーバーに会員番号が存在するか判定する方式。セッション情報の引き継ぎは初期段階では不要
- **クーポン使用方式**: バーコードスキャン / ボタン押下 / スタッフ手動値引きの複数方式が検討対象
- **加盟店ごとのレジ連携**: 各店舗で異なるレジ・決済システムのため個別実装は予算内で困難 → 運用でカバーする方向性
- **スクリーンショット対策**: 技術的に実装可能だが完全防止は困難。クーポンコード定期更新（30秒／1ヶ月／2ヶ月など）が一般的対策。長期運用決定後の追加実装が適切
- **使用履歴管理**: DB に記録し、現場スタッフが確認できる仕組みで重複使用を防止
- **属性データ連携**: 既存システム側で API 開放が必要。取得できればクーポンシステム側で集計・データ分析が可能
- **管理画面**: ダッシュボード形式（期間指定、クーポン使用数確認）。AI サマリー作成・PDF 出力も可能
- **データ提供**: CSV 形式で提携企業に提供。各企業が自社データを確認可能に
- **クーポン設定**: 回数制限（1回のみ／複数回）など複数パターンが技術的に実装可能

## 4. 予算と費用構成

| 項目 | 金額 |
|---|---|
| 初期開発費（管理画面込み） | **300 万円以内** |
| 月額保守運用費 | **7〜8 万円程度**（30万ユーザー基準） |
| 開発ツール費 | 基本は弊社既存契約に含む。専用契約が必要な場合のみ相談 |

- 既存アプリと同サーバーに空き領域があればホスティング可能 → サーバー代追加なし
- 要件定義と開発を一括見積もりとすることが望まれている

## 5. 開発スケジュール

- AI 駆動開発では**要件定義が極めて重要**。完璧なドキュメントがあれば高速開発可能、曖昧だと従来同等速度
- 要件定義が固まった場合、**開発期間 1〜1.5 ヶ月**
- 要件定義書には画面一覧と機能一覧が詳細に含まれ、機能は最小単位まで仕様が詰められている必要あり
- デザイン・カラーは AI 駆動開発では要件定義と同時にフロントエンド開発が進行するため、開発過程でのコミュニケーションが必要

## 6. データ管理とセキュリティ

- テスト環境でのデータ使用に関する社内規定の事前確認が必要
- 属性データ非取得の場合、テストはログイン情報（会員番号＋パスワード）のみ
- 本番環境にテスト用データなし＋本番データ使用不可の場合、既存 DB 側にステージング環境構築が必要 → スコープ拡大リスク

## 7. 契約形態

- 基本モデル: 概算見積もり → 要件定義フェーズ（時間単価・準委任）→ 本見積もり → 実装フェーズ
- 今回: **要件定義と開発を一括見積もり**。追加要件の線引きを明確にした上で提案
- 費用発生は契約書締結後。モックアップ・提案書作成は営業活動の範囲

## 8. クーポン運用に関する検討事項

- クーポン配布期間は未決定。会員特典として継続 or 使用状況・参加企業の増減により半年〜1年で見直し
- スクショ対策は期間限定施策ではオーバースペック → 長期運用決定後に追加検討
- セルフサービス店舗（ガソリンスタンドなど）ではスタッフ声かけが難しいため運用方法調整が必要
