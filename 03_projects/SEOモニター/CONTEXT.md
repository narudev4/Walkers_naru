## 1. プロジェクト概要（What）

「**SEO の自動化**」を実現する社内ツール。記事作成・添削・公開・リライト までを一気通貫で扱い、WordPress と連携して「特化メディア」を AI で量産・運用するためのプラットフォーム。

---

## 2. 戦略の前提（Why） — ここが一番大事

### 2-1. なぜ今 SEO 自動化なのか

**Walkers メディア / AI メディア のような汎用メディアの自動化ではない**。  
ビッグキーワードを AI で量産すると、Google の評価上むしろ**順位が下がる**領域に入っている。  
だから「人間 vs AI」の単純な置換ではなく、**AI でも勝てる領域に張る**ための装置として SEO モニターを位置付ける。

### 2-2. 「AI で勝てる領域」=「情報がない領域」

> 「AI がやっても順位が上がる領域っていうのがあって、それがめっちゃ特化したメディア。なぜかと言うとそもそも情報がないから。情報がない領域は、AI だろうが人間だろうが、情報がある方に人が流れる」（鳳汰）

ニッチが極まりすぎているテーマは、そもそも一次情報も既存メディアも薄い。  
→ そこに体系的なコンテンツを置けば、AI 産でも上位を取りに行ける。

### 2-3. 想定する「特化」の3軸

| 特化軸 | 具体例 |
|---|---|
| **業界特化メディア** | 例: 「マッチングアプリ専門のアプリ開発情報サイト」。アプリ開発費用・作り方・開発の流れ などを、マッチングアプリだけに絞って最強のサイトにする |
| **業務領域特化メディア** | 特定の業務オペレーション領域に絞ったメディア |
| **事例特化メディア** | 事例（ケーススタディ）にフォーカスしたメディア |

→ いずれも「ニッチ × 体系化」の組み合わせで AI コンテンツが勝てるドメインを狙う。

## 3. 機能要件（How）

> 鳳汰のメモ:「俺もまだ要件詰めてないけど、基本的に SEO モニター上で〜」

### 3-1. コア機能（一気通貫の運用フロー）

1. **記事作成** — SEO モニター上で記事を生成
2. **添削** — 生成記事の添削（AI が品質を担保）
3. **公開** — WordPress などへ自動入稿
4. **リライト** — 既存記事のリライト提案・実行
5. **自動更新提案** — 「情報が古くなった箇所」を自動検知してユーザーに通知

### 3-2. 連携

| 連携先 | 目的 |
|---|---|
| **WordPress** | 公開先。MCP 連携（音声では「MC連携」と聞こえるが文脈上 MCP）で自動入稿 |
| 既存 Walkers メディア / AI メディア | 一部機能（リライト箇所の通知など）を流用可能 |

### 3-3. リライト提案フローのねらい

> 「リライトとかも全部できます。自動でも、例えば情報が古くなりましたとか、情報が古いところがあったとしたら、自動で SEO モニターの方から提案してくれる。そういうところができたらだいぶ自動化できる」（鳳汰）

> 「リライトのここをリライトした方がいいですよって通知が来る。それは別に人間が書き換えるにしろ、AI から通知くれたら助かるもんな」（会話）

→ **完全自動化を目指すのではなく、「AI が監視 → 人 or AI が修正」のハイブリッドも許容する**設計でよい。

### 8-2. フェーズ→SEOモニター機能マッピング試案

動画で鳳汰が言及した「記事作成・添削・公開・リライト・自動更新提案」を、**この11フェーズに対応付ける**と次のようになる:

| 動画で言及 | 対応フェーズ | SEOモニターでの実装ねらい |
|---|---|---|
| **記事作成** | 1〜5（戦略→KW→SERP→構成→執筆） | KWマップから記事を引き出して、構成→本文をAIが一気通貫で生成。一次情報・固有名詞・数値の埋め込みフックを必須化 |
| **添削** | 6（校正・編集） | 表記ゆれ・誤字・出典確認・薬機法/景表法・SEO要件・内部リンクのアンカーテキストをチェック |
| **公開** | 7（入稿・公開） | **WordPress MCP連携**で構造化データ・OGP・slug・meta・内部リンクを自動投入 |
| **リライト** | 10（リライト・改善） | 対象選定〜再分析〜改修〜再計測まで支援 |
| **自動更新提案** | 8〜10（初動→測定→リライト） | GSC連動でQuick Wins検出 / 順位低下検知 / 鮮度（公開日経過＋競合更新）監視 → 通知 |
| **戦略・分析の運用** | 1, 2, 3, 9, 11 | サイトごとの戦略書・KWマップ・ナレッジ蓄積を内部DB化（特化メディア量産が前提なので**マルチサイト対応必須**） |

### 8-3. このフロー視点から見えた、動画だけでは見落としていた要件

1. **マルチサイト前提のデータモデル**: 業界特化メディアを複数立てる構想なので、サイト単位で戦略・KWマップ・KPIを持つ必要がある
2. **GSC / GA4 / Ahrefs / Microsoft Clarity 連携**: 効果測定フェーズで利用ツールが集約されており、API/MCP連携の対象として有力
3. **「型化」フェーズ（11）の存在**: 単発記事を作るだけでなく**ナレッジを次サイトに転用する仕組み**を設計に組み込む必要がある
4. **既存スキル群との関係**: フロー内で `/title-gen`, `/create-diagrams`, `/fact-check`, `/article-monitor`, `/seo-article`, `/repost-note`, `mcp__gsc__detect_quick_wins` が明示参照されている
   → SEOモニターは**ゼロから作るのではなく、既存スキルをワークフローとしてオーケストレーションする**プロダクトと位置付けるのが筋
5. **構造化データ・OGP・パンくず・canonical** など SEO 入稿の細目: WordPress MCP に必要な引数仕様の洗い出しが必要
6. **法務チェック（薬機法・景表法・金商法）**: 業界特化メディアで業種次第では必須。デフォルトでチェック項目として組み込む

```
  priority, priorityReason,
  rewriteSuggestions: [{section, action, reason, suggestedContent}]
}
```

→ **動画で鳳汰が「自動更新提案」と言っていた機能は、既に動いている**。  
　`rewriteSuggestions[]` の `suggestedContent` には**記事に即貼り込める本文案**が入っている。
