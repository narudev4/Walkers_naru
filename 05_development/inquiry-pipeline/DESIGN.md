# 問い合わせ半自動化 [A] 設計

作成: 2026-07-25 / ステータス: 設計確定・未実装

## 目的

HP フォームの問い合わせから、営業スパムを除外して本物の見込み客にだけ
日程調整メールの下書きを 15 分以内に用意する。

現状のリードタイムは約 14 時間（Y.G GROUP: 受信 7/15 00:37 → 日調送信 7/15 14:44）。

## スコープ

### 含む
- 問い合わせ検知（ポーリング）
- スパム / 本物の判定
- 4 カレンダーからの空き枠算出
- 日調メール下書き作成（CC 6 名）
- スプレッドシートへの記録
- 日程確定の返信検知 → 確定メール下書き

### 含まない（層2・後回し）
- 案件ディレクトリ生成 / CONTEXT.md
- カレンダーへの予定登録（naru 承認後に手動）

## アーキテクチャ

性質の異なる2層 + ハブとなるスプレッドシート。

```
[層1] GAS（クラウド・24h・5分間隔トリガー）
  ① 新規問い合わせ検知 → スプシに「未判定」行を追加
        ↓
[層2] Windows の claude -p（常時起動・5分間隔）
  ② 未判定行を読む → 本物 / スパム判定 → 結果をスプシに書く
        ↓
[層1] GAS
  ③ 「本物」行を検知 → 4カレンダー空き取得 → 日調下書き作成 → 状態更新
```

最大遅延 15 分（5分 × 3ホップ）。

### 役割分担の根拠

| 処理 | 担当 | 理由 |
|---|---|---|
| Gmail / カレンダー / 下書き | GAS | naru のアカウントで動くため OAuth 設定が一切不要 |
| スパム判定 | Windows claude -p | Claude Max サブスク内で動くため API 課金ゼロ |
| 状態管理 | スプレッドシート | 両層をつなぐハブ。naru が見る画面でもある |

Windows 側は Google 認証を持たない（スプシ経由でのみ層1と通信する）。

### 将来の拡張

層2 を足すだけで [B]〜[E] が同じ構造に乗る。
- tl;dv 録画検知（GAS がポーリング）→ スプシに積む → claude -p が議事録生成
- 日程確定 → 案件ディレクトリ生成 / CONTEXT.md 更新

未解決: Windows の claude -p が `03_projects/` を触る場合、Mac との
ファイル同期手段が必要（S3 同期は 2026-07-02 に凍結済み）。Git 経由が有力。
層2 着手時に決定する。

### 過去の実装が動かなかった理由

GAS プロジェクト `walkers-inquiry-draft-worker`
ID: `1LyutyHOvY-vFraeYBYdaCF2d3hayQIPk8zakr-pym_b3CjsNYixWBna8`

`error_log` タブに残っていた実際のスタックトレースから、故障原因は 2 つ。

**1. `URI malformed`（2026-03-25 〜 04-15）**
```
URIError: URI malformed
    at decodeURIComponent (<anonymous>)
    at doGet (Code:26:27)
```
WPForms の webhook を GET で受け `decodeURIComponent` していたが、日本語・`\/`・
全角スペースを含む本文で例外になる。営業メールは長文で記号が多いためほぼ確実に踏む。
3 月下旬以降、問い合わせがシートに記録されなくなった原因。

**2. `NOTION_TOKEN が未設定`（2026-07-10）**
```
Error: NOTION_TOKEN が未設定
    at createNotionSalesRecord (InquiryDraft:350:21)
    at runInquiryDraftPipeline (InquiryDraft:69:5)
```
Notion 登録が**必須ステップ**として組まれており、そこで例外を投げるとパイプライン
全体が停止する設計だった。7/10 に動かそうとしてここで止まったまま。

### 受信方式の決定（2026-07-25 naru 判断）

**Gmail ポーリングを主経路とする。webhook は使わない。**

WordPress 側の送信は Code Snippets プラグインに仕込んだ PHP
（`wpforms_process_complete` フック → `wp_remote_get` で GET 送信）。
WPForms の Webhooks アドオンは使っていないため、プランの制約とは無関係。

実測で判明した事実:

| 経路 | 状態（2026-07-25 時点） |
|---|---|
| WordPress → GAS webhook | **2026-06-10 以降停止**。error_log にエラーもないためリクエスト自体が届いていない |
| WordPress → メール → Gmail | 正常稼働中（7/24 の問い合わせまで実物を確認） |

`お問い合わせ` タブの実データは 2026-06-10 11:37（小林 大悟）で終わり、
次の行は 7/10 の naru による手動テストデータ。1 ヶ月以上、実データが記録されていない。

**GAS の `doPost` は外部から動作しないことも実測済み**（GET は 200 で JSON を返すが、
POST は `--post301 --post302` でリダイレクトを維持しても HTML「ページが見つかりません」
が返る）。既存コードのコメント「Google Workspace では doPost が制限される」は正しい。

webhook を採用しない理由:

1. **naru 一人では復旧できない。** WP 側の Code Snippets の復活が必要
2. **依存が 3 つある。** WordPress / Code Snippets / GAS デプロイ URL。
   Gmail ポーリングなら Gmail 1 つに減る
3. **過去に 2 回止まり、2 回とも気づけなかった。** 3 月の decodeURIComponent と
   6 月の送信停止。合計で 4 ヶ月以上機能していなかった

将来 WP 側が復旧したら「速い方を採用し、遅い方が取りこぼしを埋める」併用に移行できるが、
[A] の完成には不要。

### 本設計がこれをどう回避するか

| 故障原因 | 対策 |
|---|---|
| webhook の `decodeURIComponent` | Gmail をポーリングする。デコード処理自体が存在しない |
| WP 側の送信停止 | WordPress に依存しない。Gmail に届いていれば処理できる |
| Notion 必須ステップで全停止 | Notion は [A] のスコープ外。呼ばない |
| 故障に気づけない | error_log に書くだけで終わらせず、失敗時は naru に通知する（下記） |

### 失敗の可視化（必須要件）

過去の実装は error_log に静かに溜まるだけで、止まっていることに naru が気づけなかった。
本実装では以下を必須とする。

- 判定・下書き作成に失敗した問い合わせは `対応状況` に `error` を立て、`判定メモ` に理由を書く
- 一定時間（例: 30 分）以上 `未判定` のまま滞留している行があれば naru に通知する
- 「問い合わせが 0 件」と「パイプラインが止まっている」を区別できるようにする

## 判定ロジック

### 中心となる問い

> 相手が「買いに来た」のか「売りに来た」のか。

打ち合わせを申し込んでいる方向で決まる。日本語表現は酷似しているため
キーワードでは判別できず、全文を LLM に読ませる必要がある。

- 「お打ち合わせのお時間をいただけないでしょうか」（相手が依頼）→ 本物
- 「オンラインでご説明させていただけないでしょうか」（相手が売り込み）→ スパム

### 補助シグナル

いずれも**単独では判定を決めない**。上の中心となる問いを補強する材料として扱う。

| 営業側 | 本物側 |
|---|---|
| 送り手が自社商材の特徴・価格・実績を説明している | 相手が自社の課題・状況・構想を語る |
| 配信停止リンクがある | Walkers への依頼・相談・見積・提案の要求 |
| 宛名が不特定（「経営者様」「営業ご担当者様」等） | 具体的な要件・規模・予算・スケジュール |
| 相手が日程候補を提示（TimeRex 等の URL） | |

### 判定してはいけないこと（誤設計の記録・2026-07-25 修正）

1. **メールの長さで判断しない。**
   1 行の本物（前田様「アプリの開発費用の相談」）も、1 行の営業もある。

2. **冒頭の自社紹介で判断しない。**
   Y.G GROUP は「まぜそば・ラーメンブランドを5店舗経営しており」から始まるが本物。
   必ず全文を読み、末尾の依頼の向きで決める。

3. **相手の日程提示を決定打にしない。**
   本物の問い合わせでも「来週の月火が空いています」と書いてくる可能性がある。
   営業と判定してよいのは「自社商材の売り込み **かつ** 日程提示」の場合。

4. **商材のジャンルで例外を作らない。**
   AI ツール / システム開発 / 補助金 / 経理 — ジャンルは判定に一切関係しない。
   売り込みは売り込み。トレンドタウン（ChatGPT法人導入の営業）も
   シェルパーズ（助成金を使った SNS 運用内製化の営業）も営業。

### 分類と処理

| 判定 | 処理 |
|---|---|
| 本物（inquiry） | 日調メール下書きを自動生成 |
| 営業（sales） | 下書きは作らない。**スプシに別リストとして記録**（後でまとめて見返せるように） |

判定に迷った場合（confidence: low）も本物として扱い、下書きを作ったうえで
「要確認」と明記する。naru が送信 / 破棄を判断する。

### 実データ

- グレーだが本物の実例: 株式会社Y.G GROUP（2026-07-15）
  ラーメン店 5 店舗の自社紹介から始まるため冒頭数行では営業に見えるが、
  会員 CRM プラットフォーム構築の明確な発注意図がある。初回 MTG 成立済み。
- 直近 7 件はすべて営業スパム（AI 導入 / 経理 BPO / 給与計算 / 相互リンク /
  SNS 運用 / 成果報酬アポ代行 / 海外融資系）。

## 日程算出

### 同席者条件

MTG は「naru 必須 AND（古谷 or 渡辺のどちらか同席可能）」で成立する。

| カレンダー | 役割 |
|---|---|
| `primary`（naru） | 必須参加者 |
| `daiki.furutani@walker-s.co.jp` | 古谷・仕事 |
| `fullsrodd@gmail.com` | 古谷・個人 |
| `atsushi.watanabe@walker-s.co.jp` | 渡辺 |

古谷の 2 カレンダーは OR 合成（いずれかに予定があれば busy）。
古谷 busy と渡辺 busy の重複区間のみハードブロック。

確認済み: 社内メンバーのカレンダーは naru のアカウントから読める
（フリー/ビジー共有のため予定タイトルは見えないが、時間帯は取得できる）。

### ブロック分類

| 条件 | 分類 |
|---|---|
| 予定の duration < 2時間 | ハードブロック（除外） |
| 予定の duration >= 2時間 | 貫通（作業ブロックとみなす） |
| 終日イベント | 貫通（作業ブロック / 記念日扱い） |
| `transparency: TRANSPARENT` | 貫通 |

閾値は `INQUIRY.HARD_BLOCK_MAX_HOURS = 2`（2026-07-25 naru 判断で 2 時間を維持）。

同席者条件は区間演算で実装済み: `naru ∩ (古谷 ∪ 渡辺)`。
古谷の 2 カレンダーは和集合で「空き」を取るため、いずれかが空いていれば同席可能と扱われる。
`MIN_SLOT_MINUTES = 60` 未満の細切れ枠は候補に出さない。

### その他

- 営業時間: 11:00〜18:00
- 除外日: 土日祝
- 曜日は日付から算出する（手計算禁止）
- 時刻区切りは `~`

## 日程確定フェーズ

相手からの返信を検知 → 日時を抽出 → 確定メール下書きを作成するところまで自動。
カレンダーへの予定登録と案件ディレクトリ生成は naru 承認後（層2・スコープ外）。

## 冪等性

同じ問い合わせを二重処理しないこと。スプシの行に処理済みフラグを持たせ、
Gmail の Message-ID をキーにする（1LC の `backup.py` で `chunkId` を入れたのと同じ考え方）。

## 完了の定義

7 日間の運用継続をもって完了とする。それまでは「実験中」。
