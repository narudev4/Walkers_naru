# YouTube AI動画 台本生成（HeyGen用）

記事URLまたはテーマから、HeyGen動画制作用の台本を自動生成する。
動画の尺は固定せず、元記事の長さ・見出し構造にそのまま比例する。記事が長ければ台本も長くなる。

## 入力

$ARGUMENTS に記事URLまたはテーマが渡される。

- URLの場合: WebFetch or Chrome MCPで記事を取得し、内容をベースに台本化
- テーマの場合: WebSearchで情報収集し、台本化

## ソース別の台本生成戦略（URL host で判定・CRITICAL）

入力 URL のホスト名で **台本構造の作り方が変わる**。これを間違えると下流の音声分割精度・口語の自然さ・視聴継続率がすべて落ちる。

### URL host = walker-s.co.jp（自社メディア記事）

- 原文は最初から listicle / how-to 構造（X選 / N つの〇〇 / ステップ解説）
- **記事の h2/h3 見出しに従って台本を作る**（後述「台本の長さ（尺の決め方）」セクションの基本ルール通り）

### URL host = note.com（論考・主張型記事）

- 原文は essay 構造（h2 = 主張ステップ、結論が後半、現場相談ベースではなく論理展開）
- **原文の章立てに従ってはいけない**。Walkers 標準の listicle / how-to 構造に **リフレーム** する
- 原文は素材であって型ではない

#### リフレーム手順

1. **既存成功スクリプト3本を Read** で読み込む（型として真似する）:
   - `projects/what-is-adalo/script.md`
   - `projects/what-is-claudecode/script.md`
   - `projects/saas-survival-4quadrant/script.md`（初の note リフレーム実証例）
2. 原文 `article.md` から **コア主張 / 固有データ / 固有名詞** を抽出（数字・固有名詞は一切落とさない）
3. Walkers listicle 構造に再構成する。型の例:
   - 「X 個の〇〇」「N 選」
   - 「N つの対策 / N つのポイント」
   - 「N タイプ別戦略」「N 象限で整理」
   - 「N つのステップ解説」
4. **リフレーム後の sec 数の目安**:
   - 原文 h2 数より少なく集約する（例: 原文 7 h2 → リフレーム後 5 sec）
   - **背景 1 + 列挙 N + まとめ 1** の枠で **4〜6 sec** が目安
   - 列挙パートはタイトル本体の「N 個の」「N 選」「N つの」と一致させる（例: タイトルが「3 つの真実」なら列挙パート = 3 sec）
   - 短すぎ（3 sec 以下）= 中身が薄い／長すぎ（7 sec 以上）= 集約できていないサイン。再度集約する
5. その他は通常の yt-script フロー（冒頭5枚固定 / CTA8枚固定 / DNA口語 / TTS-friendly セルフチェック）

#### 経緯（なぜこのルールが必要か）

過去 Row 11 (`saas-survival-4quadrant`) で note 原文の章立てに従って台本化した結果、3 重の失敗が出た:

1. **Whisper 音声分割の精度低下** — 原文の長文 essay スタイルが Whisper segment 化と相性が悪く scene 分割マッチが失敗
2. **口語の自然さが出ない** — 論考型の段落構造を残すと「〜なんですよね」「実はですね」のような Walkers DNA が乗りにくい
3. **視聴継続率の構造になっていない** — listicle/how-to は「X 選」など期待値設定で離脱を防ぐが essay は途中で結論が見えず離脱しやすい

リフレームして listicle 化することで Whisper 分割 29/29 全 high 信頼マッチ・DNA 口語自然・視聴継続率構造に揃った。

## 話し方のDNA（必ず再現する口語パターン）

以下の表現パターンを台本全体に散りばめること:

- 「というのもですね、」（理由の導入）
- 「〜んですけども、」「〜んですけど、」（逆接・補足）
- 「〜なんですよね。」（共感・強調）
- 「めちゃめちゃ」（強調の副詞）
- 「〜ていう風に思います。」（意見の表現）
- 「〜かなという風に思います。」（柔らかい提案）
- 「つまりですね、」（要約の導入）
- 「実はですね、」（新情報の導入）
- 「〜というわけです。」（結論）
- 「是非最後までご覧ください。」（視聴継続の誘導）

### 文末表現のバリエーション（AI感削減・CRITICAL）

**同じ文末パターンが3回以上連続しないこと。** 以下のバリエーションを使い分ける。

#### 文末のカテゴリと使い分け

| カテゴリ | パターン例 | 使用頻度 |
|---------|----------|---------|
| **断定** | 「〜です。」「〜ます。」 | 全体の20%程度 |
| **共感** | 「〜なんですよ。」「〜なんですよね。」 | 全体の20%程度（1スライド最大2回） |
| **補足接続** | 「〜んですけど、」「〜んですけども、」 | 全体の15%程度 |
| **問いかけ** | 「〜と思うんですよ。」「〜じゃないですか。」 | 全体の10%程度 |
| **提案** | 「〜かなと思います。」「〜をおすすめします。」 | 全体の10%程度 |
| **強調** | 「〜というわけです。」「〜ということなんです。」 | 全体の10%程度 |
| **体言止め** | 「〜という点です。」「〜というアプローチです。」 | 全体の10%程度 |
| **余韻** | 「〜んですよね...。」「〜と言えるかもしれません。」 | 全体の5%程度 |

#### NG例（AI感が出る）
```
〜なんですよ。〜なんですよね。〜なんですよ。〜なんですけど、〜なんですよね。
```
→ 「なんですよ」系が5連続。ロボット感が強い。

#### OK例（人間的）
```
〜です。というのもですね、〜んですけど、〜と思うんですよ。
ここが面白いところで、〜という点です。つまり〜ということなんです。
じゃあ〜かというと、そう単純ではないんですよね。
```
→ 断定→補足→共感→体言止め→強調→問いかけとバリエーションが豊富。

#### 台本生成時のセルフチェック
台本を書き終えた後、各スライドの文末パターンを確認し、同じカテゴリが3回以上連続していたら別のカテゴリに書き換える。

### 使用量の制限（AI感削減・CRITICAL）

| 表現 | 上限 | 理由 |
|-----|------|------|
| 「〜なんですよね」「〜なんですよ」 | **1スライドあたり最大2回** | 多用するとAI感が出る。人間はここまで連発しない |
| 「めちゃめちゃ」 | **動画全体で3回以内** | 入れすぎると不自然 |
| 「続いてですね」 | **動画全体で2回まで** | セクション遷移を全部これにすると機械的 |

### セクション遷移のバリエーション（最低5パターン使い分ける）

同じ遷移表現を連続で使わないこと。以下からランダムに選ぶ:

```
- 「それではまず最初にですね、〜について解説していきます。」（最初のセクションのみ）
- 「続いてですね、〜について解説していきます。」（最大2回まで）
- 「さて、ここからは〜について見ていきましょう。」
- 「では次にですね、〜についてお話しします。」
- 「ここからはですね、〜に焦点を当てていきます。」
- 「それではですね、〜について結論をお話しします。」（結論セクションのみ）
- 「最後にですね、補足として〜をご紹介します。」（最終セクションのみ）
```

### 比較表・リストの読み上げルール（AI感削減）

スライドに比較表やリストがある場合、**全項目を棒読みしない**:

1. **最も重要な2〜3項目だけ**をナレーションで深く語る
2. 残りの項目は「他にも〜がありますが、詳しくはスライドをご覧ください」で流す
3. 各項目の間に**感想や補足を挟む**（「ここが面白いところで」「意外なのが」等）

❌ NG例（棒読み）:
```
自由度はノーコードは中程度。バイブコーディングは高い。
学習コストはノーコードはツールの操作。バイブコーディングはプロンプト。
所有権はノーコードはプラットフォーム依存。バイブコーディングは自分で保有。
```

✅ OK例（人間的）:
```
ここで特に注目してほしいのが、自由度と品質管理のトレードオフなんですよ。
のーこーどは自由度を制限する代わりに、プラットフォームが品質を担保してくれる。
一方バイブコーディングは自由度が高い分、品質管理は全部自分でやる必要がある。
他にも学習コストや所有権の違いがありますが、詳しくはスライドをご覧ください。
```

### 絶対使わない表現
- 「皆さん」の多用（1回まで）
- 「それでは」の連続
- 箇条書きの棒読み感
- **冒頭ナレーションでの結論前置き** (「結論からお伝えすると、」「結論を申し上げると、」「結論から言うと、」)
  - スライド3 (動画の趣旨) の **スライド表示** での結論先出し（キャッチ1行）は OK・むしろ構造的に必要
  - ただし **ナレーション本文** でこの前置きを使うと、スライドの結論先出しと二重になって冗長・不自然になりやすい
  - 完全禁止ではなく **「冒頭ナレーションでは原則避ける」** 程度のニュアンス。本文の途中で論点整理として使うのは OK
  - NG (冒頭で冗長): 「そこで本動画ではですね、結論からお伝えすると、〇〇を5つと…」
  - OK: 「そこで本動画ではですね、〇〇を5つと…」（前置きなしで本題へ）

### TTS-friendly 表記戦略（2026-05-08 追加・CRITICAL）

ElevenLabs JP voice の癖を踏まえて、台本生成時点で次の表記指針を守る。**辞書 (BASE_MAP / pronunciation JSON) に頼らず、台本そのものを TTS-friendly に書く方針。** 都度辞書追加すると無限に増えてキリがない。

#### 1. カタカナ複合語

「ノーコード」「ローコード」のような **長音記号 (ー) を含むカタカナ複合語** は、ひらがな化（旧ルール `のーこーど`）すると逆効果（「の高度」「濃厚度」「愛のコード」と誤読）。

- **第一選択**: カタカナのまま使う（`ノーコード`、`ローコード`）。前後の文脈次第で 50-80% は正常に読まれる
- **誤読時の対応**: 中黒で区切る（`ノー、コード`）。これでも一定確率で崩れる
- **どうしてもダメな時**: 別表現に置き換え（`AI開発専門` `コード不要のツール`）。意味が変わらない範囲で
- **避ける表記**: `のーこーど`（ひらがな化）、`えーあい のーこーど`（空白区切りのひらがな化）— どちらも検証で逆効果と確認済み (claudecode-security-failure)

#### 2. 同音異義の漢字熟語

訓読み熟語のうち、**音読みでも通じてしまう熟語** は誤読が起きる。代表例:

| 元の語 | 誤読 | 対処 |
|---|---|---|
| 事故事例 (じこじれい) | じこうじれい (事項事例) | `事故・事例` に分割、または `事故ケース` `事故とその実例` に言い換え |
| 既存 (きそん) | きぞん | `もともとある` `現行の` に言い換え (元 BASE_MAP に登録済) |
| 行う (おこなう) | いく | (元 BASE_MAP に登録済) |

**判定基準**: 訓読み熟語で「音読み + 音読み」「音読み + 訓読み」の境界が曖昧なものは要注意。「事故事例」は「じこ + じれい」(訓+訓) だが、「じこう + じれい」(音+訓) と読まれてしまう。

#### 3. 数字 + 助数詞・選択語

**一般則: 数字 + 助数詞はアラビア数字のままで OK**

`5つ` `7つ` `11個` `3倍` `2回` のような「数字 + ひらがな助数詞 / 漢字計量単位」は **アラビア数字のまま書いて良い**。ElevenLabs JP voice は通常「いつつ」「ななつ」「じゅういっこ」「さんばい」と正しく読む。漢数字化（`七つ` 等）やひらがな化（`ななつ` 等）は不要（むしろ「ひちつ」等で逆効果のこともある）。

個別パターンで誤読が確認されたら `voice_pronunciation.json` に追加する運用（辞書を肥大化させない）。

**例外: `N選` だけは漢数字化必須**

`5選` `3選` のような **アラビア数字 + 漢字選択語「選」** は誤読頻発。

- **必ず漢数字化**: `五選` `三選` `七選`
- **代替**: `5つ` `3つ`（より自然な日本語に倒す）
- **理由**: ElevenLabs が「ごせん」「さんぜん」と読み、Whisper が「5000」「3000」に補正してしまう

#### 4. 結論前置きの禁止

「結論からお伝えすると、」「結論を申し上げると、」「結論から言うと、」を**ナレーション冒頭で使わない**。スライド側で結論先出ししているので二重になる。詳細は [絶対使わない表現](#絶対使わない表現) 参照。

#### 5. 台本最終チェック (台本生成プロセスの最後に必ず実行)

台本を出力する直前、Claude (=台本を書いている自分) は以下のセルフチェックを行う:

- [ ] カタカナ複合語 (4音節以上 + 長音記号含む) を grep。`ひらがな化されていないか`、`不自然な中黒が入っていないか` 確認
- [ ] 同音異義熟語 (事故事例 / 既存 / 行う等) を grep。誤読リスクある場合は別表現に置換
- [ ] アラビア数字 + 助数詞 (`\d+選` `\d+名` `\d+種` `\d+通り`) を grep。漢数字化または `〜つ` 化
- [ ] 「結論からお伝えすると」「結論を申し上げると」を grep。**ヒットしたら必ず削除**
- [ ] 丸数字（①〜⑨）がナレーション本文に残っていないか grep

**このチェックを台本完成の必須工程**にする。チェック結果を「TTS-friendly 自己チェック完了」として明示的にユーザーに報告する。

## 台本の長さ（尺の決め方）

**固定の尺テンプレートは使わない。** 元記事の見出し構造（h2/h3）にそのまま追従する。

### 基本ルール
- 記事のh2見出し1つ → 動画の1セクション（セクションタイトル + 解説スライド1〜3枚）
- 記事のh3見出し1つ → 解説スライド1枚
- **記事内のSTEP/手順が番号付きで列挙されている場合 → 各STEP=1スライド（複数STEPを1スライドにまとめるのは絶対NG）**
- h2が3つなら3セクション、h2が10個なら10セクション。上限なし。
- 記事が長ければ台本も長くなる。記事が短ければ台本も短くなる。
- 情報を省略・圧縮しない。記事の内容をすべて台本に反映する。

### スライド枚数の目安（あくまで目安）
- 1セクションあたり: セクションタイトル1枚 + 解説1〜3枚 = 2〜4枚
- 記事のh2が6つなら、本編は12〜24枚程度
- これに冒頭5枚 + 末尾CTA8枚が加わる

### 各解説スライドの秒数目安
- セクションタイトル: 5秒
- 解説スライド: 20〜40秒（内容量による）
- 1スライドの台本テキストが長すぎる場合は、複数スライドに分割する

## 台本構造

すべての動画は以下の3パートで構成される:
1. **導入**（冒頭5枚・必ず5スライドに分割）
2. **本編**（セクション × N）— 記事のh2ごとに1セクション。各セクション = セクションタイトル + 解説スライド1〜3枚
3. **CTA**（固定8枚）— 宣伝 + 問い合わせ誘導（固定テキスト）

### 冒頭5枚の構造（CRITICAL — yt-slidesスキルと完全一致させること）

台本で**必ず5つの独立したスライドとして書く**。1スライドに詰め込むのは絶対NG。
※ 目次スライドは廃止。作成しない。

**冒頭5枚の長さ目安**（個別スライドの単独尺。**台本に書くタイムコード（後述）は前スライドからの累積値**で別物）

| スライド | 種類 | 台本に書く内容 | 単独尺の目安 |
|---------|------|--------------|---------|
| 1 | タイトル | 挨拶（「皆様こんにちは〜」）+ テーマ紹介 | 20〜30秒 |
| 2 | 問題提起（セリフ抽出型） | テーマの背景・課題・悩み共有（「こういったご相談を〜」） | 20〜30秒 |
| 3 | 動画の趣旨（内容リスト型） | 結論先出し + 本動画の概要 + 「是非最後までご覧ください」 | 25〜35秒 |
| 4 | 自己紹介 | 固定テキスト（下記参照） | 15秒 |
| 5 | チャンネル登録 | 固定テキスト（下記参照） | 8秒 |

**なぜ5分割が必須か:** この台本からyt-slidesスキルが自動でPPTXを生成する。スライドスキルは冒頭5枚を「タイトル/問題提起/動画の趣旨/自己紹介/チャンネル登録」の固定構成でXMLコピー生成する。台本のスライド番号と構造が一致しないと、スライド生成・音声分割の下流工程がすべて壊れる。

### 冒頭1〜3枚の質的ルール（CRITICAL — 離脱率に直結）

冒頭の1〜3枚は視聴継続率の鍵。以下のルールを厳守する。

#### スライド1（タイトル）
- **タグは禁止**（「【〜で作ったアプリ】」のような頭文字タグはサムネと重複するので廃止）
- **サブタイトルは禁止**（「【失敗例＆成功のコツも徹底解説】」のような煽り補足も廃止）
- **タイトル本体は3行構成**で大胆に。情報量より視認性
- 固有名詞（Claude Code 等）はタイトル本体に組み込む（タグ扱いしない）

例:
```
NG: タグ「【Claude Codeで作ったアプリ】」 + タイトル「収益化する11の方法」 + サブタイトル「【失敗例＆成功のコツも徹底解説】」
OK: タイトル「Claude Codeで\n作ったアプリを収益化する方法\n11選」のみ
```

#### スライド2（問題提起 / セリフ抽出型）
- **ナレーション原稿の中の "視聴者の独白セリフ" 部分を抽出して鉤括弧「」で囲んで表示**
- スライドはナレーションに従属するが、スライド2は **ナレーション全文ではなく "セリフ部分のみ" を抽出**
- 視聴者が口にしそうな自然な独白で書く（業界用語禁止・主語明示）
- 内容によっては複数セリフを並べてもOK

**ナレーション原稿の「セリフ部分」を書くときの分割ルール（CRITICAL）:**
- **1セリフは "1呼吸で言える長さ"（目安40字以内）** に収める
- 原文（記事）がカンマ区切りの長い1文でも、**人間が話す自然な区切りで「。」で2文に分割する**
- 不安・疑問・困惑のような感情が2つ以上含まれる場合は分ける
- ナレーション側を2文にすれば、スライド2のセリフ抽出も自動で2鉤括弧になる

例:
- NG: 「クロードコードで動くものは作れたんだけど、本当にこれで起業して食べていけるのか、何から手を付ければいいのか全くわからない」（1文・60字超）
- OK: 「クロードコードで動くものは作れたんだけど、本当にこれで起業して食べていけるのか…」「何から手を付ければいいのか全くわからない」（2文）
- スライド2 では2鉤括弧として表示される

**slides.json で複数セリフを書く形式（CRITICAL）:**
- 複数の鉤括弧セリフは **`\n\n` (改行2つ) で区切って lines フィールドに書く**
- 1 つの lines 文字列に連結して書くと、スライド上で 1 つの鉤括弧に統合されてしまい NG（鉤括弧の間にスペースが無い詰まった見た目になる）
- 縦位置が下にずれて見える場合は `top_in: 1.5` （inch 単位）を併用して TextBox を上に寄せる（yt_slide_engine 既存対応）

例 (slides.json):
```json
{
  "type": "text",
  "lines": "「クロードコードで動くものは作れたんだけど、本当にこれで起業して食べていけるのか…」\n\n「何から手を付ければいいのか全くわからない」",
  "top_in": 1.5
}
```

**よくある間違い**:
- ❌ `"lines": "「セリフ1…」「セリフ2…」"` (1 文字列に連結 → 1 鉤括弧の連続表示になる)
- ❌ `"lines": "「セリフ1…」\n「セリフ2…」"` (改行 1 つでは間隔が足りず詰まる)
- ✅ `"lines": "「セリフ1…」\n\n「セリフ2…」"` (改行 2 つで適切な間隔)

**ナレーションに独白セリフが無い場合の手順（CRITICAL）:**
1. **ナレーション側を先に「視聴者独白型」に書き直す**（"こんなご相談を〜「〜」と。" のような型）
2. その後、独白部分を抽出してスライド本文化
3. **スライド本文を先に決めてから後付けでナレーションに鉤括弧を入れるのは禁止**（音声とスライドが乖離する）

例（claudecode-app-monetize):
```
ナレーション: 「最近こういったご相談を本当に多くいただくんですよ。『Claude Codeで試作までは作れたんだけど、どうやってお金を生む仕組みにすればいいのか決められない』と。…」
スライド本文（セリフ抽出）: 「Claude Codeでアプリは作れたけど、ビジネスモデルの設計でつまずいてしまう…」
```

#### スライド3（動画の趣旨 / 内容リスト型）

**スライド表示とナレーションは別物として書き分ける**。書く場所を間違えると ElevenLabs が丸数字を誤読する事故が起きる。

**スライド表示（slides.json に書く）**:
- 固定構造: **キャッチ1行 + 「【本動画の内容】」見出し + 内容リスト ① ② ③**
- 結論先出し（「〜を全11個、事例付きで整理！」のような形）
- 丸数字 ① ② ③ は slides.json 側にだけ書く（PPTX で視覚的に表示される。ElevenLabs には渡らない）

**ナレーション（script.md の `### 【スライド3】` セクションに書く）**:
- スライド表示の文面を **そのままコピペしない**。読み下しで自然に列挙する
- **丸数字（①〜⑨）も「【本動画の内容】」見出しも一切書かない**（`### 【スライドN】` セクション本文は HTML コメント以外すべて ElevenLabs に渡される。丸数字は「やち」「み三」のように誤読される）
- 例: 「99パーセントが失敗する本当の理由、成功するための2つの鉄則、そしてアプリ開発に逃げてしまう心理と対策まで、一気通貫で整理していきますので、是非最後までご覧ください」

例:
```
# slides.json（表示用 — ① ② ③ OK）
{
  "type": "text",
  "lines": "収益化の選択肢を全11個、事例付きで整理！\n\n【本動画の内容】\n① 収益化方法11選\n② 起こりがちな失敗4選\n③ 成功させる4つのポイント"
}
```

### 専門用語ルール（L1 + L2）— 離脱率対策

| レベル | ルール | 適用範囲 |
|---|---|---|
| **L1: 列挙の禁止** | 専門用語を3語以上連続で羅列するのはNG。スライド側のリストに任せ、ナレーションでは概念だけ語る | 動画全編 |
| **L2: 冒頭は素人言葉のみ** | 冒頭スライド1〜3のナレーション内では「専門用語」を使わない | 冒頭3スライド |

**「専門用語」の判定基準（CRITICAL）:**

以下のいずれかに該当する語は「専門用語」扱い:
1. **業界用語** … その業界の人だけが日常的に使う語（例: フリーミアム、サブスク、アフィリエイト、ペルソナ、PMF、CVR、ARR）
2. **カタカナ専門語** … 一般向けに日本語訳が広まっていない外来語（例: スポンサーシップ、リテンション、エンゲージメント、コンバージョン）
3. **略語・頭字語** … LP、MVP、API、SaaS、UI/UX、KPI、ROI など
4. **業界比喩** … その業界での慣用的な意味を持つ語（例: 「フロー」「導線」「導入」など、文脈次第）

**判定の指針:** 迷ったら「中学生がスマホでこの動画を見たときに意味がわかるか？」を基準にする。NG なら素人言葉化する。

**冒頭3スライドのナレーションでの境界（L2の例外運用）:**
- 「ビジネスモデル」「収益モデル」「アプリ開発」: グレー。**1スライド内に1回までは許容**、それ以上の繰り返しは素人言葉化（「お金を生む仕組み」「お金を稼ぐ方法」など）
- 「Claude Code」「Walkers」のような固有名詞: 専門用語扱いしない（タイトルに含まれていれば視聴者は知っている前提）

**NG例（冒頭で）:**
- 「フリーミアムにすべきか、サブスクにすべきか、それともアプリ内課金か…」 ← L1+L2違反
- 「PMFとARRの観点から…」 ← L2違反（略語2連発・中学生に通じない）

**OK例（冒頭で）:**
- 「どうやってお金を生む仕組みにすればいいのか」（=ビジネスモデル/収益モデルの素人言葉化）
- 「アプリは作れたけど、その先がわからない」（=具体的シーン）
